# Harness Template Pack

This pack is a copy-ready starting point for the harness that surrounds an agent as it works. A harness here means the small set of files that give an agent its instructions, its scope, and its memory, so the agent does not have to hold all of that in its head, and so its work can be checked and resumed. Copy these files into your own project, fill in the square-bracket placeholders with your own details, and then keep them current as the project changes, because an out-of-date harness quietly points the agent in the wrong direction.

## What each file is for

- [AGENTS.md](./AGENTS.md) is the starter instruction file for a repository. It records the tech stack and versions, the architecture and conventions the agent must follow, the verification commands it must run before declaring work done, and what it must never do without asking. Use it as the single place where the rules of the project live.
- [feature_list.json](./feature_list.json) is the machine-readable scope of the work. Machine-readable here means a file written in JavaScript Object Notation (JSON) that a script can read and update, so both a person and a programme can work from the same list. Each feature in the file is a triple, which means it carries three linked parts: a behaviour description, a verification command, and a current state. The states are `not_started`, `active`, `blocked`, and `passing`, and a feature moves from `active` to `passing` only when its verification command succeeds.
- [init.sh](./init.sh) is the environment health-check script. Run it with `bash init.sh` before starting work, and it checks the language runtime version, checks that the required tools are present, checks that the dependencies are installed, and checks that the tests can run. Each check prints a clear pass or fail line, and the script stops at the first failure, so a broken environment is found before any work begins.
- [goal-template.md](./goal-template.md) is the goal file for loop engineering. Loop engineering here means designing a repeated cycle in which an agent works, checks its result, and decides what to do next, and the goal file holds that cycle together by stating one goal in one sentence, the definition of done as verifiable conditions, the loop type, and the stop conditions. The loop types are goal, timed, and maker-checker, and each one is explained in the template with guidance on when to choose it.
- [loop-state-template.md](./loop-state-template.md) is the loop state file. It records the current goal, the current step, the features done, in progress, and blocked, the last verification result, and the next action, so a loop can be paused at the end of one session and resumed in the next without losing its place.

## How the files work together

The files form one connected flow, and each file hands the next one what it needs. [AGENTS.md](./AGENTS.md) is the index the agent reads first, because it tells the agent how the project works, which commands prove that work is done, and which actions need permission. From there the agent turns to [feature_list.json](./feature_list.json), which is the machine-readable scope, because that file lists exactly which features are in scope and what command proves each one. Before the agent starts on those features, it runs [init.sh](./init.sh), which is the environment check, because a feature cannot be verified in an environment that is not working. Then the [goal-template.md](./goal-template.md) and [loop-state-template.md](./loop-state-template.md) files carry a loop's state between sessions, because the goal file states what the loop is trying to achieve and when it stops, while the loop state file records where the loop has reached, what was last verified, and what the single next action is. The loop state file points back to `feature_list.json` for the feature lists, so the two stay in step and the JSON file remains the source of truth when they disagree. Work through the flow in that order, and update the state files as you go, so the harness always describes the work as it really stands.

## Which chapters use them

- [Chapter 1, Agent Architecture and State Machines](../chapter-01-agent-architecture-state-machines/README.md) uses the pack for the harness frame and for feature lists, because that chapter introduces the harness itself and the idea that scope should be written down before the agent starts.
- [Chapter 4, Advanced Memory and Context Engineering](../chapter-04-advanced-memory-context-engineering/README.md) uses [AGENTS.md](./AGENTS.md) for progressive disclosure, because that chapter shows how an agent reads a short index first and loads detail only when it needs it, which keeps the working context small.
- [Chapter 9, Self-Correction and Reflection Loops](../chapter-09-self-correction-reflection-loops/README.md) uses the goal and loop state templates for the correction loop, because that chapter builds the cycle in which an agent checks its own result, records what failed, and tries again with the failure in view.
- [Chapter 10, Trajectory Evals and Continuous Integration Gates](../chapter-10-trajectory-evals-ci-gates/README.md) uses [feature_list.json](./feature_list.json) and [init.sh](./init.sh) for verification, because that chapter turns the verification commands into checks that run automatically, so a feature counts as done only when its evidence passes.

Start with chapter 1 to set the harness up, then return to these templates whenever a later chapter asks for one of them, and adapt the placeholders to your own project as you go.
