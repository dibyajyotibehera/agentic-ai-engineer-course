# Chapter 11 — Graceful Degradation and Fallbacks

*Keep an agent useful when a model, a tool or a budget fails — and know when to stop rather than serve something wrong.*

## What this chapter is about

Every agent you ship will, sooner or later, meet a day when something it depends on stops working. A model provider returns errors for an hour, a tool that answered in two hundred milliseconds starts timing out after twenty seconds, a runaway loop burns through a day's budget before lunch, or the network drops altogether while a user is mid-task. The question is never whether this will happen; the question is what your agent does in the first minute after it happens, and whether that behaviour was designed in advance or improvised in a panic. This chapter is about designing that behaviour, so that failure changes what the agent can do, in a planned order, instead of changing whether the user can trust it at all.

That distinction matters because an agent is not a web page. A web page that fails can show an error and wait, and nobody is harmed beyond a lost click. An agent that fails badly can do worse than nothing: it can retry a payment, invent an answer with great confidence when the retrieval step that would have grounded it is down, or quietly switch to a weaker model that was never evaluated and start giving worse answers without telling anyone. Graceful degradation, then, is not a euphemism for tolerating failure. It is the discipline of deciding in advance, for each kind of failure, how much capability you are willing to lose, in what order you will lose it, and at what point losing more would be worse than stopping. The rest of this chapter works through that discipline step by step, from detecting that something is wrong, through the mechanisms that contain the damage, to the moment when the honest answer is a refusal.

## The idea in plain words

Imagine a support agent that answers questions about a product. On a good day it reads the question, retrieves the relevant help articles, drafts an answer with a frontier model, and cites its sources. Now imagine the retrieval service goes down. The naive agent carries on regardless, because nothing in its code checks whether retrieval worked, and it answers from the model's memory instead — fluently, confidently, and sometimes wrongly. A gracefully degrading agent behaves differently, because its designer asked beforehand what a good answer looks like when retrieval is unavailable, and the answer turned out to be a narrower one: it can still answer questions about the product's public pricing page from a small cache, it can still file a ticket for a human to answer, and it can say plainly that it cannot verify the details right now. It has lost capability, but it has not lost honesty, and the user can still get something useful done.

That example carries the whole idea. Degradation is a designed behaviour, not an accident, and it is designed as a ladder: each rung is a smaller, cheaper, more reliable way of serving the same request, and the agent steps down the ladder only when the rung above it has provably failed. The ladder is also labelled, so that every step down is visible in logs, in metrics and, where it matters, to the user. An agent that silently degrades is an agent whose operators cannot tell whether it is working well or merely working, and whose users cannot tell whether an answer came from the best available evidence or from a guess. So the first rule of this chapter is that a fallback you cannot see is not a fallback at all; it is a hidden change of behaviour, and hidden changes of behaviour are how production incidents become trust incidents.

The second rule follows from the first, which is that every rung of the ladder must have been tested before it is needed. A fallback model that has never been run against your evaluation set is not a fallback; it is a hope. A cached answer that has never been checked for staleness is not a fallback; it is a stale answer waiting for its moment. A browser fallback that has never been exercised against the real site is not a fallback; it is a demo. Much of this chapter, and most of the exercises, is therefore about proving the fallback path works while everything is still healthy, because the hour of the outage is the worst possible time to discover that it does not.

## Detecting the failure before you degrade

Nothing in this chapter works without detection, and detection is harder than it looks, because an agent fails in more ways than a web service does. A web service is either up or down; an agent can be up and still wrong, up and still slow, or up and still ruinously expensive. So detection has to cover four different kinds of signal, and each kind needs its own threshold, because each kind fails in its own way.

The first kind is the error signal, which is the most familiar: the model provider returns a status code, the tool raises an exception, the network times out. Here the crucial skill is classification, because not every error deserves the same response, and retrying the wrong error is one of the fastest ways to turn a small failure into a large one. The rollout rule from the [LLMOps.si deployment article](https://www.llmops.si/articles/llm-deployment-ci-cd-staging-rollback/) is the clearest statement of this: a fallback chain retries only 429, 500, 502, 503 and 504, because a 400 is your bug, not a retry. A 400 means the request itself was malformed, and sending the same malformed request to a second provider will fail the same way while hiding the bug from you; a 429 means you are being rate-limited and should back off before trying again; a 500-series error means the provider is struggling and a different provider, or the same provider after a pause, may succeed. The same logic extends beyond status codes: an authentication failure means your credentials are wrong and no amount of retrying will fix them, a content-policy refusal means the request was blocked for a reason that a weaker model will not overturn, and a timeout means the call may or may not have completed, so retrying a call with side effects needs an [idempotency key](https://www.llmops.si/articles/llm-deployment-ci-cd-staging-rollback/) — a client-generated identifier that lets the server recognise a repeat — or it needs to be treated as unsafe to repeat at all.

The second kind of signal is latency, which is a failure even when nothing returns an error. An agent that takes ninety seconds to answer a question a user expected in five has failed that user, and if it holds a model connection open for those ninety seconds it is also consuming capacity that other requests need. This is where the serving alert thresholds from the [LLM course](https://github.com/mlabonne/llm-course) deployment section earn their place: alert when the 95th percentile latency rises above 2 seconds, when the error rate rises above 5%, or when memory usage rises above 90%. Those numbers are alert thresholds for a serving deployment, not universal laws, and your own thresholds will depend on your product — an asynchronous research agent can tolerate minutes that a chat agent cannot — but the principle is portable: pick the numbers in advance, write them down, alert on them, and let the alert, not a user's complaint, be the first sign that something is degrading. Latency also matters inside the fallback ladder itself, because a fallback that takes ten times longer than the primary is not a rescue; it is a queue forming in slow motion, and the circuit breaker in the next section exists precisely to stop you paying that cost on every request.

The third kind of signal is cost, which fails silently in a way that errors and latency do not. A model call that succeeds is indistinguishable, in the moment, from a model call that succeeded at ten times the intended price, and an agent loop that retries a failing step is a machine for turning a small error into a large bill. Cost detection therefore has to be measured per run, per task and per user, in tokens and in money, as the run proceeds — not reconstructed from an invoice at the end of the month. The [Claude Cookbook cost optimisation notebook](https://platform.claude.com/cookbook/cost-optimization-cost-optimization) makes this concrete by insisting on a measured baseline first: get the task working on a capable model, build an evaluation, measure the cost per task, and only then start trading cost against quality. That order matters for degradation too, because a cost kill-switch that trips at an arbitrary number is guessing, while one that trips at a number derived from your measured cost per task is enforcing a budget you actually understand. The companion [latency optimisation notebook](https://platform.claude.com/cookbook/latency-optimization-latency-optimization) adds the other half of the measurement discipline, defining latency as time to first token, time to last token and output tokens per second, so that a degraded path can be compared against the primary on the same terms instead of on vibes.

The fourth kind of signal is quality, which is the hardest to detect and the most important to get right, because a degraded agent that answers wrongly is worse than one that refuses. Quality detection means checking the output, not just the call: did the retrieval step return anything, did the tool return a result in the shape the agent expected, does the answer cite a source that actually exists, does the fallback model's answer pass the same checks the primary model's answer had to pass? This is where the previous chapter's trajectory evaluations meet this chapter's fallbacks, and the connection is worth stating plainly: if you cannot grade an answer, you cannot trust a fallback to produce one, and the fallback chain should therefore run the same evaluation set as the primary path, with its own prompt variant if it needs one, as the LLMOps.si article insists. A fallback that has never been graded is an untested change to your product, deployed automatically, at the worst possible moment.

## Circuit breakers: stop calling what is already broken

Once you can detect failure, the next question is what to do with a dependency that keeps failing, and the answer is the circuit breaker, a pattern from *Release It!*, described in [this write-up on the circuit breaker](https://martinfowler.com/bliki/CircuitBreaker.html) as wrapping a protected call in an object that monitors for failures and, once failures reach a threshold, trips so that all further calls return with an error without the protected call being made at all. The electrical metaphor is exact: just as a physical breaker cuts the circuit before a fault can start a fire, a software breaker cuts the calls before a failing dependency can drag the rest of the system down with it, whether by exhausting threads, filling queues, or burning money on requests that cannot succeed.

The breaker is a small state machine with three states, and understanding the transitions between them is the whole pattern. In the **closed** state, which is normal operation, calls pass through and failures are counted; a success resets the count, and a timeout counts as a failure, because a call that never returns is a failure even though no error was raised. When the failure count — or, in a more sophisticated breaker, the failure rate over a rolling window — crosses a threshold, the breaker moves to the **open** state, where calls fail immediately without touching the dependency at all. That fast failure is the point: it protects the struggling service from further load, it protects your agent from waiting on timeouts it has already learned are coming, and it frees the agent to do something else, such as stepping down the fallback ladder, instead of standing in a queue for a service that is not there. After a reset timeout has elapsed, the breaker moves to the **half-open** state, where a limited number of trial calls are allowed through to test whether the dependency has recovered; if a trial succeeds, the breaker closes and normal service resumes, and if it fails, the breaker reopens and the timeout restarts, often with the timeout growing longer each time so that a persistently sick dependency is probed less and less often.

Three design decisions inside that simple machine deserve a principal engineer's attention, because they are where real breakers differ from textbook ones. The first is what counts as a failure, and the warning in the circuit-breaker write-up applies directly: not all errors should trip the circuit, since some reflect normal failures that are part of regular logic. A 400 from a tool, a content-policy refusal, or a validation error from your own code are not signs that the dependency is sick, and counting them will trip your breaker on a healthy service; a 500, a 503, a connection failure and a timeout are. The second decision is whether to trip on a count or on a rate, and the answer depends on traffic: a count of five failures trips quickly on a busy service but may never trip on a quiet one, while a rate — the write-up suggests tripping at a 50% failure rate — adapts to volume but needs enough traffic to be meaningful, so a low-traffic dependency needs a minimum call volume before the rate is trusted. The third decision is the half-open probe policy, because a single successful trial call is weak evidence that a service has recovered, and a flood of trial calls from many breaker instances at once is a thundering herd that can knock the service over again just as it recovers; limiting probes to one at a time, requiring several consecutive successes before closing, and adding jitter to the reset timeout are all ways of making recovery gentle rather than violent.

There is also a scope decision that is easy to get wrong, which is that a breaker protects one dependency, not your whole agent. Each model provider, each tool, each external service gets its own breaker, with its own thresholds, because a search service that fails five times in a minute and a payment service that fails five times in a minute are different events with different consequences. And a breaker is not a fallback by itself: it is the mechanism that *decides* a dependency is unavailable quickly, so that the fallback logic — the subject of the next three sections — can run instead of waiting. A breaker without a fallback leaves the user with a fast error, which is better than a slow one but still an error; a fallback without a breaker leaves the agent paying a timeout on every request before it even starts falling back, which is a slow error wearing a fallback's clothes.

## Model cascading: stepping down in capability, not in reliability

With the breaker deciding quickly that the primary model is unavailable, the agent needs somewhere to go, and the most useful somewhere is usually a cheaper, smaller model — but only if that step down has been planned as a cascade rather than improvised as a panic. A model cascade is an ordered list of models, from the most capable to the least, where each step down trades capability for availability or cost, and where the order is chosen before the outage, not during it. The shape is familiar from the [Microsoft AI Agents for Beginners](https://microsoft.github.io/ai-agents-for-beginners/10-ai-agents-production/) production lesson, which suggests switching to a second large language model provider as a backup when the first is down, and routing simple queries to smaller models while reserving expensive large models for complex reasoning; the cascade in this chapter takes both ideas and makes them explicit, ordered and testable.

The ordering question is where the judgement lives. The naive order is by price — frontier model first, then the cheapest model that will answer — but price order and capability order are not the same thing, and the right order depends on the task. For a summarisation task, a small model may be nearly as good as a frontier one, so stepping down costs little; for a multi-step planning task, a small model may fail in ways that look like success, producing a confident plan with a missing step, and stepping down costs everything. The cascade therefore has to be ordered per task type, not per agent, and each rung needs its own evidence: run the same evaluation set against every model in the chain, record the pass rate and the cost per task for each, and write down the quality you lose at each step, so that the decision to step down is a decision with a known price rather than a hope. The Claude Cookbook's cost optimisation discipline is the method for this — measure the baseline, then sweep the cheaper configurations and keep the Pareto frontier, the set of configurations where no cheaper option is as good and no better option is as cheap — and the cascade is simply that frontier written down as an ordered list, with the understanding that an outage moves you along it.

There is a subtlety in the cascade that catches experienced teams, which is that different models fail differently, and a cascade that only handles errors will miss the failures that matter most. A cheaper model that returns a malformed tool call, an empty answer, or an answer that fails your output validation has failed just as surely as a model that returned a 503, and the cascade should treat it that way, stepping down again or refusing rather than passing the bad output on. Conversely, a cheaper model that succeeds slowly may be worse than a cached answer that succeeds instantly, which is why the cascade in this chapter does not end at the cheapest model. The full ladder, from the top, runs: the frontier model; a cheaper model from the same provider, which shares the provider's outage risk but not its price; a model from a different provider, which shares neither; a cached answer, which costs nothing and answers instantly but may be stale; and finally a refusal, which costs nothing, answers honestly, and preserves trust. The order of the second and third rungs is a judgement call — same-provider-cheap is faster to reach and shares your existing authentication and prompt tuning, while different-provider is genuinely independent and survives a provider-wide outage — and the right answer for your system depends on whether your most likely failure is a model being rate-limited or a provider being down. Either way, the order must be written down, tested, and logged, because a cascade whose order nobody can state is not a design; it is a pile of `try` blocks.

That last rung, the refusal, deserves emphasis, because it is the rung most teams forget to build and the one that matters most. A refusal is not a failure of the agent; it is the agent behaving correctly when it cannot do the job well. It should say what it could not do, why it could not do it, and what the user can do next — retry later, ask a narrower question, contact a human — and it should be logged as a refusal, not as a success, so that a day full of refusals shows up as an incident rather than as a day of suspiciously cheap, suspiciously fast answers.

## Cost-aware routing and cascades: choosing before you fail

The cascade above steps down *after* something has failed, and that timing is its limit as a cost tool, because a cascade that only ever moves on failure still pays frontier prices for every request that succeeds. Cost-aware routing is the decision that happens before the task starts, and the distinction between the two is worth keeping crisp, because conflating them is how a team builds a fallback ladder, watches it work beautifully in a drill, and then wonders why the bill never falls. Routing asks, for this request, which is the cheapest model that can do this job well; cascading asks, now that the chosen model has failed, which model tries next. A request can be routed cheaply and still cascade if the routed model fails, and a request routed to the frontier model can still cascade down from there, so the two mechanisms compose rather than compete — routing saves money on the healthy path, cascading saves the request on the failing path, and the kill-switch in the next section is what stops either of them from running away.

The routing decision itself has a shape that is worth naming, because it keeps three choices that are usually tangled apart. The first choice is *when* to route: per request, which is the whole task sent to one model; per step, which is each step of an agent loop routed on its own (the subject of a paragraph below); or per retry, which is re-routing after a failure rather than simply stepping down the fixed cascade, for example sending a retry to a different provider instead of a cheaper model from the same one. The second choice is *what signal* to route on: how complex the task looks, what has happened in this conversation so far, and whether the step needs tool use at all, since a step that only formats an answer that already exists needs far less capability than a step that must decide which tool to call next. The third choice is *how much compute* to spend: the size of the model, and the thinking budget it is given, since a small model allowed a long reasoning budget can sometimes out-perform a large model given almost none, and a frontier model given a generous budget on a trivial task is the most expensive way to produce a two-sentence summary. When a routing design goes wrong, it is usually because one of those three choices was made implicitly — the router routes per request because nobody asked about per step, or it routes on task type alone because nobody measured complexity — so writing the three down, with the choice made for each, is the design document.

Once the shape is clear, the arithmetic is simple, and it is worth writing out because it is the number a routing decision is judged by. The expected cost of a routing policy is the sum over models of the probability of routing to that model multiplied by the cost of one call on it, or in symbols, expected cost = Σ P(route to model) × cost per call on that model, and the quality constraint sits alongside it rather than inside it: the cheapest routing only counts if every model it routes to clears the quality bar for the task types it serves, measured on your own evaluation set before the router ships, exactly as the Claude Cookbook discipline in the detection section requires — baseline first, evaluation second, cost trading third. A worked example makes the shape concrete, using illustrative prices rather than real vendor prices: suppose a call costs 6 cents on the frontier model, 1.2 cents on a mid-size model and 0.2 cents on a small model, and suppose traffic splits 60% easy, 30% medium and 10% hard, with the easy share routed to the small model, the medium share to the mid-size model and the hard share kept on the frontier model. Then the expected cost per task is 0.6 × 0.2 + 0.3 × 1.2 + 0.1 × 6.0 = 1.08 cents, against 6 cents for sending everything to the frontier model, which is 82% cheaper — $10.80 a day against $60 for a thousand tasks a day — *provided* each routed share clears the quality bar for its task type, and the moment one of them does not, the saving is not a saving at all, it is a quality cut wearing a routing policy's clothes. That proviso is the whole discipline, and it is why routing without an evaluation set is just a cheaper way to be wrong.

There are two broad ways to build the router that makes that decision, and they fail in different ways. Predictive routing uses a small classifier — the router itself — to predict which model can handle this particular task, trained on labelled pairs of task and cheapest model that passed, so that two summarisation tasks can go to different models because one is a two-sentence policy summary and the other is a forty-page contract with ambiguous clauses. Non-predictive routing uses fixed rules instead: heuristics keyed on task type, a lookup table that sends summarisation to the small model and planning to the frontier model, or an A/B fallback that tries the cheap model first and steps up only if its answer fails a check. The fixed version is easier to build, easier to explain and easier to debug, and for a stable workload with clean task types it is often enough; its failure mode is the task that looks like its type and is not, the summarisation that is really a reasoning task in disguise, which the fixed rule sends cheap and gets wrong. The predictive version handles that task, because it looks at the individual prompt rather than only its label, but it has a failure mode of its own: the router can be wrong, and a router that is wrong systematically — that has learned, from biased training data, that a certain kind of question is easy when it is not — will misroute the same tasks every day until somebody notices. That is why the code in this chapter implements the predictive router as a small rule-based complexity scorer and labels it plainly as a stand-in for a learned router: the scorer is the shape of the decision, and the learned classifier is what replaces it once you have the labelled data to train it, not before.

Agent-step routing is the place where that distinction pays for itself, because an agent run is not one task but a sequence of steps with wildly different needs, and routing the whole run to one model wastes money in one direction and risks quality in the other. A research run might plan with the frontier model, extract facts with a mid-size model, and format the result with the small model, and the right routing decision for the formatting step has nothing to do with the right decision for the planning step — the plan needs judgement, the formatting step needs only to follow a template. Routing per step means each step carries its own signal, its own complexity estimate and its own quality bar, and the cost of the run is the sum of the routed steps rather than the frontier price multiplied by the number of steps. The risk to watch is that a step routed too cheaply can poison the steps after it: a bad plan from a small model does not stay a bad plan, it becomes a wasted extraction and a polished formatting of the wrong answer, so the steps that shape the rest of the run — planning, tool selection, the decision about what to retrieve — are the ones where routing up is cheapest insurance, and the steps that only polish what already exists are the ones where routing down is nearly free.

None of that is trustworthy without routing evals, because a router is a model of its own, and a model that is never evaluated is a hope. The evaluation starts with a golden set: a fixed collection of tasks with a known minimum quality for each, run against every router version, so that a new router is judged on the same tasks as the old one. The replay matrix is that comparison written down side by side — router version against router version, pass rate and average cost per task for each — and it is what catches the version that is cheaper only because it fails a task the old version passed. Shadow scoring is the step before promotion: the new router's choice is logged on live traffic but not enforced, so the user keeps getting the old router's answer while you collect the evidence about where the two disagree, and where they disagree and the old answer was no better, the new router was right. A canary rollout is the step after that: the new router decides for a small share of traffic, with its pass rate, cost and fallback rate watched against the control share, and the share grows only while the numbers hold. The interview angle follows directly: a strong answer does not say "I would route easy tasks to a small model", it writes the expected-cost formula, states the quality constraint that makes the saving real, names the signal the router uses and how it would be wrong, and describes the golden set, the replay matrix and the shadow period that would prove the router before it decided anything for a real user — and then, as the explain-back, defends the routing decision to a reviewer who only sees the cost saving, by showing the quality numbers the saving was conditioned on, because a saving without its quality condition is not a result, it is a rumour.

## Cost kill-switches: budgets that actually stop the run

A cascade controls which model answers, but it does not control how many times the agent asks, and an agent loop that retries, replans and spawns sub-agents can turn a single user request into hundreds of model calls. That is why the cost control in this chapter is a kill-switch, not a budget report: a mechanism that stops a run in mid-flight when the money is gone, rather than one that notices afterwards. The distinction is the difference between a speedometer and a brake, and only the brake prevents the crash.

A kill-switch needs three pieces, and each one is simple on its own. The first is a meter, which counts tokens and converts them to money as the run proceeds, using the provider's usage block on every response — input tokens, output tokens and cached tokens, priced from a table you control and can update when prices change, exactly as the Claude Cookbook's cost notebook does with its `usage_cost()` function. The meter must count the whole run, including retries, fallback calls and sub-agent calls, because a budget that only counts the primary model's calls is a budget with a hole in it exactly where the expensive behaviour lives. The second piece is a set of budgets, and there should be more than one: a per-run budget that stops a single runaway task, a per-user or per-team budget that stops one user from consuming the whole day's allowance, and a global budget that stops everything when the organisation's limit is reached. Each budget needs two thresholds, a warning that pages a human and a hard stop that halts the run, because a hard stop with no warning is a surprise, and a warning with no hard stop is a suggestion. The third piece is the halt itself, which must be safe: the agent stops making model calls, finishes any in-flight tool call or rolls it back, writes down what it had completed and what it had not, and tells the user plainly that it stopped because of cost, not because of an error in their request. A halt that leaves a half-written file, a half-sent message or a half-completed transaction is worse than the spend it prevented.

Two design points make kill-switches work in practice rather than on paper. The first is that the budget must be checked before each expensive step, not just after it, because a single model call can itself be enormous — a long context window, a large output — and checking only between calls lets one call blow the budget by an order of magnitude. The practical rule is to estimate the cost of the next step from its input size and a cap on its output, and to refuse the step if the estimate alone would breach the budget. The second point is that the kill-switch must be testable without spending real money, which means the meter and the budget must be separable from the provider: inject a fake price table and a fake model that returns token counts, and run the loop until it trips, as the exercises do. A kill-switch that has only ever been tested by reading its code is a kill-switch you will discover does not work on the day it matters.

There is a temptation, when building kill-switches, to set the budget from the price list rather than from the product, and it should be resisted. The right budget comes from the measured cost per task: if your evaluation says a task costs a certain amount on the primary model and a smaller amount on the fallback, then a per-run budget of a small multiple of the primary cost gives the agent room to retry and fall back while still catching a loop that has gone wrong. A budget set without that measurement is either so loose that it never trips or so tight that it trips on legitimate work, and both failures teach the team to ignore it, which is the worst outcome of all.

## Offline queuing: doing the work later, in order, exactly once

Everything so far has assumed the agent can reach *something* — a cheaper model, a cache, a human. Offline queuing covers the case where it cannot reach anything at all: the network is down, every provider is unreachable, or the agent is running on a device with no connectivity. The right response in that case is not to fail every request, and not to pretend the work happened; it is to accept the work, store it durably, and replay it when connectivity returns. That sounds simple, and the durable part is where it becomes engineering.

A queue that lives only in memory is not a queue; it is a hope that the process will not restart, and processes restart at exactly the wrong moments. So the queue must be written to disk — a file, a SQLite database, any store that survives a crash — before the agent tells the user the task is accepted, and the write must be atomic, so that a crash halfway through leaves either the old state or the new state, never a half-written entry. Each queued task needs an identifier, a payload, a timestamp, and a count of how many times it has been attempted, because replay without those fields is guesswork. It also needs an idempotency key, the same idea as in the retry discussion: when the task is replayed, the downstream system must be able to recognise that it has seen this task before, so that a replay after a crash does not execute a side effect twice. A task that sends a message, charges a card or writes a file must be safe to replay, or it must not be queued at all — and deciding which tasks are safe to queue is a product decision, not an implementation detail, because queuing an unsafe task is how a user ends up charged twice for a message they sent once.

Replay itself has rules, and they follow from the same honesty that governs the rest of this chapter. Tasks replay in the order they were accepted, because order is part of what the user meant: a message that says "cancel the order" must not replay after a message that says "confirm the order" if it was sent first. A task that fails on replay is retried with backoff, and after a bounded number of attempts it moves to a dead-letter store — a separate place for tasks that could not be completed — rather than blocking the queue behind it forever, because one poisoned task should not hold every task behind it hostage. And the user must be told what happened: which tasks were queued, which were replayed successfully, and which need their attention. An agent that silently drops queued work has not degraded gracefully; it has lost the user's work and hidden the loss.

The queue also needs a bound, because an unbounded queue is a different kind of failure. If connectivity is down for a day, the queue will grow, and a queue that grows without limit will exhaust disk, exhaust memory, or replay for hours after connectivity returns, delivering answers to questions nobody is asking any more. So the queue has a maximum size and a maximum age: when it is full, new tasks are refused with a clear message rather than accepted and lost, and when a task is older than its useful life — a price check from yesterday, a "what is the weather now" question from this morning — it expires rather than replaying as a stale answer. Those bounds are product decisions too, and they should be written down next to the budgets, because they are the same kind of decision: how much failure are we willing to absorb before we say no?

## API-to-browser fallbacks: the same task, through a different door

There is one more rung on the ladder that deserves its own section, because it crosses a boundary most agents treat as fixed: when the structured Application Programming Interface (API) a tool normally uses is down, the same task can sometimes be done through the browser instead, by driving the website the way a person would. A flight search whose API returns errors can be run against the airline's website; a listing lookup whose API is rate-limited can be read from the search results page; a form submission whose endpoint is down can be completed in the browser, if the site itself is still up. This is the fallback that [Microsoft's Lesson 15](https://microsoft.github.io/ai-agents-for-beginners/15-browser-use/) teaches as a primary technique — a [Computer Use Agent](https://microsoft.github.io/ai-agents-for-beginners/15-browser-use/) that combines [Browser-Use](https://microsoft.github.io/ai-agents-for-beginners/15-browser-use/) for AI-driven navigation with [Playwright](https://microsoft.github.io/ai-agents-for-beginners/15-browser-use/) and the [Chrome DevTools Protocol](https://microsoft.github.io/ai-agents-for-beginners/15-browser-use/) for browser control — and this chapter treats it as a fallback, which changes how it must be built.

The change is in the contract. An API returns structured data with a documented schema, an error code and a predictable latency; a browser returns a page that can change layout without notice, show a pop-up, ask for a CAPTCHA, or load slowly enough that the agent times out halfway through a multi-step flow. So a browser fallback must be narrower than the API path it replaces: it should handle the common case — read a price, find a listing, submit a simple form — and refuse the cases it cannot verify, rather than guessing at a page it cannot parse. It must extract its result into the same typed structure the API path returns, using a schema such as [Pydantic](https://microsoft.github.io/ai-agents-for-beginners/15-browser-use/), and validate it the same way, so that downstream code cannot tell which path produced the answer and does not need to. And it must be slower, more expensive and less reliable by design, which means it sits low on the ladder: below the cheaper model, below the cache, and only above the refusal, because a browser fallback that runs on every request would be a worse product than the API it replaces.

There are also boundaries that no fallback may cross. A browser fallback must not bypass authentication, must not defeat a CAPTCHA or a bot check, and must not do through the user interface what the API refused to do for a policy reason — if the API refused because the user is not authorised, the browser must refuse too. Those are not technical limits; they are the difference between a resilient agent and one that evades the controls placed on it, and the distinction belongs in the design document, not in a comment buried in the code. The browser fallback is also the most expensive rung to maintain, because websites change, and a fallback that is never exercised will be broken when it is needed; the exercise for this section therefore runs the fallback against a local page the student controls, so that the *mechanism* — detect the API failure, drive the browser, extract typed data, validate it — can be practised without depending on a live site that may change tomorrow.

## Semantic-cache hardening: a cache that lies is worse than no cache

The caching number in the next section — up to 68.8% fewer API calls in the GPT Semantic Cache paper, at a cosine similarity threshold of 0.8 — is the reason semantic caching is tempting, and it is also the reason it needs hardening, because a cache hit is an answer served without calling a model, which means it is also an answer served without the model's judgement, without its grounding, and without the chance to notice that the world has changed since the answer was written. The existing chapter treats caching correctly, as cost optimisation that can serve as a rung on the fallback ladder, and this section is about making that rung safe to stand on, because a cache that returns the wrong answer quickly is not a fallback, it is a fast way to be wrong at scale.

Threshold tuning is where the hardening starts, and the first thing to understand is that 0.8 is a starting point, not a universal constant. It is the optimum in the paper's sweep from 0.6 to 0.9 on the paper's traffic, which means it is the best threshold for their queries, their embedding model and their tolerance for error — and your traffic is none of those things. A support desk whose questions repeat almost verbatim can afford a lower threshold, because near-duplicates are genuinely the same question; a desk whose questions share vocabulary but ask different things — "how do I cancel my order" against "how do I cancel my subscription" — needs a higher one, because similarity there is a trap. Re-tuning is therefore a measurement exercise on your own traffic: collect pairs of queries, label whether the cached answer to the first would have been correct for the second, sweep the threshold across the range, and pick the point where the cost of a false hit — serving a wrong answer — balances against the cost of a miss — paying for a fresh call. That balance is a product decision, not a property of the embedding model, and it changes as your traffic changes, so the threshold is a number you revisit, with the sweep re-run, rather than a constant you set once and forget.

The failure taxonomy is what that sweep is protecting against, and it is worth naming the four failures separately, because each one needs a different defence. A false hit returns the wrong answer: the new query was similar enough to pass the threshold but meant something different, and the user receives a confident answer to a question they did not ask. A stale hit returns an answer that was right when it was cached and is wrong now: the policy changed, the price changed, the feature was removed, and the cache, which has no way of knowing, keeps serving the old truth. Cross-tenant leakage returns the right answer to the wrong person: a cached answer written from one customer's data, or in one customer's context, is served to another customer, which is a privacy failure as well as a correctness failure. And a poisoned cache entry returns an answer that should never have been stored at all: a hallucinated or manipulated answer got written into the cache, perhaps during an outage when the fallback model was answering badly, and now it is served with the authority of a cached result, repeated until somebody notices. Each of these is worse than a cache miss, because a miss costs money and a hit that is wrong costs trust, and the defences below are organised around making each one harder to happen and easier to notice.

Scoped keys are the defence against leakage and a large part of the defence against staleness, and the rule is simple to state: the cache key must contain everything that could change the right answer. That means the tenant, so that one customer's answers can never be served to another; the version, meaning the version of the policy, the price list, the document set or the model prompt that produced the answer, so that a policy change invalidates the old entries instead of leaving them to be served; and the task type, so that a summarisation answer is never served as if it were an extraction answer. A key that is only the query text is a key that assumes the same words always mean the same thing for the same person under the same rules, and that assumption is false in exactly the cases that matter. Scoping the key is cheap — it is a string you build when you write the entry — and the cost of not scoping it is the leakage and staleness failures above, discovered by a customer rather than by you.

Verifier models are the defence against false hits, and the idea is to spend a little to save a lot: before serving a cached answer, a cheap model checks whether the cached answer still fits the new query. The check can be as simple as asking the small model whether the cached answer answers the new question, or comparing the key facts in the cached answer against the new query's requirements, and it costs a fraction of a full frontier call, which is the point — a cache that saves a frontier call but spends a small-model call to verify it is still far cheaper than the frontier call, and far safer than serving the cached answer unchecked. The verifier does not need to be perfect to be useful; it needs to catch the cases similarity misses, which are precisely the near-duplicates with a different meaning, and it needs its own threshold, tuned the same way as the cache threshold, because a verifier that approves everything is decoration and a verifier that rejects everything is a cache that never hits.

Finally, there are the cache-busting anti-patterns, the things not to do, and they are worth listing plainly because each one looks like a shortcut in the moment. Do not cache without versioning, because a policy change will then leave you serving the old policy with no way to tell which entries are stale. Do not cache personalised answers under a shared key, because that is cross-tenant leakage built in on purpose rather than by accident. Do not trust similarity alone for high-stakes answers — anything touching money, a hard-to-reverse action, or a safety decision — because a similarity score is a measure of how alike two questions look, not of whether they have the same answer, and the cost of being wrong there is not the price of a model call. And do not let the cache fill during an outage without marking what went in: answers written while the fallback model was degraded are the poisoned entries of tomorrow, so entries written in degraded mode should carry a flag, a short expiry, or both, and a cache that was filled by a struggling model should be treated as suspect until it is re-verified. The principal-level angle is the same as for routing: a strong answer names the threshold as a tuned number from its own traffic, not a constant borrowed from a paper; walks through the failure taxonomy and the defence for each failure; and explains, as the explain-back, why a cache hit rate is a cost number and not a resilience number, because the day the cache is full of stale answers is the day a wonderful hit rate and a failing product are the same day.

## The numbers that matter

A chapter about degradation should be honest about which of its numbers are measured and which are chosen, so here they are, together, with their sources. The serving thresholds come from the [LLM course](https://github.com/mlabonne/llm-course) deployment section: alert when the 95th percentile latency exceeds 2 seconds, when the error rate exceeds 5%, or when memory usage exceeds 90%. The retry rule comes from the [LLMOps.si deployment article](https://www.llmops.si/articles/llm-deployment-ci-cd-staging-rollback/): retry and fall back only on 429, 500, 502, 503 and 504, because a 400 is your bug. The serving efficiency number comes from the [PagedAttention paper](https://arxiv.org/abs/2309.06180), presented at the Symposium on Operating Systems Principles (SOSP) in 2023: the [vLLM](https://arxiv.org/abs/2309.06180) system improves throughput by 2 to 4 times at the same latency compared with FasterTransformer and Orca, with the gains larger for longer sequences, larger models and more complex decoding — which matters here because a fallback that runs on your own serving stack inherits that efficiency, while a fallback that runs against a struggling provider does not. And the caching number comes from the [GPT Semantic Cache paper](https://arxiv.org/abs/2411.05276): semantic caching reduces API calls by up to 68.8%, with cache hit rates from 61.6% to 68.8% across query categories, and a cosine similarity threshold of 0.8 is optimal in the paper's sweep from 0.6 to 0.9. That last figure needs its warning repeated, because it is easy to misread: the 68.8% figure is from that arXiv paper, not from the [GPTCache](https://arxiv.org/abs/2411.05276) library, and the two must not be conflated, just as caching itself must not be confused with a fallback. Caching is cost optimisation — it avoids a call you did not need to make — while a fallback is what you do when the call you needed to make has failed; a cache can *serve* as a rung on the fallback ladder, as this chapter uses it, but a cache hit rate is not a measure of resilience, and a system with a wonderful cache and no fallback still fails completely the first time it meets a question it has never seen during an outage.

Everything else in this chapter that looks like a number — a breaker that trips after five failures, a reset timeout of thirty seconds, a queue that holds a thousand tasks — is a chosen default for the exercises, not a measured result, and the code says so wherever it appears. Your production numbers will come from your own traffic, your own evaluation set and your own cost per task, and the skill this chapter teaches is how to derive them, not what they are.

## Putting it together: the degraded agent

The pieces above compose into a single agent, and it is worth walking through one request end to end to see how they fit, because the composition is where most designs fail. A request arrives, and the agent first checks its budgets: is there enough remaining budget for this run to attempt the primary path at all, and if not, does it refuse now, cheaply, rather than starting work it cannot finish? It then routes the request — choosing the cheapest model that clears the quality bar for the task, and routing each step of the run on its own where the steps differ — and calls the routed model through a circuit breaker, with a timeout, and the breaker either passes the call through or fails fast because the provider is already known to be down. If the call succeeds, the agent validates the output and proceeds; if it fails with a retryable status, it retries with backoff and jitter, a bounded number of times, and then steps down the cascade — cheaper model, different provider, cached answer — with the breaker consulted at each step so that a known-dead provider is never tried again. If the model path is exhausted, it tries the tool path: the API first, then the browser fallback if the task is one the browser can do safely, and then the queue if the task can wait. At every step the meter is running, and if the budget is breached the run halts safely and says so. And if every rung is exhausted, the agent refuses, clearly and with a next step, and logs the refusal as a refusal.

Three properties of that walk-through are worth naming, because they are the properties a principal engineer should check in any design review. The first is that every transition is logged with its cause: which rung served the request, why the rung above it failed, and what it cost. The second is that every rung was evaluated before the outage, so the quality at each step is known rather than hoped for. And the third is that the whole ladder is exercised regularly, not just in an incident: a scheduled drill that takes the primary model offline in a staging environment and watches the agent step down, recover and step back up is the only evidence that the ladder works, and the absence of such a drill is evidence that it does not. The code in this chapter is built to make that drill easy — every dependency is injected, every failure can be simulated, and the demo runs the whole ladder against mock providers in seconds — because a fallback you cannot drill is a fallback you cannot trust.

## The principal-level interview angle

In an interview, this topic separates engineers who have operated a system from engineers who have only read about one, and the separation shows in how they answer the question that sits behind all of it: *when do you degrade, and when do you refuse?* A weak answer lists mechanisms — "I would add retries and a fallback model" — without saying when each one fires, what it costs, or how you would know it worked. A strong answer starts from the user and the harm: it names the failure modes, distinguishes a retryable error from a bug using the status-code rule, explains why a circuit breaker exists to stop paying timeouts rather than to handle errors, and walks through a cascade with its quality and cost at each rung, including the rung where the honest answer is a refusal. It also names the failure modes of the mechanisms themselves: a breaker that trips on validation errors and takes down a healthy service, a cascade that silently serves worse answers for hours because nobody alerted on fallback rate, a kill-switch that halts a legitimate long task because its budget was set from a price list instead of a measured cost per task, a queue that replays a payment twice because nobody added an idempotency key, a browser fallback that bypasses a control the API was enforcing.

The second interview question that matters is *how do you prove the fallback path works before you need it?*, and the answer is a drill, not a diagram. Describe the staging exercise: take the primary provider offline, watch the breaker trip, watch the cascade step down, watch the cost tally move, watch the queue accept and replay, and then restore the provider and watch the breaker close. Name the metrics you would watch during the drill — fallback rate, time to recover, cost per task at each rung, refusal rate — and name the alerts you would set on them in production, using the serving thresholds from this chapter as a starting point. And name what you would *not* do: you would not test a fallback for the first time during an incident, you would not let a fallback run ungraded, and you would not let a degraded mode become the permanent mode because nobody noticed the primary had been down for six hours. That last point is the one that most often impresses, because it shows the engineer understands that the most dangerous failure is not the outage but the silent, indefinite degradation that follows it.
