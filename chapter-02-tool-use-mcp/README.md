# Chapter 2 — Tool Use & MCP

## The idea in plain words

An agent that cannot act is a chatbot with ambitions, and the moment it starts acting it needs tools, which is where the trouble starts, because every tool is a new integration and every integration is a new way for the system to break. Before the Model Context Protocol (MCP) existed, connecting a language model to `N` tools across `M` applications meant building `N × M` bespoke integrations, each with its own calling convention, its own error handling and its own idea of what a tool's arguments should look like, and every one of them had to be rebuilt when the model changed. The Model Context Protocol, which Anthropic introduced on 25 November 2024 and donated to the Agentic AI Foundation on 9 December 2025, replaces that tangle with a single contract, and the protocol's own documentation reaches for the most honest analogy available, comparing it to a USB-C port: one connector shape that any compliant application and any compliant server can plug into, so a capability built once as an MCP server works in any compliant client. The idea is deliberately boring, and that is the point, because a tool interface should be the most boring part of your system, and the excitement should live in what the agent does with it, not in how the two sides manage to talk at all.

The shape of the idea is a small cast with fixed jobs. A host is the artificial-intelligence application the user actually runs, a client is the connector inside that host, and a server is the service that provides the capabilities, and the rule that keeps the whole arrangement honest is that each client talks to exactly one server, while a host may run many clients. The server offers three kinds of primitive, and the distinction between them is the first design decision this chapter asks you to internalise, because the protocol assigns each primitive a different controller: tools are model-controlled, which means the model decides when to call them; resources are application-controlled, which means the host decides what context to attach; and prompts are user-controlled, which means the user picks a reusable workflow template. That division is not decoration, it is the security model in miniature, since a tool is arbitrary code execution wearing a friendly name, while a resource is data the application chose to share, and confusing the two is how an agent ends up treating a document it was asked to read as an instruction it must obey.

## The mechanism, from the wire up

Everything in the Model Context Protocol is a JSON-RPC 2.0 message, where JSON-RPC (JavaScript Object Notation Remote Procedure Call) 2.0 is the lightweight, transport-agnostic remote procedure call protocol defined by the JSON-RPC Working Group, and understanding that sentence is understanding most of the protocol, because once you can read a JSON-RPC request and write a JSON-RPC response, there is very little left that a framework can hide from you. A request is a single JSON (JavaScript Object Notation) object with four fields: `"jsonrpc"` must be exactly `"2.0"`, `"method"` names the procedure, `"params"` carries its arguments, and `"id"` matches the response to the request, while a request without an `"id"` is a notification, which by the rules of JSON-RPC 2.0 must never be answered, and answering one would corrupt the framing of everything after it. A response carries the same `"id"` and either a `"result"` or an `"error"`, and the error is a small object with a numeric code and a message, where the codes are standardised: `-32700` for a parse error, `-32600` for an invalid request, `-32601` for a method not found, `-32602` for invalid parameters, and `-32603` for an internal error, with the range from `-32000` to `-32099` reserved for errors the server defines itself. Those five codes and that one reserved range are the entire error vocabulary your server needs, and the discipline of the chapter is to use them precisely, so that a client can tell a malformed call from a missing method from a refusal without parsing your prose.

The transport is a separate layer from the messages, and the two transports the specification defines are standard input/output (stdio) for a server running as a local subprocess, where messages are newline-delimited JSON on the pipes, and Streamable HTTP (Hypertext Transfer Protocol) for a remote server, where each call is a single HTTP POST, while the older HTTP plus Server-Sent Events (SSE) transport is deprecated and should not be chosen for new work. The local case is the one this chapter builds first, because it is the easiest to observe: the host spawns the server, writes one JSON object per line to its standard input, reads one JSON object per line back from its standard output, and keeps all logging on standard error, since standard output is the wire and a single stray log line there is a parse error for the client. That separation is not a nicety, it is a correctness property, and it is the first thing to check when a server that works by hand fails under a real host.

The current revision of the specification, dated 2026-07-28, then changes the shape of the conversation in a way that matters enormously if you run servers behind a load balancer, which you do if you run them on Amazon Web Services Elastic Container Service (ECS), because it makes the protocol stateless. Earlier revisions opened every session with an `initialize` handshake that negotiated the protocol version and capabilities once, and kept protocol-level sessions behind an `Mcp-Session-Id` header, which meant any given request only made sense in the context of the session it belonged to, and a load balancer had to keep each client pinned to one server instance. Revision 2026-07-28 removes the handshake, the sessions and the header entirely, and instead every request carries its own protocol version and client capabilities in its `_meta` field, under namespaced keys such as `io.modelcontextprotocol/protocolVersion`, so any request can land on any server instance behind a plain round-robin load balancer, and a server must not rely on any earlier request to establish context such as capabilities, protocol version or client identity. Discovery moves with that change into a dedicated call, `server/discover`, which every server must implement and which returns the protocol versions it supports, its capabilities and its identity, and a client may call it first or skip it and send requests directly, handling a version error if one comes back. The code in this chapter implements exactly that revision, and it answers a client that still sends the old `initialize` handshake with a `-32601` error whose message explains the migration, because a removed method deserves a signpost rather than silence, and because an experienced engineer is the person who has to explain to a team why their older client stopped working. Two further consequences of the revision are worth carrying with you: roots, sampling and logging are deprecated, with a minimum twelve-month window before any of them can be removed, so nothing breaks today but nothing new should be built on them; and long-running work moves into an optional Tasks extension, rather than living in the core protocol.

With the wire understood, the conversation itself is short, and its brevity is a feature. The client asks `server/discover` and learns what the server speaks, then asks `tools/list` and learns what the server can do, receiving for each tool a name, a human-readable description and an `inputSchema` written in JSON Schema, which defaults to the 2020-12 dialect when no `$schema` is declared, and then it asks `tools/call` with a tool name and an arguments object, and gets back content, usually text, which flows into the model's context as the tool's result. That is the whole loop, and everything else in the chapter is about making that loop safe, because the loop as described so far trusts everyone: it trusts the model to send well-formed arguments, it trusts the server to check them, and it trusts the tool list to contain only tools the caller should have. None of those trusts survive contact with production, which is why the next two sections exist.

## Schemas that fail closed

A tool's schema is a contract, and like every contract it is only as good as its enforcement, so the question to ask of any tool definition is what happens when the model sends something the contract does not allow. A language model is a fluent generator of almost-right JSON (JavaScript Object Notation), and almost-right is the dangerous case: a missing field, a string where an integer belongs, an invented extra argument, a ticket identifier that does not match the pattern, a status outside the enumeration. The naive server coerces what it can and guesses at the rest, so the string `"5"` quietly becomes the integer `5`, an unknown field is silently ignored, and a call that should have failed instead runs with arguments nobody declared, which is how a support agent ends up resolving the wrong ticket with a note nobody wrote. The strict server does the opposite, and the code in `schemas.py` shows the shape of it: every tool's arguments are a Pydantic model — Pydantic being the Python data-validation library that turns type annotations into runtime checks — configured with `extra="forbid"` and `strict=True`, so a missing required field is rejected, a wrong type is rejected with no silent coercion, an unknown field is rejected, and a value outside its declared range, pattern or enumeration is rejected, and the failure is reported as a JSON-RPC `-32602` error that names the exact field and the exact rule it broke. Crucially, the check happens before the handler runs, so a malformed call has no side effects at all: no partial write, no retry with guessed arguments, nothing to clean up, and that ordering, validate first and execute second, is the fail-closed property the whole section is named for.

Two design choices make the strict schema more than a validation trick. The first is that the schema the model sees and the schema the server enforces are the same object: `schemas.py` generates the advertised `inputSchema` from the Pydantic model with `model_json_schema()`, so the contract the model reasons from cannot drift away from the contract the server enforces, and when you tighten a rule in one place it tightens everywhere at once. The second is that some rules cannot be written one field at a time, and the chapter's example is deliberately chosen to show it: moving a ticket to `resolved` without saying how it was resolved is a write that destroys information, so the `UpdateTicketStatusArgs` model carries a model-level validator that requires a resolution note exactly when the status is `resolved`, which is cross-field validation, and it is the kind of rule that belongs in the schema rather than in the handler, because the handler should never have to defend itself against its own arguments. Anthropic's own guidance on writing tools for agents makes the same point from the model's side, urging tool authors to treat the tool layer as an agent-computer interface, designed and tested as carefully as a user interface, with clear names, precise descriptions and evaluated behaviour, and the strict schema is the enforcement half of that advice: a good description helps the model call the tool correctly, and a strict schema makes an incorrect call impossible to execute.

## Discovery as a boundary, permissions as the enforcement

Discovery feels like a convenience, a way for the client to learn what tools exist, but in a production system it is also a security boundary, and the distinction between those two views is where most tool designs go wrong. If `tools/list` returns every tool the server knows about, then every caller learns about every capability, including the write tools it should never touch, and the model, which reasons from whatever it can see, will sooner or later be talked into calling one of them, whether by a confused user, a misleading document, or an injected instruction in tool output. The scoped server in `scoped_server.py` therefore filters discovery by the caller's role, so a read-only caller asking `tools/list` receives only the read tools and never learns that a write tool exists at all, and an auditor can read that answer for a given role and know exactly what the role is capable of, which is a property worth having when you are asked, as you will be, to prove what a particular agent can and cannot do.

Filtering discovery is the first line of defence, and it must never be the only one, because a caller can always guess a tool name and call it directly, bypassing the list entirely. The call itself is therefore checked a second time, before validation and before execution, and a caller without the required scope receives a JSON-RPC `-32001` error, a server-defined code in the reserved range, whose message names the role, the missing scope and the tool. The ordering matters and is worth stating plainly: permission is checked before argument validation, so an unauthorised caller learns nothing about whether its arguments were well formed, and validation is checked before execution, so a malformed call has no side effects, which gives the server a three-gate shape — authorisation, then validation, then execution — where each gate fails closed and each failure is distinguishable by its error code. Scopes themselves follow the `<resource>:<action>` shape, coarse enough to audit in one glance and fine enough that a read-only caller cannot write: `docs:read`, `tickets:read` and `tickets:write` cover the chapter's whole domain, and a fourth scope, `tickets:admin`, is reserved for a destructive tool that does not exist yet, which is the right way to treat a dangerous capability, as a scope waiting for a design review rather than a tool waiting for a caller.

The last question about permissions is where the caller's identity comes from, and the honest answer is that it must never come from inside the JSON-RPC body, where a caller could simply claim a wider scope. In this chapter the role is fixed when the server process starts, with a `--role` flag, which stands in for the production arrangement: the process runs as a service account with a fixed identity, and the identity arrives with the transport, through an OAuth (Open Authorization) 2.1 token on a remote server or a mutually-authenticated TLS (Transport Layer Security) certificate, and the server maps that authenticated identity to scopes before any tool is listed or called. The specification is explicit that it cannot enforce any of this at the protocol level, and that implementers must build the consent, authorisation and access-control flows themselves, which is why the chapter treats scoping as a server design discipline rather than a protocol feature: the wire gives you the shape of a tool call, and everything about who may make it is yours to build.

## The numbers that matter

A chapter that invents numbers would be worse than one with none, so the figures here are either traceable to a verified source or labelled as measurements from running this chapter's own code. The protocol itself is young: Anthropic introduced it on 25 November 2024, donated it to the Agentic AI Foundation on 9 December 2025, and the current specification revision is dated 28 July 2026, which means the stateless core you have just read about is less than four months old at the time of writing, and any tutorial, course or server that still opens with an `initialize` handshake is teaching a superseded revision, which is a useful filter when you are judging material. The course that supplies this chapter's syllabus shape, DeepLearning.AI's "MCP: Build Rich-Context AI Apps with Anthropic", runs 1 hour 58 minutes at intermediate level and was published on 14 May 2025, so it predates the stateless revision by more than a year, and its FastMCP server build remains a good shape to follow while its protocol details need the update this chapter provides. FastMCP itself is the framework that most Python teams reach for first, and its history explains why: its first version was incorporated into the official MCP Python software development kit (SDK) in 2024, so the framework and the official SDK share a lineage, and the FastMCP equivalent in this chapter's `code/` directory exists so you can see, side by side, how much of the wire the framework absorbs and what it leaves to you, which is the scoping and the validation strictness. The deprecation policy gives you a planning horizon rather than a deadline: a deprecated feature remains part of the specification for a minimum of twelve months, so sampling, roots and logging keep working while you migrate off them, and the right response is a dated migration note, not a panic. Finally, the chapter's own measurement, taken by running `test_server.py` on the machine that built it: a `tools/call` round trip over the local stdio transport takes a median of 0.04 milliseconds across 50 calls against one server process, which tells you that for a local server the protocol overhead is negligible next to anything the tool actually does, and therefore that when a local tool call feels slow, the slowness is in the tool or in the model round trip, not in the wire, while the 18 acceptance checks in that same suite are the evidence that the server behaves as this lesson claims.

## The advanced-level design-review angle

A reviewer who has run agents in production will not ask you to recite the specification; they will ask you what breaks, and the strongest answers in this chapter are all failure stories with a mechanism attached. Ask yourself what happens when the model invents an extra argument, and the answer you want ready is that the call fails with `-32602` before anything executes, because the schema forbids unknown fields and validation precedes execution, and you can point at the exact line where that ordering is enforced. Ask what happens when a compromised or careless server advertises a write tool to a read-only agent, and the answer is that discovery is filtered by scope so the tool never appears, and the call is refused with `-32001` even if the name is guessed, because discovery filtering is a courtesy and call-time authorisation is the enforcement. Ask what breaks when a team upgrades to the 2026-07-28 revision, and the answer is anything that kept per-session state, from in-memory maps indexed by session identifier to per-connection subscription lists, because the protocol is now stateless and every request must carry what the server needs, which is also why the revision is a gift to anyone running servers behind a load balancer. Ask where validation should live, in the schema, the server or the agent, and the answer is that the schema is the single source of truth, generated once and enforced at the boundary, while the agent's own checks are a courtesy that a hostile or confused caller can skip. And ask the question that separates a senior engineer from an expert: a tool result comes back containing an instruction, such as a ticket whose text tells the agent to delete another ticket, and what stops it, and the answer is that tool results are untrusted input, that a write tool requires a scope the read path never holds, and that the human-approval gate for write tools is a separate control from the protocol, which is the design that Chapter 7, on inter-agent security and guardrails, will build in full.

## Mapping to your production stack: Mastra and Amazon Bedrock

Everything in this chapter maps onto the stack you already run, and the mapping is worth making explicit, because the raw server is a teaching device and Mastra is where the lessons get applied. Mastra's `MCPClient` is the client side of this chapter: it connects to one or more MCP servers over stdio or Streamable HTTP, and it offers two ways of loading tools that mirror the discovery discussion, a static configuration through `getTools()`, which fetches the tool list once, and a dynamic configuration through `getToolsets()`, which re-reads tools per request, so the choice between them is the choice between a frozen tool list and one that follows the server as it changes, and the dynamic form is the one that honours a server whose `tools/list` answer depends on the caller. The client also speaks the 2026-07-28 revision and asks the server which revisions it offers through `server/discover`, falling back to the pre-2026 `initialize` handshake for servers that have not upgraded, which is the production version of the migration signpost this chapter's raw server returns as an error. On the approval side, Mastra's `requireToolApproval` option requires human approval before executing tools from a server, and the lesson to carry across is that approval is a host-side control, not a protocol property: the wire will happily deliver a write call, and something outside the wire has to decide whether it may run, which is exactly the gate this chapter's scoped server implements with scopes and which Chapter 8, on human-in-the-loop and breakpoints, will make durable. Mastra's built-in MCP server, which exposes agents, workflows and tools at `/api/mcp`, states the scoping rule in its strongest form, since each MCP tool is a thin wrapper around an existing HTTP route and a call runs through the same validation, authentication, role-based access control (RBAC) and ownership checks as the HTTP request, with the same request context, so an MCP client can never do more than the same user could do over the HTTP application programming interface (API), and that sentence is the production standard against which to judge any server you build: the MCP surface must never be more permissive than the API it wraps. Two further Mastra behaviours deserve attention: the documentation warns that tool responses must be treated as untrusted input, because a malicious or compromised server can use tool output for prompt injection and the transport client does not sanitise responses, so sanitisation belongs at the agent layer; and the default tool-schema validator supports JSON Schema 2020-12, which is the same dialect this chapter's Pydantic models generate, while Mastra's own tools are declared with Zod schemas in TypeScript, so the strictness discipline transfers directly even though the validation library changes. On the model side, Amazon Bedrock's Converse API (application programming interface) expresses tools through its `toolConfig`, and the model returns a `toolUse` block that your agent loop translates into an MCP `tools/call`, which means the Bedrock tool call and the MCP tool call are two envelopes around the same decision, and a malformed `toolUse` block should fail at your translation layer with the same fail-closed discipline, before any MCP request is written to the wire. The habit to take back to production is a short one: generate the schema once, enforce it at the boundary, filter discovery by the caller's scopes, check permission before validation, and never let the MCP surface exceed the HTTP API it wraps.

## Agent skills and tools: two different units of reuse

A tool is a single action the model can take, and a skill is the procedure that tells the model how to do a job that takes several actions, and the confusion between the two is why agent codebases so often end up with either a hundred tools the model cannot choose between or one giant prompt that nobody can maintain. A tool, as this chapter has built it, is one callable function with a name, a description and a JSON Schema: `search_docs` searches, `get_ticket` reads, `update_ticket_status` writes, and each one does exactly one thing and says so in its schema. A skill sits one level up: it is a packaged bundle, a folder with a `SKILL.md` file at its root, plus optional scripts the agent can run, reference documents it can read, and templates it can fill in, and the file itself has two parts, a YAML (YAML Ain't Markup Language) frontmatter block carrying a `name` and a `description`, and a Markdown body carrying the procedure — when to use the skill, the steps to follow in order, and the resources it may call. The description is the trigger, because the agent reads only names and descriptions at the start of a session and loads the full body only when a request matches, which is the progressive-disclosure design of the Agent Skills open standard, published at agentskills.io: tens of tokens per skill at discovery, the full body only on activation, where the specification recommends keeping the body under 5,000 tokens, and reference files only when a step points at them, so a library of fifty skills costs the session almost nothing until one of them fires, where fifty tools would cost their full schemas on every single call, which is the tax the next section prices.

The choice between the two units follows from what varies and what repeats. Reach for a tool when the job is a single action whose inputs can be written down as a schema, because a tool is the smallest thing the model can be wrong about, and a wrong tool call fails with a precise `-32602` against a named field. Reach for a skill when the job is a multi-step procedure that should be followed the same way every time, such as resolving a support ticket: read the ticket, search the documentation for the known failure, apply the fix, then move the ticket to `resolved` with a note saying how it was resolved, and the skill is what keeps the agent from skipping the second step or forgetting the fourth, because the procedure lives in one file the team can review instead of in the model's improvisation. The two compose in both directions, which is where the power and the failure mode both live: a skill calls tools, and a skill can call another skill when a job contains a sub-job, so a ticket-resolution skill can invoke a refund skill that itself calls the refund tool, and the composition stays readable as long as each layer does one job. The failure mode arrives when a skill's instructions contradict a tool's schema, and it arrives quietly: a skill that tells the agent to resolve a ticket without a note, or to pass a value the schema forbids, does not produce an error at the skill layer at all, because the skill is only prose, and the failure surfaces later as a `-32602` from the tool, which looks like a model mistake when it is really a disagreement between two sources of truth. The schema always wins at runtime, so the discipline is to treat the schema as the authority and the skill as its narration, and to test every skill by running its steps against the real tools, because a skill nobody has executed is a procedure nobody has verified. The advanced-level design-review angle is the placement question: given a procedure, where does each piece belong, and the answer you want ready is that anything the model must decide fresh each time belongs in a tool call, anything that must happen the same way every time belongs in a skill, and anything that must never happen belongs in neither, it belongs in a scope, which is the boundary this chapter already built. Explain it back this way: take the ticket-resolution procedure and say, for each step, whether it is a tool, a skill, or a permission, and what breaks if you put it in the wrong one.

## When not to reach for MCP

The Model Context Protocol earns its keep when a capability must be reused across hosts and clients, and it charges rent in exactly the cases where that reuse does not exist, so the decision is a cost calculation, not a loyalty test. The first cost is tokens, and it is a per-call tax, because the model needs every tool's schema in context before it can choose one, which means the schemas are re-sent on every turn of the conversation, not once at the start. Worked example, labelled as an assumption rather than a measurement: suppose ten tools whose schemas average 200 tokens each, which is 2,000 tokens attached to every turn before a word of the user's request is counted, and over a twenty-turn conversation that is 40,000 input tokens spent on describing tools, most of which were never called, and the tax grows with every tool you add, whether or not the conversation needs them. The wire itself is not the tax, since this chapter measured a local `tools/call` round trip at a median of 0.04 milliseconds, so the cost to watch is tokens and moving parts, not latency. The second cost is output: a tool that returns megabytes of context, such as a search tool that dumps whole documents instead of identifiers and summaries, spends the context window the model needs for reasoning, and a tool result that large also slows every later turn, because the result stays in the conversation, so the fix is to return pointers and pages rather than payloads, and if the tool cannot be reshaped that way it may not belong behind a model at all. The third cost is signal-to-noise: a tool list so long that the model picks the wrong tool, or picks a plausible-sounding one over the right one, is a selection problem the protocol cannot solve, and the chapter's own scoping discipline is the mitigation, since a filtered `tools/list` is also a shorter one, but filtering only helps when the list was too long because it contained tools the caller should never have seen, not when it is too long because the domain genuinely needs fifty tools.

Against those costs, the alternatives are deliberately unglamorous. A plain function call in the same process has no wire, no serialisation and no schema tax beyond what the model already holds; a direct REST (Representational State Transfer) call suits a single integration owned by the same team, where the client and the server change together; and a narrow purpose-built client suits a high-frequency call, such as a billing lookup an agent makes fifty times a minute, where a dedicated client can cache, batch and retry in ways a generic protocol call cannot. The rule of thumb that ties them together is to use the Model Context Protocol when the capability crosses a boundary that matters, a different team owns the server, the same tool must work in more than one host, or the caller is untrusted and needs scoping, and to skip it when the caller and the capability live in the same process, the integration is one client and one server that will never be reused, or the call is fixed and frequent enough that a direct call is cheaper, faster and one fewer process to deploy and monitor. The advanced-level design-review angle is the reversal: a reviewer who assumes the Model Context Protocol is always the answer is asking you to defend the boring choice, and the strongest defence is a number, so carry the worked example above and be ready to say what the schema tax costs per conversation, what the tool returns per call, and what breaks if the server process dies, because a protocol that adds a process, a wire format and a token tax to a call that needed none of those is not standardisation, it is overhead wearing a standard's name.

## Gateways and observability: a reference shelf

Once model calls and tool calls leave your laptop, two pieces of infrastructure sit in front of them and behind them, and this section is a reference shelf for both, not a recommendation. A gateway, also called a large-language-model gateway or an artificial-intelligence gateway, is a proxy that sits between your application and the model providers: your code sends one OpenAI-compatible request to one endpoint, and the gateway decides which provider serves it, attaches the real provider credential, and records what happened, which gives you one place for routing, fallbacks, budgets and key management instead of one integration per provider. An observability stack sits behind the calls and records them: every model call and tool call, its tokens, its cost, its latency, and the prompt version that produced it, so that when an agent goes wrong in production you can replay the run instead of guessing from the final answer. The rule for both shelves is the same as for the protocol itself: check the current pricing and documentation before you commit, because this category changes owners and price lists faster than any other in this course, and several entries below carry exactly that warning.

First, instrument once against the OpenTelemetry GenAI conventions where your stack allows it, because several of these backends ingest the same trace format, and the backend is then a choice you can revisit instead of a rewrite. Second, remember that traces are not an audit trail: they are sampled, they expire, and they exist to debug a run, while proving what an agent did belongs to the approval records and scoped permissions this chapter built, which is the subject Chapter 7 returns to.
