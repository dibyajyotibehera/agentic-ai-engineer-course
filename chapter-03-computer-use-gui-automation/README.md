## The idea in plain words

Every agent you have built so far in this course talks to the world through an Application Programming Interface (API) — a contract written for machines, with named operations, typed arguments and deterministic errors. Computer use is what you reach for when no such contract exists, because the only interface on offer is the one designed for a human being: a screen full of pixels, a mouse pointer and a keyboard. The agent looks at a screenshot, decides what a person would do next, and then does it — moving the cursor, clicking a button, typing into a field — before taking another screenshot to see what changed. That loop, repeated dozens of times, is the whole idea, and everything difficult about this chapter follows from it, because a screenshot is the most expensive and least precise observation an agent can consume, and a coordinate on a screen is the most fragile action it can emit.

The reason this matters at advanced depth is that the screen is not a niche. It is the fallback interface for the entire economy: the legacy internal tool with no API, the vendor portal that only exists as a web page, the desktop application your company bought in 2009 and cannot replace, the government form that only renders in a browser. Sooner or later, every agentic system meets a workflow that cannot be reached any other way, and the engineering question it raises has three parts: under what conditions is screen-driving the right call, how do you make the clicks land, and what does each task cost you. A model can click things — badly — so that is not the question; the question is whether screen-driving is the right call for this workflow, and what it costs to make it reliable. This chapter answers those three questions in order, and it does so with numbers you can check, because the field's headline numbers are easy to misread and the cost of a screenshot-driven agent is easy to underestimate by an order of magnitude.

## The mechanism, step by step

### The screenshot loop

The canonical computer-use loop is the one Anthropic shipped when it launched computer use in public beta on 22 October 2024 with Claude 3.5 Sonnet, the first frontier model to offer the capability, and it is worth understanding precisely because every other implementation is a variation on it. Your application declares a computer toolset in the request, the model replies with tool calls naming actions such as `screenshot`, `left_click`, `type` and `key`, your application executes each call against a sandboxed desktop — typically a virtual display inside a container — and returns the results, with a fresh screenshot image for every `screenshot` call, before calling the model again. The loop continues until the model answers in plain text or a step cap stops it, and the cap is load-bearing rather than decorative, because without it a confused agent will happily click the same dead button for a hundred steps at your expense. Anthropic's own documentation describes this loop, including the batch-action pattern in which the model returns several actions in one turn — click, type, then screenshot — and your application runs them in order, stopping at the first failure, so that the model can observe the outcome of its own actions before deciding what to do next.

Notice what the loop does not give the model: any structured knowledge of what is on the screen. The model sees pixels and must infer, from those pixels, where the "Submit" button is, what state the form is in, and whether its last click actually did anything. That inference is called grounding, and it is where computer-use agents mostly fail, which is why the rest of this section is about making grounding reliable rather than about the loop itself — the loop is the easy part, and any engineer can write it in an afternoon, whereas grounding is the part that decides whether the agent works.

### Grounding: turning "the blue button" into coordinates

Grounding is the problem of converting a model's intention — "click the checkout button" — into a point on the screen, an `(x, y)` coordinate pair, and it is the principal failure mode of screenshot-driven agents. The model can describe the right element in words and still click the wrong place, because estimating a coordinate from a downscaled image is an imprecise act: a button that is 40 pixels wide on a 1920-pixel-wide screen occupies a small fraction of the image the model actually sees, and an error of a few dozen pixels is the difference between "Submit" and the advertisement beside it. Anthropic's own prompting guidance acknowledges this directly, recommending that you place the instruction text before the screenshot image in the message, because the target description is processed before the image and improves click accuracy, and that you use the `zoom` action to inspect a region at full resolution when small text is not legible in the downscaled screenshot. These are not polish; they are admissions that raw coordinate estimation from a full-screen image is unreliable, and they point at the two directions the field has taken to fix it — giving the model a better picture, or giving it something better than a picture.

### Set-of-Mark prompting: label first, then point

Set-of-Mark prompting, published in October 2023, is the single most effective grounding trick in this chapter, and its mechanism is disarmingly simple: instead of asking the model to guess coordinates from a bare screenshot, you first segment the image into regions with an off-the-shelf segmentation model such as the Segment Anything Model (SAM), then overlay visible marks — numbers, boxes or masks — on each region, and hand the marked image to the model. The model then answers with a mark, "click 7", instead of a coordinate, and your code translates the mark back into the centre of the corresponding region. The task changes from continuous coordinate regression, which vision-language models are bad at, to discrete selection among labelled options, which they are good at, and the measured effect is dramatic: on the RefCOCOg referring-expression comprehension benchmark, GPT-4V went from 25.7% accuracy to 86.4% with Set-of-Mark prompting — but read that number with the caveat it deserves, because it was measured on a sub-sampled set of 177 instances, not the full benchmark — while referring segmentation reached 75.6% mean Intersection over Union and phrase grounding on Flickr30K reached 89.2% Recall@1. The paper is [Set-of-Mark Prompting Unleashes Extraordinary Visual Grounding in GPT-4V](https://arxiv.org/abs/2310.11441), and the code is public, so this is a technique you can reproduce rather than a result you must take on trust.

The engineering lesson of Set-of-Mark prompting runs deeper than the numbers, because it generalises into a design principle: never make the model do in one step what your deterministic code can do better in two. Segmentation and labelling are deterministic, cheap and exact; selection among labels is what the model is for. The same principle reappears everywhere in this chapter — in coordinate mapping, in screenshot diffing, in the Document Object Model (DOM) hybrid below — and it is the difference between an agent that guesses and an agent that is engineered. Exercise 2 in [exercises.md](exercises.md) makes you build this pipeline yourself, with a DOM-derived labeller standing in for a segmentation model, so you can measure the accuracy gain on your own screen instead of quoting the paper's.

### Coordinate mapping: the arithmetic between two grids

Even with Set-of-Mark prompting, coordinates eventually have to land somewhere, and the mapping between the model's coordinate grid and the screen's pixel grid is a small piece of arithmetic that causes a large share of real-world failures when it is wrong. The model typically answers in a normalised 0–1000 grid, while the screen is 1920 by 1080 physical pixels, the screenshot the model saw may have been downscaled to 1280 by 720, and the browser viewport may be offset inside the window by a toolbar and a bookmark bar. Each of those is a linear transform — a scale factor on each axis plus an offset — and the correct click is the composition of all of them, applied in the right order. Get the order wrong, or forget the device pixel ratio on a high-DPI display, and every click lands systematically off-target by a constant displacement, which is a particularly nasty failure because the agent's screenshots will show the cursor hovering near the button it meant to press, and the model will conclude that the button is unresponsive rather than that its aim is off. The discipline this demands is the same one you already apply to any coordinate system in graphics or robotics: name every frame of reference, write the transform down, test it with a known target before you trust it with a real task, and log the raw and transformed coordinates on every action so that a systematic offset is diagnosable from the trajectory instead of invisible inside it. The code in this chapter's `code/` directory includes a coordinate mapper with exactly that logging, and Exercise 2 asks you to measure its error on targets of decreasing size, because the error that is invisible on a large button is fatal on a 16-pixel icon.

### Screenshot diffing: seeing only what changed

A screenshot-driven agent that re-reads the entire screen on every step is doing far more work than the task requires, because most steps change only a small region — a field fills in, a spinner appears, a toast notification slides up — and the rest of the screen is identical to the step before. Screenshot diffing is the technique of comparing consecutive screenshots pixel by pixel, computing the bounding boxes of the regions that actually changed, and using those regions to decide what the agent needs to look at next. Its first use is efficiency: you can crop the next screenshot to the changed region and send the model a small, high-resolution image of exactly what moved instead of a large, downscaled image of everything, which attacks both the token cost and the legibility problem at once. Its second use is verification: after a click, the diff between the before and after screenshots is the ground truth of whether the click did anything, and an agent that checks the diff instead of assuming success will not march onward from a click that silently missed. And its third use is change detection in its own right — watching a page for a price change, a status flip or a new row in a table — which is a legitimate automation task that needs no model at all, and a useful reminder that not every screen problem is an agent problem. Exercise 3 builds a differ from scratch with Pillow, including the threshold tuning that separates a real change from rendering noise such as a blinking cursor or an animated advertisement, because a differ with no threshold reports everything as changed, which is the same as reporting nothing.

### DOM and accessibility-tree agents: the structured alternative

All of the machinery above exists because screenshots are unstructured, and the obvious question is why you would accept that when the browser already knows exactly what is on the page. The Document Object Model — the browser's structured representation of the page, with every element, its role, its text and its bounding box — is available to any automation that runs inside the browser, and the accessibility tree is a cleaned-up version of the same information, the tree of roles and names that screen readers use, which strips away layout divs and styling noise and leaves the semantic structure: buttons, links, text fields, headings, and their labels. An agent that reads the accessibility tree instead of a screenshot gets exact element identities for free, clicks by element reference instead of by guessed coordinate, and consumes text tokens instead of image tokens, which is cheaper by a wide margin. This is the architecture of [Browser-Use](https://microsoft.github.io/ai-agents-for-beginners/15-browser-use/), the open-source framework at the centre of the Microsoft lesson this chapter adapts, and it is why that lesson pairs Browser-Use with [Playwright](https://playwright.dev/python/docs/intro) and the [Chrome DevTools Protocol](https://chromedevtools.github.io/devtools-protocol/): Playwright owns the browser lifecycle and the deterministic actions, Browser-Use owns the open-ended navigation, and the two share one Chrome session over the Chrome DevTools Protocol so that the agent and the deterministic code are always looking at the same page.

Playwright itself deserves a sentence of its own, because it is the default browser engine for this chapter's code and for much of the agent ecosystem: it drives Chromium, Firefox and WebKit through one Python API, it waits automatically for elements to become actionable instead of making you sleep and hope, and its locators — `get_by_role`, `get_by_label`, `get_by_text` — address elements the way a user thinks about them, by role and name, which is precisely the vocabulary an agent needs. Its counterpart, [Puppeteer](https://pptr.dev), is Google's Node.js library for driving Chrome over the same protocol, and the choice between them in this course is Python versus JavaScript rather than capability. The point that matters for the decision framework below is that a DOM-driven agent is not a lesser computer-use agent; it is a computer-use agent that refused to throw away information the browser was already offering, and on any page where the DOM is available and stable, it is faster, cheaper and more reliable than the screenshot loop by a distance that is not close.

### The hybrid: deterministic actors, vision agents, and the seam between them

The honest architecture, and the one Microsoft's Lesson 15 actually teaches, is neither pure screenshots nor pure DOM, but a hybrid with a clean seam. Deterministic Playwright actors handle the fast, scripted, repeatable parts — logging in, navigating to a known URL, filling a form whose fields you already know — because a script does those in milliseconds with zero model cost and zero grounding risk. The vision agent takes over only for the parts that are genuinely open-ended: dismissing an unexpected pop-up, coping with a layout that shifted, finding the one control on a page you have never seen before. The two share the browser through the Chrome DevTools Protocol, so the handoff is a state transfer inside one session rather than a restart, and the design question becomes where to draw the seam — which steps are scripted and which are delegated — rather than which religion to join. That seam is also where the guardrails live: the deterministic layer is where you put allow-lists of URLs, confirmation gates before consequential actions, and hard step caps, because a script enforces those exactly while a model merely intends to. Chapter 7 returns to this from the security side; here, the takeaway is that the hybrid is not a compromise you settle for, but the architecture you design toward.

## How good is it, really: the OSWorld progression and the ruler that changed

The benchmark that anchors this whole field is [OSWorld](https://os-world.github.io/), a set of 369 real desktop tasks running on real Ubuntu, Windows and macOS virtual machines — LibreOffice, Chrome, VS Code, GIMP, Thunderbird, the file manager, the terminal, and workflows that span several applications at once — graded by execution-based checkers that inspect the final machine state rather than the model's words, so each task is a binary pass or fail with no partial credit. The human baseline measured in the original paper is 72.36%, which already tells you something important: competent humans fail more than a quarter of these tasks, because some instructions are ambiguous, some tasks are genuinely hard, and some graders are strict, so "human-level" here means matching a noisy reference point, not achieving perfection.

Against that ruler, the progression reads like a success story until you look at the dates. Claude 3.5 Sonnet scored 14.9% screenshot-only when computer use launched in October 2024, rising to 22.0% when given more steps. OpenAI's Computer-Using Agent, launched with Operator on 23 January 2025, scored 38.1% on OSWorld, 58.1% on WebArena and 87% on WebVoyager — the WebVoyager figure reflecting that its tasks are simple navigation rather than hard desktop work. Claude Sonnet 4.5 reached 61.4% on OSWorld-Verified in September 2025, and Claude Sonnet 4.6 reached 72.5% in February 2026, the first model to cross the human baseline. Operator, meanwhile, was folded into ChatGPT agent on 17 July 2025 and the standalone product was shut down on 31 August 2025, a reminder that a good benchmark score is not the same as a viable product.

But the story has a seam in it, and an experienced engineer must be able to see the seam. On 28 July 2025 the OSWorld maintainers released OSWorld-Verified, an in-place repair of the existing task set: over-strict graders were loosened to fuzzy matching, tasks that had become infeasible as the live web changed were fixed or removed, ambiguous instructions were rewritten, and the infrastructure moved so a full evaluation ran in about an hour instead of ten. Scores measured before that date and scores measured after it were therefore measured on different task definitions with different graders, and they are not comparable — plotting Claude 3.5 Sonnet's 14.9% on the original OSWorld on the same smooth curve as Sonnet 4.5's 61.4% on OSWorld-Verified splices two different rulers together, and the specific deltas across the July 2025 boundary are apples to oranges even though the direction of travel is real. Add to that the second caveat, that every score in the paragraph above is self-reported — each vendor runs its own harness, its own prompt, its own step budget and reports its own best configuration, so cross-vendor comparison is comparing scaffolds as much as models — and the honest reading of the progression is that models genuinely got much better at short, single-application desktop tasks, and that the headline numbers overstate how much of that improvement transfers to anything else.

The transfer gap is the most important fact in this section, and it is where the benchmark story meets production reality. Independent analysis of the field, summarised in the [Agentropic essay on what OSWorld scores really mean](https://www.agentropic.ai/blog/computer-use-agents-osworld-reality/), shows the cliff clearly: on UI-CUBE, a set of 226 enterprise tasks, frontier models scored 67–85% on simple atomic interactions — click this, fill that — and then fell to 9–19% on complex multi-step enterprise workflows, while humans with no prior experience of the applications still scored 61.2% on those same complex tasks. The same pattern repeats across other benchmarks the essay surveys: GPT-4o falling from 42.7% on atomic tasks to 3% on compositional workflows on WorkArena++, and from 64.52% on single-application tasks to 21.43% on three-application tasks on OfficeBench. The mechanism the essay points to is architectural — memory, hierarchical planning and state coordination across steps — and its authors argue explicitly that it is not fixable by better prompting. So the OSWorld progression tells you that the grounding problem is largely being solved, and the cliff tells you that the planning problem is not, which is exactly the split you should carry into any build-or-buy decision: if your workflow is short and single-application, a current screenshot agent is a credible tool; if it is long, multi-application and stateful, the benchmark number tells you almost nothing about whether it will work.

## The cost arithmetic: why screenshots are the expensive way to see

Cost is where the screenshot-versus-DOM decision stops being a matter of taste and becomes arithmetic, and the arithmetic is unforgiving. The figures in this section come from Anthropic's own documentation as summarised in an explainer checked on 28 October 2026, and they are worth working through slowly because they explain why every production computer-use system eventually becomes a hybrid. Declaring the computer toolset adds about 4,500 input tokens to every request, before the model has seen anything at all, because the tool definitions themselves must be carried in context. Each screenshot costs roughly 1,000 to 1,800 input tokens, depending on resolution. And because the agent loop re-sends the conversation on every step, those costs compound: a 30-step task works out to about 783,000 input tokens in total, which is about $1.61 on Claude Sonnet 5.5 at list prices. That is $1.61 for one task, one time, on a task short enough to finish in 30 steps — and the moment you add prompt caching, longer screenshots, higher resolution for legibility, or a step budget of 50 or 100, the number grows, while the cost of the equivalent DOM-driven task stays close to the cost of the text alone, because an accessibility-tree snapshot is a few hundred tokens of structured text and a deterministic Playwright click costs no model tokens at all.

Three consequences follow from that arithmetic, and they shape every design decision in this chapter. First, the fixed cost dominates the short task: the 4,500-token toolset declaration is paid on every request whether the task takes one step or fifty, so screenshot agents are uneconomic for short, repeatable work and only begin to make sense where the task is genuinely open-ended enough to justify the overhead. Second, the per-step cost is dominated by images, not reasoning, so the highest-leverage optimisation is not a smarter model but a smaller observation — screenshot diffing to send only the changed region, zooming into a region instead of re-sending the whole screen, dropping to the accessibility tree whenever the page allows it — and each of those is a deterministic engineering choice, not a prompting trick. Third, the total cost scales with steps, and screenshot agents take more steps than humans for the same task — the Agentropic essay reports successful agents taking 1.4 to 2.7 times as many steps as a human — so a task that looks like $1.61 at 30 steps is $4 or more at the step counts a real workflow needs, and a run that succeeds is still a run you paid for in full. Exercise 4 makes you build this cost model as code, with the verified token figures as its anchors, so that you can answer the question "what does this workflow cost at 1,000 runs a month" with a number instead of a feeling, and so that you can see for yourself where the break-even point between the screenshot path and the DOM path sits for your own task mix.

## The advanced-level design-review angle: API first, structured DOM second, screenshots last

If this chapter appears in a design review, it will not appear as a request to recite a benchmark. It will appear as a design question — "automate this workflow" — and the answer the reviewer is listening for is a decision procedure, applied in order, with a reason at each step. The procedure is the spine of this chapter, and it runs like this. First, ask whether an API exists, including the undocumented or unofficial one, because an API call is deterministic, cheap, testable and auditable, and every other option is a workaround for its absence; if the vendor has an API, use it, and if the workflow is valuable enough, the correct engineering answer may be to negotiate for API access rather than to build a screen agent. Second, if there is no API but there is a browser, ask whether the DOM or the accessibility tree can carry the task, because structured selectors are exact where coordinates are approximate, text tokens are cheap where image tokens are dear, and a Playwright script is a testable artefact where a screenshot trajectory is a hope; this is where the hybrid architecture earns its keep, with deterministic actors doing the known steps and the model reserved for the genuinely unknown ones. Third, and only third, reach for screenshots — for the desktop application with no DOM, the canvas-rendered interface, the legacy tool that exposes nothing else — and when you do, bring the full grounding toolkit: Set-of-Mark prompting so the model selects instead of guessing, coordinate mapping with every frame of reference named and logged, screenshot diffing so the agent verifies each action against what actually changed, and a step cap with a human approval gate before anything consequential, because a screen agent that can click "Submit" can also click "Delete all" with the same confidence.

That ordering is also the answer to the question of what to build first in production, and it is the standard you should hold any vendor demo to: ask which of the three layers the demo actually used, and whether the task it performed would have survived the API question. A demo that drives a screen to do something an API could have done in one call is not a demonstration of capability; it is a demonstration of cost. And the safety corollary belongs in the same answer, because a screen agent reads untrusted content as part of its job — instructions embedded in a web page or an image can override the operator's instructions, which is why Anthropic's documentation warns that computer use carries prompt-injection risks distinct from ordinary API use, runs classifiers over returned screenshots to flag injected instructions, and advises isolating the agent from sensitive data and actions. The agent that can see everything can be told anything, and the approval gate is not a product feature but the boundary between automation and delegation of judgement.

By the end of this chapter you will have driven a form end to end with deterministic DOM selectors, built a Set-of-Mark labeller and measured how much it improves click accuracy over raw coordinate guessing, written a screenshot differ that can tell a real change from rendering noise, and modelled the cost of a screenshot-driven task against its DOM-driven equivalent with real token figures.
