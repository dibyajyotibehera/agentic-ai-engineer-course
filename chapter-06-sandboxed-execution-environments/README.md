# Chapter 6 — Sandboxed Execution Environments

> **Provenance.** The shape of this chapter — local execution versus container versus microVM, and the idea that isolation and resource controls are the lesson — is inspired by the syllabus of DeepLearning.AI's [Building Coding Agents with Tool Execution](https://learn.deeplearning.ai/courses/building-coding-agents-with-tool-execution/lesson/i11do3/tool-execution-environments) (proprietary; syllabus inspiration only, nothing copied). Everything else in this chapter is original writing: no course anywhere teaches [WebContainers](https://webcontainers.io/api), [gVisor](https://gvisor.dev/docs/architecture_guide/intro/), Docker-in-Docker, or network egress blocking, so those sections were written from the primary documentation linked throughout.

## What you will be able to do

By the end of this chapter you will be able to take an agent that writes and runs code — the most dangerous tool an agent can own — and put a real boundary around it: choose the isolation mechanism that matches the threat, configure it so that a hostile or merely buggy program cannot read your secrets, eat your host, or phone home, and then *prove* the boundary holds by attacking it yourself. You will know when a plain container is enough, when you need a second kernel or a whole virtual machine, and when the honest answer is to stop running the code on your own infrastructure at all and hand it to a managed sandbox service.

## The idea in plain words

An agent that can run code is an agent that can do anything a program can do, because that is what running code means. Every other tool you give an agent — a database query, a file read, an Application Programming Interface (API) call — is a narrow corridor with walls you chose. Code execution is not a corridor. It is a door into a room where the agent can build its own corridors, and if that room is your laptop, your build server, or your production Amazon Elastic Container Service (ECS) task, then the agent can reach everything in that room: your files, your credentials, your network, your neighbours on the same host.

A sandbox is the decision to stop pretending that code execution is just another tool call and to treat it as what it is — running untrusted code — and to give that code a room of its own, with walls you control, a ceiling on what it can consume, and a door to the network that is locked unless you open it for a named destination. The rest of this chapter is the engineering of those walls: what they are made of, how strong each material is, what each one costs you in latency, complexity and compatibility, and how you verify, rather than assume, that they hold. The through-line is a single habit that separates an experienced engineer from someone who has merely read the [Docker](https://docs.docker.com/engine/containers/resource_constraints/) documentation: you do not ship a sandbox you have not tried to break.

## The threat model, or what agent-generated code can do to you

Start with the uncomfortable premise, because everything that follows is a consequence of it: agent-generated code is untrusted code, even when the agent is yours, the model is yours, and the user is well-meaning. The model does not write code the way your team writes code. It writes code by predicting what code usually looks like, which means it will cheerfully reproduce a pattern that downloads and executes a remote script, or that reads an environment variable full of credentials and posts it somewhere, or that follows a plausible-sounding instruction embedded in the very data it was asked to analyse. And that is the benign case. The hostile case is a prompt injection smuggled into a web page, a document, or a tool result, which is exactly the attack that Chapter 7, on inter-agent security and guardrails, is built to defend against — but no guardrail is perfect, and the sandbox is what stands between a guardrail failure and a breach. So the threat model has to cover both the agent that makes a mistake and the agent that has been turned against you, and it has to cover them without assuming you will notice in time, because the whole point of an agent is that it acts while you are not watching.

Walk through what the code can actually do once it runs, and the list organises itself into five harms, each of which maps onto a control you will meet later in the chapter, so keep the mapping in mind as you read. First, it can read things it should not read, which is the confidentiality harm: your source code, your database credentials in environment variables, the cloud credentials on the host, the private keys in a home directory, or the files of another tenant's agent running on the same machine. Second, it can write things it should not write, which is the integrity harm: deleting data, corrupting a shared volume, overwriting the agent's own tooling so that the next run behaves differently, or planting a back door that only fires later. Third, it can talk to things it should not talk to, which is the exfiltration and pivoting harm: sending your data to an attacker-controlled server, downloading a second-stage payload, scanning your internal network for databases and metadata services, or using your host as a relay to attack someone else. Fourth, it can consume things it should not consume, which is the availability harm: a fork bomb or an unbounded allocation that starves every other workload on the host, a tight loop that burns CPU until your bill or your pager notices, or a disk-filling write that takes down the node. And fifth, it can persist, which is the harm that makes the other four worse: a process that survives the agent run, a cron entry, a modified startup script, or a poisoned cache that turns one bad execution into a permanent compromise.

Notice what this list implies about where the boundary has to sit. Reading and writing are filesystem and permission problems, so the sandbox needs a filesystem the code cannot escape and an identity with almost no privileges. Talking is a networking problem, so the sandbox needs egress control that defaults to nothing. Consuming is a resource problem, so the sandbox needs hard limits enforced by the kernel, not by asking the code politely to behave. And persisting is a lifecycle problem, so the sandbox needs to be disposable: created for one run, destroyed afterwards, with nothing carried over except the results you explicitly copy out. Any design that answers only one or two of these five is not a sandbox, it is a hope, and the exercises at the end of this chapter are built around proving each of the five fails in turn.

There is one more part of the threat model that practitioners routinely get wrong, which is the question of *whose* code you are afraid of. If the only code that ever runs is generated by your own agent for your own task, on your own data, then a container with sensible limits is a proportionate answer, because your adversary is mostly your own agent's mistakes plus the occasional injected instruction. But the moment the code comes from a third party — a user pasting a script, a marketplace agent, a document the agent was asked to execute, or a multi-tenant platform where one customer's agent runs beside another's — then the adversary is a human who is actively trying to escape, and a shared kernel starts to look like a thin wall. That distinction, between accidental harm and adversarial escape, is the axis on which the whole comparison in this chapter turns, and it is the first question an experienced engineer asks before choosing a mechanism: not "which sandbox is best", but "who am I keeping out, and how hard will they try?"

## The mechanism, layer by layer

Isolation is not one technology. It is a stack of mechanisms, each of which closes a different avenue, and the art of sandboxing is knowing which layers you have, which you are missing, and which layer you are actually relying on when you say the word "sandbox". So before the named products, here is the stack itself, from the inside out, because every product in this chapter is a different combination of these same layers.

At the bottom, closest to the code, are the Linux primitives that every container is built from. Linux namespaces give a process its own view of the world: its own process tree, its own mount table, its own network interfaces, its own user identifiers, so that code inside the namespace cannot even name things outside it, let alone touch them. Control groups, universally shortened to [cgroups](https://docs.kernel.org/admin-guide/cgroup-v2.html), are the accounting and enforcement layer: they measure how much CPU time, memory, disk input/output and how many processes a group of processes has used, and they enforce the ceiling you set, which is how a memory limit becomes a killed process rather than a suggestion. Secure computing mode, known as [seccomp](https://gvisor.dev/docs/architecture_guide/intro/), filters the system calls a process may make, so that even code running as root inside a container cannot invoke the calls that would let it escape. Linux capabilities break the old all-or-nothing root privilege into individual permissions, so a container can be denied the capability to mount filesystems or administer the network even while it runs as the root user inside its own namespace. And a read-only root filesystem, a non-root user, and the `no-new-privileges` flag together remove the classic escalation paths, which are the ways a process gains more privilege than it started with. None of these primitives is a sandbox on its own. Together, correctly configured, they are what makes a container more than a packaging format, and every failure mode in this chapter's exercises traces back to one of them being left at its default.

On top of those primitives sits the container itself, and it is worth being precise about what a container is and is not, because the most common sandboxing mistake is treating a container as a security boundary when it is, by default, a packaging and resource boundary with a shared kernel. A container is a process, or a small group of processes, running on the host kernel with namespaces and cgroups applied, and the [Docker documentation on resource constraints](https://docs.docker.com/engine/containers/resource_constraints/) states the default plainly: a container has no resource constraints unless you set them, and it can use as much of a given resource as the host kernel scheduler allows. That sentence is the whole reason the first exercise in this chapter exists. The shared kernel is the container's strength — it is why containers start fast and pack densely — and it is also its weakness, because a kernel vulnerability is a container escape, and the code you run is one system call away from the host kernel, as the [gVisor security introduction](https://gvisor.dev/docs/architecture_guide/intro/) puts it. So a container is the right sandbox when your threat is accidental harm and ordinary mistakes, and it is the wrong sandbox, on its own, when your threat is a determined adversary with a kernel exploit, which is a judgement call this chapter will keep returning to.

That judgement call is exactly what gVisor was built for, and it is the first of the three named mechanisms in this chapter because it changes the boundary without changing your tooling. [gVisor](https://gvisor.dev/docs/architecture_guide/intro/) is an application kernel, written in the Go programming language, that runs in userspace and sits between the sandboxed code and the host kernel, intercepting the code's system calls and serving them itself instead of passing them through. The component that does this is called the Sentry, and the crucial property, stated in gVisor's own security introduction, is that gVisor never passes a system call through to the host: if a kernel feature has not been reimplemented inside gVisor, the sandboxed workload simply cannot use it, which means an attacker who wants to escape has to exploit both the gVisor Sentry and the host kernel, which share no code. In practice you use it as an [Open Container Initiative (OCI)](https://gvisor.dev/docs/architecture_guide/intro/) runtime called `runsc`, so the only change to a Docker workflow is `--runtime=runsc`, and on Kubernetes you select it with a `RuntimeClass`, which means your images, your registry and your deployment tooling stay exactly as they are. The cost is real and you should name it honestly: system-call-heavy workloads run slower, because every call is intercepted and handled in userspace, and some kernel features are not implemented, so a few programs fail under `runsc` that run fine under the standard `runc` runtime, which means you test your real toolchain under gVisor before you commit to it rather than discovering the incompatibility in production. And gVisor is explicit about what it does *not* protect against — side-channel attacks of the Spectre family, exploits inside the sandboxed workload itself, and attacks on components above the sandbox — so it strengthens the kernel boundary without pretending to be a complete security story, which is precisely the kind of honest boundary an experienced engineer wants to hear.

If gVisor strengthens the boundary by adding a second kernel in userspace, the microVM strengthens it by adding a second kernel behind a hardware boundary, and that is the mechanism underneath the most widely used managed sandbox service in the agent world. A microVM is a stripped-down virtual machine: a real guest kernel, running behind the [Kernel-based Virtual Machine (KVM)](https://github.com/firecracker-microvm/firecracker/blob/HEAD/README.md) hardware virtualisation boundary, with a deliberately tiny device model so there is very little machinery for an attacker to target. [Firecracker](https://github.com/firecracker-microvm/firecracker/blob/HEAD/README.md) is the open-source virtual machine monitor, originally built at [Amazon Web Services (AWS)](https://github.com/firecracker-microvm/firecracker/blob/HEAD/README.md) for [AWS Lambda](https://github.com/firecracker-microvm/firecracker/blob/HEAD/README.md) and [AWS Fargate](https://github.com/firecracker-microvm/firecracker/blob/HEAD/README.md), that made microVMs practical for this purpose, and its design is the reason the agent-sandbox industry converged on it: a microVM is still a virtual machine, with the hardware-enforced isolation that implies, but it starts fast enough and weighs little enough that you can create one per agent run, per user, or per task, instead of sharing one machine between tenants. [Kata Containers](https://documentation.suse.com/cloudnative/rke2/latest/en/add-ons/kata.html) takes the same idea into Kubernetes, running each pod inside its own lightweight virtual machine with its own guest kernel while keeping the ordinary container workflow, and the lesson to take from both is that the microVM is what you reach for when the shared-kernel risk is the risk you cannot accept, and you are willing to pay for a per-sandbox kernel in startup latency and memory overhead to remove it.

[E2B](https://docs.e2b.dev) is what that microVM looks like when someone else operates it for you, and it is the managed end of the spectrum, which matters because operating your own microVM fleet is a platform project, not a feature. E2B provides isolated cloud sandboxes — Firecracker microVMs, created on demand, with a [Python](https://docs.e2b.dev) and [JavaScript](https://docs.e2b.dev) software development kit — in which an agent can run commands, work with files, and execute code, and the service adds the lifecycle machinery that is tedious to build yourself: templates that define what environment a sandbox starts with, pause and resume that preserves both filesystem and memory so a long-running agent can be suspended cheaply, and a timeout after which the sandbox is killed whether or not the agent remembered to clean up. The E2B documentation is the reference for the exact software development kit surface, and the example in `code/e2b_example.py` shows the shape of it — create a sandbox, run the generated code inside it, kill the sandbox when the run finishes — while being explicit that it needs an E2B API key and therefore cannot be run for free in this chapter's exercises. The decision E2B forces is an organisational one as much as a technical one: you trade control and per-run cost for not having to operate the isolation layer yourself, and for a team whose product is the agent rather than the sandbox, that trade is usually correct, while for a team running at a scale or in a regulatory environment where code and data must stay inside their own [Virtual Private Cloud (VPC)](https://e2b.dev/llms.txt), the bring-your-own-cloud deployment exists precisely because the trade is not always correct.

WebContainers sit at the opposite end of the spectrum from E2B, and they are in this chapter because they dissolve an assumption the rest of the chapter makes, which is that sandboxed code has to run on a server at all. [WebContainers](https://webcontainers.io/api) are a WebAssembly-based operating system that runs a real [Node.js](https://webcontainers.io/api) runtime entirely inside a browser tab, built by [StackBlitz](https://webcontainers.io/api), and the public [WebContainer API](https://webcontainers.io/api) lets you boot a container, mount a filesystem into it, spawn processes, and serve the result back to the page, all without any server-side execution. The security boundary here is the browser's own sandbox, which is the most battle-tested sandbox in existence, and the isolation is almost free: the code cannot reach your filesystem, your network, or your credentials except through the browser APIs you explicitly grant, and when the tab closes the whole environment is gone. The limits are equally stark and you must not hand-wave them away: it is Node.js only, so your Python agent code does not run there; it needs cross-origin isolation headers, which means the page that hosts it must send the `Cross-Origin-Embedder-Policy` and `Cross-Origin-Opener-Policy` headers or `SharedArrayBuffer` is unavailable and the container will not boot; and the code runs on the user's machine, in their browser, which makes WebContainers a superb fit for interactive demos, tutorials, and agent-built front ends that the user can preview and edit, and a poor fit for anything that must run server-side, at scale, or out of the user's sight. The example in `code/webcontainer_boot.mjs` shows the boot-mount-spawn shape, and the lesson it teaches is a strategic one: sometimes the cheapest sandbox is the one you do not operate, because the user's browser is already operating it for you.

Docker-in-Docker is the mechanism in this chapter that you will most often be told to use and most often need to refuse, so it deserves a careful treatment rather than a warning label. The name covers two different designs, and confusing them is itself a security failure, so keep them apart. True Docker-in-Docker runs a second Docker daemon inside the container, usually from the `docker:dind` image, and it needs `--privileged` mode because the inner daemon needs kernel features that ordinary containers are denied, which means the container that hosts it has effectively been given the keys to the host. Docker socket binding, often called Docker-outside-of-Docker, is the other design: it mounts the host's Docker socket, `/var/run/docker.sock`, into the container, so the Docker client inside the container talks to the daemon on the host, and every container it starts is a sibling on the host, not a child inside the sandbox. That second design looks safer because there is no `--privileged` flag, but it is arguably more dangerous, because access to a rootful Docker daemon is root-equivalent access to the host: a process that can talk to the daemon can start a privileged container, mount the host root filesystem into it, and read every secret on the machine, which is exactly the attack the breakout exercise in this chapter demonstrates. The legitimate uses are real but narrow — building container images inside a [continuous integration (CI)](https://tiendu.github.io/2025/04/18/dind.html) job is the canonical one — and the safe ways to do it are to run the job on a dedicated, disposable host you do not care about, to use a rootless daemon, or to use a socket proxy that restricts which Docker API calls the job may make, and the rule that governs all of them is simple: never give untrusted agent-generated code access to a Docker daemon, in either form, because the moment you do, your sandbox is the daemon, and the daemon is the host.

Resource limits are where the sandbox stops being a wall and becomes a budget, and they deserve their own section because they are the control most often configured wrongly, usually by being left at the default. The enforcement mechanism is [cgroups version 2](https://docs.kernel.org/admin-guide/cgroup-v2.html), the Linux kernel's unified hierarchy for organising processes and distributing resources, and Docker's flags are a thin, friendly layer over cgroup files: `--memory` writes to `memory.max`, `--cpus` writes to `cpu.max`, and `--pids-limit` writes to `pids.max`, which is why you can verify a limit either through `docker inspect` or by reading the cgroup files directly. The [Docker resource constraints documentation](https://docs.docker.com/engine/containers/resource_constraints/) gives you the semantics you need to set them correctly: memory is a hard limit, so exceeding it gets the process killed by the out-of-memory killer with exit code 137, while CPU is a throttle, so exceeding it only slows the process down; `--memory-swap` set to the same value as `--memory` removes swap access entirely, which matters because an unset swap limit silently doubles the memory a container can use; and the minimum memory value Docker accepts is 6 megabytes, which is a useful reminder that the limits are enforced by the kernel whether or not your application understands them. The limits you should always set, on every sandbox, are memory with swap disabled, CPU, process count, and wall-clock time, because each one closes a different denial-of-service avenue — memory stops the allocation bomb, CPU stops the tight loop, the process limit stops the fork bomb, and the timeout stops the job that never returns — and the first exercise proves each of them by running code that tries to exceed them and watching it fail. There is a second, subtler point about limits, which is that they are also a cost control: a sandbox with no CPU limit is a sandbox that can burn your cloud bill as fast as it can burn your host, and the timeout is the cheapest kill-switch you own, so set it before the run starts, not after you notice the run has not finished.

Network egress blocking is the last mechanism, and it is the one that most directly answers the exfiltration harm, so it is worth treating as a first-class control rather than an afterthought to the container flags. The strongest form is also the simplest: `--network none`, which the [Docker run reference](https://github.com/Shopify/docker/blob/master/docs/reference/run.md) documents as disabling all incoming and outgoing networking, leaving only the loopback interface, so the code can compute but cannot talk to anyone, and your only channels in and out are files and standard input and output. That is the correct default for any agent run that does not need the network, which is most of them: code that analyses a dataset, transforms a file, or runs a test suite has no business making network calls at all, and giving it a network is giving it an exfiltration channel for free. When a run genuinely needs the network — to install a package, to fetch a dataset, to call an API — then the answer is an allowlist, not an open door, and the allowlist has to be enforced outside the sandbox, because anything enforced inside the sandbox can be changed by the code running inside it. The practical shape is a proxy: the sandbox has no direct route out, and its only egress is through a forward proxy that permits only named hosts, which is what `code/egress_proxy.py` implements in miniature, and the exercise built around it proves the point by showing one host reachable and every other host failing. There are two details that make or break an allowlist in practice, and both are easy to miss. The first is the [Domain Name System (DNS)](https://gvisor.dev/docs/user_guide/networking/), because a proxy that checks hostnames is only as good as its DNS resolution, and a sandbox that can reach an attacker-controlled DNS server can be tricked into resolving an allowed name to an attacker-controlled address, so the resolver itself has to be trusted and the allowlist has to be enforced on resolved addresses as well as names where that matters. The second is the cloud metadata service, the link-local address that cloud providers use to hand credentials to workloads, which is reachable from inside a container by default on many platforms and is the single most valuable target for exfiltrating code, so blocking it explicitly — and verifying that it is blocked, as the breakout exercise does — belongs in every sandbox checklist, not just in the advanced one. And gVisor has its own answer to the same question, documented in its [networking guide](https://gvisor.dev/docs/user_guide/networking/): external networking can be disabled entirely with `--network=none` on the `runsc` runtime, leaving only a loopback provided by gVisor's own userspace network stack, which is the same default-deny instinct expressed in a different layer of the stack.

## Choosing between the options, and when each one earns its cost

With the mechanisms in hand, the choice becomes a decision under uncertainty, and the way to make it is to work down a short list of questions in order, because each question eliminates options, and the option that survives is usually the right one. The first question is the one from the threat model: who are you keeping out, and how hard will they try, because accidental harm and adversarial escape are different problems with different price tags. The second question is where the code runs and who operates the boundary: on your own host, on your own Kubernetes cluster, in the user's browser, or on someone else's cloud, because the cheapest isolation is the isolation someone else is already operating. The third question is what the code needs: which languages, which system calls, which network destinations, and how long it runs, because every mechanism in this chapter has a compatibility edge, and the wrong choice is usually discovered when a legitimate workload fails inside the sandbox rather than when an attack succeeds. And the fourth question is what the failure costs: a slow run, a failed run, a leaked secret, or a compromised host, because the cost of the sandbox has to be weighed against the cost of the incident it prevents, and a sandbox that is slower than the agent's patience will be bypassed, which is the worst outcome of all.

The comparison below is the summary of that decision process, and it is deliberately framed in terms of what each option protects against and what it costs, rather than a ranking, because there is no best sandbox, only a best sandbox for a given threat and a given budget.

| Option | What it protects against | What it costs you | Reach for it when |
| --- | --- | --- | --- |
| Local execution, no sandbox | Nothing. It is the baseline, not an option. | Nothing, until the incident. | Never for agent-generated code. It appears here only so you can recognise it when someone proposes it. |
| Plain container (Docker, `runc`) | Accidental harm: filesystem, process and network namespace separation; resource limits via cgroups. | A shared kernel: a kernel exploit escapes the sandbox. No limits unless you set them. | Your own agent, your own data, trusted users, and you have set limits, dropped capabilities, and blocked egress. This is the default for most teams. |
| Container with gVisor (`runsc`) | As above, plus the host kernel: system calls are served by a userspace kernel, so a kernel exploit must defeat two kernels that share no code. | Slower system-call-heavy work; some programs fail under `runsc`; no protection against side channels or in-sandbox exploits. | Untrusted or third-party code on shared infrastructure, especially multi-tenant, where the kernel boundary is the risk you cannot accept. |
| MicroVM (Firecracker, Kata Containers) | As above, plus a hardware boundary: each sandbox has its own guest kernel behind KVM virtualisation. | A kernel per sandbox: startup latency and memory overhead; needs KVM, so it does not run everywhere. | Multi-tenant platforms, regulated workloads, or any case where a container escape would be a breach of another customer's data. |
| Managed sandbox (E2B) | As above, operated for you, plus lifecycle: templates, pause and resume, and timeouts. | Per-run cost and less control; code and data leave your infrastructure unless you use bring-your-own-cloud. | You are building the agent, not the sandbox, and you want isolation without operating a fleet. |
| WebContainers (browser) | The browser's own sandbox; no server-side execution at all. | Node.js only; needs cross-origin isolation headers; runs on the user's machine. | Interactive demos, tutorials, and agent-built front ends the user previews and edits. |
| Docker-in-Docker / socket mount | Nothing, if the code is untrusted: it hands the code the host daemon. | `--privileged` mode or root-equivalent daemon access. | Only for trusted CI jobs that build images, on a dedicated disposable host — never for agent-generated code. |

Read the table as a ladder, not a menu, because the options compose: a container with gVisor and egress blocked and limits set is a stronger sandbox than any one of those controls alone, and a microVM with no limits and open egress is a weaker sandbox than a well-configured container, which is why the chapter keeps insisting on the checklist rather than the brand name. The decision that matters most is usually the boring one — limits, non-root user, read-only filesystem, no network by default, destroy after use — and the exotic mechanism is what you add when the boring controls are not enough for the threat you actually face.

That framing also answers the question of what to do on your own production stack, which for this course is Mastra on AWS Elastic Container Service with Amazon Bedrock. The honest mapping is that ECS already gives you the container layer, and your job is to make sure the layer is actually configured: tasks that run agent-generated code get their own task definition with CPU and memory limits, no access to the host, a non-root user, and no route to the internet except through a proxy or a NAT gateway with an allowlist, and the secrets the task can see are the ones that task needs and no others, because the metadata service and the task role are the two credentials an escaping agent reaches for first. When that is not enough — when the code is third-party, or the tenants are mutually untrusted — then the step up is not a bigger container, it is a different boundary: gVisor as the runtime, or a managed microVM sandbox called as a tool from the agent, with the agent's own host never executing the code at all. That separation, between the agent that decides and the sandbox that executes, is the architectural point of the whole chapter: the agent is the brain, the sandbox is the hands, and you do not let the hands reach the brain's credentials.

## The advanced-level interview angle

Interviewers do not ask about sandboxes because they want a list of products. They ask because the sandbox is where a candidate's security judgement becomes visible, and the difference between a good answer and a advanced-level answer is the difference between naming a tool and reasoning about a threat. So expect the question in one of three forms, and know what each form is really testing. The first form is the scenario: "your coding agent runs user-supplied Python; design the execution environment", and the interviewer is listening for the threat model before the mechanism, because a candidate who starts with "use E2B" has answered a different question from the one that was asked, while a candidate who starts with "who is the adversary, what can the code do, and what does it need" has shown the judgement the role requires. The second form is the trade-off: "why not just run it in Docker?", and the answer that earns the senior mark is the shared-kernel argument, stated precisely — a container is a process on the host kernel, a kernel vulnerability is an escape, and the mitigations are gVisor or a microVM — followed by the honest statement of when Docker is enough, because a candidate who cannot say when the cheaper option suffices is a candidate who will over-engineer every decision. And the third form is the failure: "your sandbox was bypassed; how do you find out, and what do you change?", which is testing whether you think in terms of detection and recovery rather than prevention alone, so the strong answer talks about audit logs of what the sandbox did, egress logs that show where it tried to go, resource metrics that show the fork bomb starting, and a lifecycle that destroys the sandbox and rotates any credential it could have seen, because a sandbox you cannot observe is a sandbox you cannot trust.

There are two traps to avoid, and both are common enough that interviewers set them deliberately. The first is claiming a mechanism you do not have: saying "containers are isolated" without mentioning the shared kernel, or "we block the network" without saying where the block is enforced, or "we set limits" without saying which limits and what happens when they are hit. The second is the opposite error, which is reaching for the strongest mechanism for every workload, because an experienced engineer is expected to know that a microVM per run for a trusted internal agent is not security, it is waste, and the judgement is in matching the boundary to the threat rather than maximising the boundary. If you can walk an interviewer through the five harms, name the control that answers each one, explain why a container is enough for your own agent and not enough for a stranger's code, and describe how you would prove the boundary by attacking it, you have answered the question at the level this chapter is aiming at, and the exercises below are the rehearsal for exactly that conversation.

## What to do next

Work the exercises in order, because they are designed as a progression: first you build the sandbox and prove its limits hold, then you attack it and watch the attacks fail, then you open exactly one door in the network and prove that only that door opens. If you only do one exercise, do the breakout attempt, because a sandbox you have watched fail an attack is a sandbox you understand, and a sandbox you have only read about is a configuration file. Then read Chapter 7, which takes the other half of the problem — the prompt injection and tool-poisoning attacks that try to get malicious code into the sandbox in the first place — because the sandbox and the guardrail are two halves of the same defence, and neither is complete without the other.
