# Chapter 01 — Agent Architecture & State Machines

## The idea in plain words

Every agent you have ever shipped is, underneath the model calls, a state machine: it sits in some state, something happens, and it moves to a new state. The question this chapter answers is not how to draw that machine — drawing it is the easy part — but how to choose its shape, and how to make sure it survives the night. A support agent that triages a ticket, drafts a reply, and waits for a manager's approval is a state machine whether you wrote it as a straight-line script, as a graph, or as a loop that lets the model decide what happens next, and the difference between those three shapes is the difference between a system you can reason about at 2 a.m. and one you can only hope about. So this chapter starts where production actually starts, which is with a crash: your container is killed halfway through a run, the process is gone, the memory is gone, and the only question that matters is what comes back. If the answer is "everything, exactly where it stopped", you built a durable system; if the answer is "the run starts over, and the customer gets two refunds", you built a demo that happened to survive its first week.

That crash is the thread that ties the whole chapter together, because each of the three shapes answers it differently, and the right shape for a job is mostly decided by how much of the run you can afford to lose and how much of the run's future you can predict before it starts. A directed acyclic graph — a directed acyclic graph (DAG) — is a pipeline with no way back: each step runs once, edges only move forward, and every path through the graph can be listed before the run begins. A cyclic workflow adds a back edge, so a step can be retried or a draft can be revised, which means the graph can loop — and therefore needs a guard, a counter or a verdict that guarantees the loop ends. And a free-form agent loop hands the next-step decision to the language model (LLM) itself at every step, so the path is not drawn in advance at all: the model reads the goal and the history, picks a tool, observes the result, and decides what to do next, which is the most flexible shape and also the one whose behaviour you can only characterise statistically, never enumerate. Anthropic's "Building effective agents" draws exactly this line, and it is worth holding on to throughout the chapter: in a workflow, your code decides the sequence and the model fills in each step, whereas in an agent, the model decides the sequence at run time ([Anthropic, "Building effective agents"](https://www.anthropic.com/engineering/building-effective-agents)).

## The mechanism, step by step

### Choosing the shape: who decides what happens next

Start with the simplest question, which is also the one Anthropic's essay opens with: do you need a multi-step system at all, and if you do, who should own the next-step decision? If the task decomposes cleanly into fixed subtasks — extract the order, validate it, charge the card, send the receipt — then a DAG is the right shape, because the sequence is known before the run starts and the only thing the model contributes is the content of each step. Prompt chaining is the LLM-flavoured version of the same idea: each call processes the output of the previous one, with a programmatic check, a gate, on the intermediate steps ([Anthropic, "Building effective agents"](https://www.anthropic.com/engineering/building-effective-agents)). A DAG's great virtue is that it is enumerable: you can list every path, test every path, and prove the run terminates, because there are no cycles for it to get stuck in. Its great limit is the mirror image: it cannot retry, revise, or reconsider, so anything that fails has to be handled by a branch you drew in advance, which in practice means it gets escalated or dropped.

The moment a task needs a second attempt — a draft that fails review, a query that returns nothing useful, a tool call that times out — the DAG stops being enough, and the honest move is to add a cycle rather than to pretend the retry is a new pipeline. A cyclic workflow is a graph with at least one back edge, and LangGraph is the canonical framework for building one in Python: you define a state schema, add nodes that are plain functions, connect them with plain and conditional edges, and compile the graph, and the conditional edge is where the cycle's guard lives ([LangChain Academy, "Introduction to LangGraph"](https://academy.langchain.com/courses/intro-to-langgraph)). The guard is not decoration but the termination proof — a maximum attempt count, a reviewer verdict, a budget — and the discipline is that the guard must be owned by code, not by the model, because a model that is asked whether its own work is good enough is grading its own homework. The code in this chapter makes the comparison concrete: `code/01_dag_vs_cycle.py` runs the same four-ticket triage job through all three shapes with a deterministic mock reviewer, and the DAG escalates the one ticket that needs a second draft while the cyclic graph resolves it, which is the whole argument in miniature.

The free-form loop is what you reach for only when the number and order of steps genuinely cannot be predicted — a coding agent resolving a bug report, an investigation that may need three tool calls or thirty — and the price of that flexibility is that you lose enumerability altogether. You cannot list the paths, so you cannot test them all; you can only bound the loop with a hard step cap and a hard token and cost budget owned by code, and characterise the behaviour with evaluations over many runs instead of proofs over the graph. That is also why the loop's cost behaves differently: each step re-sends the accumulated history, so the input tokens grow with the square of the step count, and a run that wanders is not merely slow but quadratically expensive. The decision framework, then, is a ladder rather than a menu: start with a single call, move to a DAG when the steps are fixed, add a cycle when a step needs a second chance, and promote the job to a free-form loop only when the path itself is unknowable in advance — and at every rung, ask what evidence would justify climbing to the next one, because each rung buys flexibility with predictability, and predictability is what lets you sleep.

### Designing state that survives a crash

Once the shape is chosen, the next question is what the run remembers, and the governing idea is that the durable record — not the process, not the context window — is the agent. Mastra's durable-agents writing puts it crisply: a long-running agent is a durable record that short-lived processes take turns with, and the model loop, the sandbox where tools run, and the record itself are three separate things, so that any one of them can be killed and replaced without losing the run ([Mastra, "What are durable AI agents?"](https://mastra.ai/blog/what-are-durable-ai-agents)). That separation drives every design rule that follows. State must be plain data — strings, numbers, lists, dictionaries — serialised as JavaScript Object Notation (JSON), because a checkpoint is a snapshot that has to be written to a database, read back by a different process, possibly on a different machine, possibly after a deploy. The moment state holds a live handle, a model client, an open file, or a pickled object, it can no longer be restored anywhere except the process that created it, which defeats the purpose. And state must stay small, because every byte in state is written at every checkpoint: a 50-megabyte document belongs in object storage with only its key in state — the claim-check pattern — and `code/03_state_serialisation.py` demonstrates the difference, where a snapshot holding a claim check for a 50-megabyte attachment is still 240 bytes of JSON, measured locally.

State also needs a schema version, because the code that reads a checkpoint will not always be the code that wrote it. A deploy halfway through a long-running job means new code resumes old state, and without a version field the new code silently misreads the old shape — the most common way a durable system corrupts itself. The rule is therefore to stamp every snapshot with a version, to migrate old versions forward with pure functions that are tested against real snapshots captured in production, and to fail loudly on a version newer than the code, since that means the code is behind the data and guessing would be worse than stopping. Secrets deserve their own rule on top of that: a credential in a checkpoint ends up in every backup, replica, and log that the checkpoint touches, so serialisation should refuse to write any field whose name looks like a secret, and the code in this chapter does exactly that. Finally, state should distinguish two things that are constantly confused: execution state, which answers "where in the work are we" and is scoped to one run, and memory, which answers "what does the agent know" and is scoped to a user or a thread across runs. Mastra keeps them in separate storage domains for exactly this reason, and conflating them is how a resume leaks one customer's ticket into another customer's run ([Mastra, "What are durable AI agents?"](https://mastra.ai/blog/what-are-durable-ai-agents)).

### Checkpointing and recovery: snapshots versus replay

With state designed, there are two fundamentally different ways to make a run survive a crash, and the choice between them is the chapter's second big decision. The first is snapshot checkpointing, which is what LangGraph and Mastra both do: after each step — at each super-step boundary, one tick of the graph in which every scheduled node runs — the runtime writes a snapshot of the whole state to a checkpointer, keyed by a thread identifier, and a fresh process resumes by loading the latest snapshot and continuing from there ([LangGraph checkpointers documentation](https://langchain-ai.github.io/langgraph/reference/checkpoints/)). The checkpointers form a ladder of durability: the in-memory saver is for tests and forgets everything when the process exits, the SQLite saver survives a process restart on one machine, and the PostgreSQL saver is the production choice. Microsoft's Agent Framework works the same way, creating a checkpoint at the end of each superstep that captures every executor's state, the pending messages, and the shared state, with in-memory, file, and Azure Cosmos DB storage behind one protocol ([Microsoft Learn, "Workflows — Checkpoints"](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)). The crucial subtlety, and the one that bites in production, is that a checkpoint is written at a super-step boundary and never in the middle of a node — so the node that was running when the process died runs again from its first line on resume, and any side effect it performed before the checkpoint is performed twice unless the node is idempotent. The receipt node in `code/02_langgraph_checkpoint_resume.py` is idempotent by design, recording the receipt against the ticket identifier and skipping duplicates, and the exercise that removes that guard is the one that teaches the lesson permanently.

The second way is durable execution by replay, which is Temporal.io's model, and it inverts the problem: instead of snapshotting state, Temporal records the history of everything that happened — the event history — and rebuilds state by re-running the workflow code against that history ([Temporal, "Understanding Temporal"](https://docs.temporal.io/evaluate/understanding-temporal)). The workflow is ordinary code with loops and conditionals, but it must be deterministic, because replay only reconstructs the right state if the code makes the same decisions given the same history; anything non-deterministic — the wall clock, a random number, a network call — is forbidden in workflow code and must live in an activity, whose result is recorded in the history and returned verbatim on replay. The payoff for that discipline is stronger than snapshotting: a crashed activity is never re-run at all, since its recorded result is replayed, and a workflow can sleep on a durable timer for months without holding a process open. The price is the determinism contract itself, plus the event history's hard limits and an extra service to operate, and `code/04_temporal_workflow.py` lets you feel both sides — a local simulator that replays a JSON event log with no server, and the same workflow definition ready to run against a real Temporal server. There is also a third, quieter form of recovery that both models support and that Chapter 8 will develop fully: time travel, the ability to list a thread's checkpoints, rewind to an earlier one, edit the state there, and fork a new path from it, which turns a checkpoint history into a debugging tool as well as a safety net ([LangChain Academy, "Introduction to LangGraph"](https://academy.langchain.com/courses/intro-to-langgraph)).

### Putting it together: the decision framework

So the chapter's framework, stated as one flow, goes like this: first, name the unit of progress you refuse to lose — a turn, a step, or a pause inside a step — because that decides the granularity of the durable record, and Mastra's account of the three granularities is the clearest statement of the choice ([Mastra, "What are durable AI agents?"](https://mastra.ai/blog/what-are-durable-ai-agents)). Then choose the shape by who owns the next step: a DAG when the path is fixed, a cyclic graph when a step needs a second chance under a code-owned guard, a free-form loop only when the path is unknowable, with a hard cap and budget owned by code. Then design the state as small, plain, versioned JSON with claim checks for large payloads and no secrets, and choose the recovery mechanism by how much you can afford to redo: snapshot checkpointing when re-running the interrupted step is cheap and safe, durable execution by replay when re-running it is expensive, charged, or impossible. And finally, write down the failure modes before you ship — the kill between a side effect and its checkpoint, the deploy over a running workflow, the checkpoint that grows until it is slower to write than the work it protects — because each of them has a named defence in this chapter, and a system whose failure modes are named is a system that can be operated, whereas one whose failure modes are merely hoped away is a system waiting for its first 2 a.m.

## The numbers that matter

Every number here traces to a source verified live on 18 November 2026, or is labelled as measured locally by running the chapter's own code.

Temporal.io's event history is capped at 51,200 events or 50 megabytes per workflow execution, with warnings from 10,240 events or 10 megabytes, and a single payload is capped at 2 megabytes with an event-history transaction capped at 4 megabytes ([Temporal, "System limits"](https://docs.temporal.io/cloud/limits)). Those caps are the reason a long-running agent loop cannot simply run forever on Temporal: each activity adds roughly six events, so a loop that never compacts its history will hit the ceiling, and the designed escape is Continue-As-New, which closes the run and starts a fresh history carrying forward only the state you choose. The same caps are also the reason payloads must be claim checks: a transcript passed whole into every activity lands in the history permanently, so history grows toward the cap far faster than the step count suggests. Mastra's side of the ledger is the opposite scale: a suspended order workflow's whole snapshot serialised to 1,059 bytes of JSON, with a per-step map reading `reserve-inventory: success` and `human-approval: suspended` ([Mastra, "What are durable AI agents?"](https://mastra.ai/blog/what-are-durable-ai-agents)). That number is the argument for keeping state small in one figure — a checkpoint that small is cheap to write at every step, cheap to read back on resume, and small enough that keeping a long history of them is not a storage decision at all.

The chapter's own measurements, run locally while writing it, put concrete numbers on the LangGraph path. With LangGraph 1.2.22 and langgraph-checkpoint-sqlite 3.1.3, a four-ticket triage run through `code/02_langgraph_checkpoint_resume.py` produced 25 checkpoints — roughly six per ticket, one per super-step — and the SQLite file was 128 kibibytes after the full run and 4 kibibytes after a kill two super-steps in. Resuming the killed run from the same thread identifier in a fresh process reprocessed zero completed tickets and resolved all four, which is the acceptance test the exercises demand rather than a claim to take on trust. And the serialisation file shows the same smallness from the other side: a one-ticket state snapshot is 198 bytes of JSON, and adding a claim check for a 50-megabyte attachment grows it only to 240 bytes. For scale, the syllabus this chapter's shape is borrowed from — LangChain Academy's "Introduction to LangGraph" — runs to 55 lessons and about six hours of video, which is a useful calibration of how much depth the graph model repays once you commit to it ([LangChain Academy, "Introduction to LangGraph"](https://academy.langchain.com/courses/intro-to-langgraph)).

## The advanced-level interview angle

In an interview, this chapter is not tested by asking you to recite an API; it is tested by handing you a failure and asking what you would have built differently. The question will sound like: "Your agent charged a customer twice after a deploy — walk me through the design that let that happen." The strong answer starts from the kill window, not from the framework: a side effect was performed, and the record of it was not durable before the process died, so the resumed run performed it again, and the fix is an idempotency key on the side effect plus a checkpoint boundary that sits after the recording of the result rather than before it. Or the question will be a choice: "You have a ten-step onboarding flow with a human approval in the middle that can take two days — LangGraph, Temporal, or a plain loop?" The strong answer names the decision variables before picking: the approval is a durable pause, so you need a snapshot or a history that outlives the process; the steps are fixed, so a DAG or a cyclic graph beats a free-form loop; the approval arrives days later across deploys, so the state must be versioned and the node identities stable; and if the steps include charged actions, replay beats snapshotting because a crashed charge must never re-run. What marks the answer as advanced-level is not the framework name but the failure modes volunteered unprompted: the checkpoint that grows with the transcript, the deploy that breaks replay determinism, the cycle without a guard, the loop whose cost grows with the square of its steps, and the resume that leaks one tenant's state into another's because execution state and memory were stored in the same bucket. If you can name the failure mode and its defence in the same breath, you are answering as someone who has operated the system, not merely read about it.

## How this maps to Mastra and Amazon Bedrock

The reader's production stack is Mastra on Amazon Web Services Elastic Container Service with Amazon Bedrock, and the mapping is closer than the Python code in this chapter might suggest. Mastra's workflows are the DAG and cyclic shapes of this chapter in TypeScript: steps composed with `.then()`, `.branch()`, and `.dowhile()`, with `suspend()` and `resume()` providing the durable pause — suspension writes a snapshot to the configured storage, keyed by run identifier, and resuming re-executes the suspended step with typed resume data rather than restoring a call stack ([Mastra, "Suspend and resume"](https://mastra.ai/docs/workflows/suspend-and-resume)). The mapping to the chapter's rules is direct: a Mastra workflow snapshot is the LangGraph checkpoint under another name, the same small-plain-versioned JSON discipline applies, and the same warning holds — a crash mid-step can leave a run stuck in `running`, so the step that was in flight runs again and must be idempotent. Mastra's durable-agent API, currently in beta, wraps the agent loop itself in a workflow so that a long-running loop gets the same recovery contract, which is the chapter's free-form loop with a durable record underneath it rather than beside it ([Mastra, "What are durable AI agents?"](https://mastra.ai/blog/what-are-durable-ai-agents)). On the model side, the language model calls in this chapter's activities are exactly the calls a Mastra agent makes through Amazon Bedrock, whose agents product orchestrates a foundation model with action groups and knowledge bases ([Amazon Bedrock, "Create and configure agent manually"](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-create.html)), and the tools those calls invoke are, in the reader's stack, Model Context Protocol (MCP) tools — the open protocol for connecting a language-model application to external tools and data ([Model Context Protocol, "Specification"](https://modelcontextprotocol.io/specification/2026-07-28)). The architectural point carries across unchanged: whether the tool is a Bedrock action group or an MCP server, it is an activity, not workflow code — it is called from the orchestrated step, its result is recorded in the durable record, and it is the thing that must be idempotent, because it is the thing that touches the world. Chapter 2 will build the MCP side from scratch; this chapter is the reason the MCP side needs the discipline it will teach.
