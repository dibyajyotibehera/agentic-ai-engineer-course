# Chapter 01 — Agent Architecture & State Machines

## The idea in plain words

Every agent you have ever shipped is, underneath the model calls, a state machine: it sits in some state, something happens, and it moves to a new state. Drawing the state diagram is the easy part: states as boxes, transitions as arrows. This chapter is about the two decisions that actually matter. First, the control-flow topology: a straight-line script that runs the same steps in the same order, a directed graph in which each state names the next states it can move to, or a free-form loop in which the model chooses the next step each time round. Second, durability: making the run survive a crash, so that when the container is killed halfway through, the run resumes exactly where it stopped instead of starting over. A support agent that triages a ticket, drafts a reply, and waits for a manager's approval is a state machine under any of those three topologies, and the difference between them is the difference between a system you can reason about at 2 a.m. and one you can only hope about. So this chapter starts where production actually starts, which is with a crash: your container is killed halfway through a run, the process is gone, the memory is gone, and the only question that matters is what comes back. If the answer is "everything, exactly where it stopped", you built a durable system; if the answer is "the run starts over, and the customer gets two refunds", you built a demo that happened to survive its first week.

That crash is the thread that ties the whole chapter together, because each of the three shapes answers it differently, and the right shape for a job is mostly decided by how much of the run you can afford to lose and how much of the run's future you can predict before it starts. A directed acyclic graph — a directed acyclic graph (DAG) — is a pipeline with no way back: each step runs once, edges only move forward, and every path through the graph can be listed before the run begins. A cyclic workflow adds a back edge, so a step can be retried or a draft can be revised, which means the graph can loop — and therefore needs a guard, a counter or a verdict that guarantees the loop ends. And a free-form agent loop hands the next-step decision to the language model (LLM) itself at every step, so the path is not drawn in advance at all: the model reads the goal and the history, picks a tool, observes the result, and decides what to do next, which is the most flexible shape and also the one whose behaviour you can only characterise statistically, never enumerate. Anthropic's "Building effective agents" draws exactly this line, and it is worth holding on to throughout the chapter: in a workflow, your code decides the sequence and the model fills in each step, whereas in an agent, the model decides the sequence at run time ([Anthropic, "Building effective agents"](https://www.anthropic.com/engineering/building-effective-agents)).

## The harness in five subsystems

Before the crash, before the topology, before any of the machinery this chapter teaches, there is one framing decision that makes everything else fall into place, and it is to stop thinking of the agent as the system and start thinking of the harness as the system, with the agent as one component inside it. A harness is the code around the model that turns a language model that can answer questions into an agent that can finish work: it is the scaffolding that gives the model its instructions, keeps its state, checks its output, bounds what it may touch, and carries the run from its first step to its last. Anthropic's writing on harnesses for long-running agents makes the same point from the other side, which is that the model is the reasoning engine and everything else — the loop, the tools, the memory, the checks — is engineering around it ([Anthropic, "Effective harnesses for long-running agents"](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). And once you see the harness as the system, you can name its five subsystems, which this course spreads across its chapters but never gathers in one place, so here they are together, because every design decision in this chapter is a decision about one of them.

The first subsystem is instructions, which is the durable record of what the agent is supposed to do and how it is supposed to do it: the system prompt, the coding standards, the tool-use rules, the definition of done. A concrete example is a file that tells a coding agent to run the test suite before claiming a fix is complete and to never edit generated files, because instructions that live only in a chat message are lost the moment the run restarts, while instructions that live in a file the harness loads on every start survive every crash. The second subsystem is state, which is the durable record of where the run is: the feature list, the checkpoint, the conversation history, the half-finished draft. A support agent that has triaged three of four tickets keeps that progress in state, so a crash after the third ticket costs one ticket of rework rather than four. The third subsystem is verification, which is the machinery that decides whether the agent's work is good enough: a test suite, a reviewer, a type checker, a linter. Verification is what turns a claim into a fact, because an agent that says a bug is fixed has only made a claim, while an agent whose fix passes the failing test has produced evidence. The fourth subsystem is scope, which is the boundary around what the agent may touch: which directories it may edit, which tools it may call, which secrets it may never see. Scope is the subsystem that keeps a coding agent from rewriting the billing code when it was asked to fix a typo in the help text. The fifth subsystem is lifecycle, which is the machinery that carries a run from its first step to its last: starting it, pausing it for a human approval, resuming it after a crash, and knowing when it is finished. Lifecycle is the subject of most of this chapter, from the initialization phase that checks the environment before the agent starts work, through checkpointing and recovery, to the question of when a run is done rather than merely stopped.

The reason to name the five together is that they fail together, and the most instructive comparison in the harness literature shows why. Anthropic ran the same retro-game task twice with Opus 4.5: the bare model, given the task with no harness at all, finished in 20 minutes for $9, while the harnessed version, with a full loop, tools, verification and checkpoints, took 6 hours and cost $200 ([Anthropic, "Harness design for long-running apps"](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The lesson is that each subsystem you add buys capability with time and cost, so the harness is a set of deliberate trade-offs rather than a pile of features, and the five names give you the vocabulary to make those trade-offs explicitly: when a run goes wrong, you can ask whether the instructions were unclear, the state was lost, the verification was missing, the scope was too wide, or the lifecycle had no way to recover, and that question is the start of every real fix.

## The mechanism, step by step

### Before the first step: the initialization phase

Every run has a moment before the agent does any work, and that moment deserves a name, because it is where the cheapest failures in the whole system are caught. The initialization phase is the short, code-owned sequence that runs when a harness starts and before the model is called for the first time: it checks that the environment the agent is about to work in is healthy, that everything the run will need is present and reachable, and that the run's own record is ready to receive progress. Think of it as the pre-flight check on an aircraft, which is a useful comparison because the logic is the same: the check is boring, it is the same every time, it is owned by a checklist rather than by judgement, and skipping it is how a small, obvious problem becomes an expensive one halfway through the flight.

What the phase checks depends on the system, but the shape is always the same, and a concrete version for a coding agent makes the pattern visible. First, the environment itself: the working directory exists, the repository is checked out at the expected revision, the tools the agent will call are installed and on the path, and the model endpoint answers a cheap probe. Second, the credentials and configuration: the keys the run needs are present, they are the right keys for this environment rather than a production key in a development run, and the configuration files parse. Third, the durable record: the state file or database the run will checkpoint into is writable, the feature list the run will work from is present and well-formed, and there is no leftover lock or half-finished run claiming the same work. The course's `templates/init.sh` is a starter version of exactly this sequence, written as a shell script the harness runs before the first model call, and the discipline is to extend it for your own system rather than to trust that the environment you tested in is the environment you deployed to.

The reason initialization belongs in the harness rather than in the agent is that the agent cannot check its own foundations, because every check it performs already assumes the foundations are sound. A model that is asked whether its tools work will happily call a broken tool and report the error as a finding, and a model that is asked whether its credentials are valid will try them and burn a rate-limit budget discovering they are not. Initialization is also where the run's first failure mode is cheapest to fix, because nothing has been attempted yet: a missing tool at minute zero is a five-minute fix, while the same missing tool discovered after an hour of agent work is an hour of wasted tokens plus a run whose state now has to be unwound. And the phase has one more job, which is to record the starting conditions in the durable record — the environment version, the tool versions, the configuration that was in force — so that when a run behaves strangely three hours later, the operator can answer the first debugging question, which is what was different about this run, from the record rather than from memory.

### Choosing the shape: who decides what happens next

Start with the simplest question, which is also the one Anthropic's essay opens with: do you need a multi-step system at all, and if you do, who should own the next-step decision? If the task decomposes cleanly into fixed subtasks — extract the order, validate it, charge the card, send the receipt — then a DAG is the right shape, because the sequence is known before the run starts and the only thing the model contributes is the content of each step. Prompt chaining is the LLM-flavoured version of the same idea: each call processes the output of the previous one, with a programmatic check, a gate, on the intermediate steps ([Anthropic, "Building effective agents"](https://www.anthropic.com/engineering/building-effective-agents)). A DAG's great virtue is that it is enumerable: you can list every path, test every path, and prove the run terminates, because there are no cycles for it to get stuck in. Its great limit is the mirror image: it cannot retry, revise, or reconsider, so anything that fails has to be handled by a branch you drew in advance, which in practice means it gets escalated or dropped.

The moment a task needs a second attempt — a draft that fails review, a query that returns nothing useful, a tool call that times out — the DAG stops being enough, and the honest move is to add a cycle rather than to pretend the retry is a new pipeline. A cyclic workflow is a graph with at least one back edge, and LangGraph is the canonical framework for building one in Python: you define a state schema, add nodes that are plain functions, connect them with plain and conditional edges, and compile the graph, and the conditional edge is where the cycle's guard lives ([LangChain Academy, "Introduction to LangGraph"](https://academy.langchain.com/courses/intro-to-langgraph)). The guard is not decoration but the termination proof — a maximum attempt count, a reviewer verdict, a budget — and the discipline is that the guard must be owned by code, not by the model, because a model that is asked whether its own work is good enough is grading its own homework. The code in this chapter makes the comparison concrete: `code/01_dag_vs_cycle.py` runs the same four-ticket triage job through all three shapes with a deterministic reviewer by default, and the DAG escalates the one ticket that needs a second draft while the cyclic graph resolves it, which is the whole argument in miniature. The deterministic reviewer is deliberate: the comparison is only exact if every shape faces the same verdicts, so the default run needs no model API key, and passing `--live` replaces the stand-ins with real model calls — real drafts, a real model judging them, a real model choosing the free-form loop's next step — with the same outcomes and the token and cost totals printed at the end. The same two modes run through the rest of the chapter: the LangGraph demo takes `--live` for real drafting and reviewing, and the Temporal simulator takes `--live` to record real model results in its event log and replay them on the second run with no new model calls.

The free-form loop is what you reach for only when the number and order of steps genuinely cannot be predicted — a coding agent resolving a bug report, an investigation that may need three tool calls or thirty — and the price of that flexibility is that you lose enumerability altogether. You cannot list the paths, so you cannot test them all; you can only bound the loop with a hard step cap and a hard token and cost budget owned by code, and characterise the behaviour with evaluations over many runs instead of proofs over the graph. That is also why the loop's cost behaves differently: each step re-sends the accumulated history, so the input tokens grow with the square of the step count, and a run that wanders is not merely slow but quadratically expensive. The decision framework, then, is a ladder rather than a menu: start with a single call, move to a DAG when the steps are fixed, add a cycle when a step needs a second chance, and promote the job to a free-form loop only when the path itself is unknowable in advance — and at every rung, ask what evidence would justify climbing to the next one, because each rung buys flexibility with predictability, and predictability is what lets you sleep.

### From a single loop to a graph: graph engineering

The topology section above presents the directed graph as one of three shapes, and that is the right place to start, but a graph that runs a real workload needs more engineering than a shape name, because the moment a system has more than a handful of steps, the graph itself becomes a piece of software with its own design problems. Graph engineering is the discipline of building that piece of software well, and it starts with the four parts every graph is made of. A node is a unit of work, a plain function that takes the shared state and returns an update to it: triage a ticket, draft a reply, send a receipt. An edge is a permitted move from one node to another, and a conditional edge is a move whose destination is chosen at run time by code, which is where routing decisions live. The shared state is the single record every node reads and writes, the durable JavaScript Object Notation (JSON) record this chapter's state section describes, and the reason it is shared rather than passed along edges is that a node late in the graph often needs something an early node produced, and threading it through every intermediate node is how a graph becomes unreadable. And routing is the rule that decides, at each branching point, which edge to follow, which is the graph's decision logic made explicit rather than hidden inside a node's code.

Building a first graph is a sequence of six steps, and the order matters because each step only makes sense once the previous one exists. First, name the nodes, which means listing the units of work the job actually decomposes into, and the discipline here is that a node should do one thing and do it completely, because a node that does two things is a node whose failure you cannot attribute. Second, draw the edges, which means writing down every permitted move, including the moves you hope never happen, such as the edge to the escalation node. Third, define the shared state schema, which means deciding the fields every node may read and write, stamping it with a version, and writing the reducer rules that say how concurrent updates combine. Fourth, put the guard on every cycle, which means the maximum attempt count or reviewer verdict that guarantees each loop ends, owned by code. Fifth, make the nodes idempotent, because a graph that resumes after a crash re-runs the node that was in flight, and a node that sends a receipt twice is a node that was never finished. Sixth, add the observability that makes the graph operable, which means logging every transition with the node name and the state version, so that when a run goes wrong the operator can read the path it took rather than reconstructing it from a transcript.

That sequence is worth the effort when the work has structure a single loop cannot express, and it is worth naming the two comparisons that decide whether it is. A graph differs from a workflow in the sense Anthropic draws the line, because a workflow is a fixed pipeline in which code decides the sequence, while a graph is the general case that can express a pipeline, a cycle, and a conditional branch, so the honest way to think about it is that a workflow is a graph with no cycles and no conditional edges, and a graph is what you reach for when the work needs either. A graph differs from a free-form loop in the opposite direction, because in a loop the model chooses the next step every time round, while in a graph the permitted moves are drawn in advance and only the choice among them is made at run time, so the graph gives up some of the loop's flexibility and buys back the ability to enumerate the paths, test them, and prove the run ends. And the price of that purchase is the orchestration tax, which is the code you write and maintain to define nodes, edges, state schemas and guards, the extra latency of passing state through the runtime at every step, and the debugging cost of a system whose behaviour is spread across a diagram rather than sitting in one function. The tax is real, and it is why the chapter's ladder says to start with a single call and climb only on evidence, but it is also the tax that buys the properties a production system needs, so the judgement call is a concrete one: draw the graph when the job has more than a few steps, when a step needs a second chance under a guard, when different inputs must take different paths, or when the run must survive a crash and resume mid-graph, and keep the job as a script or a loop when none of those is true, because a graph drawn for a job that does not need one is complexity that will be paid for in maintenance and never repaid in reliability.

### Loop engineering: running the loop unattended

The free-form loop is the most flexible shape in this chapter, and it is also the shape most likely to be left running unattended, which is where loop engineering begins, because a loop that runs while nobody is watching needs machinery a loop that runs once in a notebook does not. Loop engineering is the harness work of turning a loop into a service, and it has three patterns, each named for what triggers the next iteration. A goal loop keeps running until a stated goal is met, which is the pattern of a coding agent that works through a feature list until every feature passes verification, and its defining problem is knowing when the goal is actually met rather than merely claimed, which is why goal loops are always paired with the verification subsystem. A timed loop runs on a schedule, which is the pattern of an agent that sweeps a queue every hour or re-checks a dashboard every morning, and its defining problem is overlapping runs, because a loop that takes longer than its interval will start a second copy of itself unless the harness holds a lock or skips the tick. A maker-checker loop separates generation from evaluation, which is the pattern of one agent drafting and a second agent, or a deterministic check, reviewing, and its defining problem is that the checker must be genuinely independent, because a checker that shares the maker's assumptions will approve the maker's mistakes.

Those three patterns are built from the same six primitives, and naming them is useful because each one is a component you can build, test and replace separately. Automations are the triggers that start a loop, a schedule, a webhook, which is a Hypertext Transfer Protocol (HTTP) notification another system sends when something happens, or a queue message, and they are the answer to the question of who starts the work. Worktrees are isolated copies of the code the agent works in, so that a loop running in one worktree cannot corrupt the work of a loop running in another, and they are the answer to the question of where the work happens. Skills are packaged capabilities the agent can invoke, a tested procedure for a recurring task, and they are the answer to the question of how the work is done well. Connectors are the typed interfaces to external systems, the issue tracker, the repository, the messaging tool, and they are the answer to the question of how the agent reaches the world. Sub-agents are the smaller agents a loop delegates to, a researcher that gathers context or a reviewer that checks a draft, and they are the answer to the question of how the work is divided. External state is the durable record outside the model that the loop reads and writes, the feature list, the checkpoint store, the evaluation log, and it is the answer to the question of what survives when the process dies.

The separation that matters most among those six is the one between the generator and the evaluator, because it is the difference between a loop that improves and a loop that merely spins. The generator is the agent that does the work, and the evaluator is the check that decides whether the work is good enough, and the rule is that the two must not be the same agent grading its own output, which this chapter already states for the cycle guard and which holds with even more force in a loop that runs unattended. A concrete example makes the failure visible: a coding loop that asks the same agent whether its fix is correct will approve its own broken fix, and the loop will mark the feature passing and move on, while a loop that runs the test suite as its evaluator will fail the same fix, keep the feature active, and try again, which is the loop doing its job. The scale of what these loops can do when they are engineered rather than merely launched is visible in OpenAI's account of running coding agents on a million-line codebase, where the harnessed agents produced roughly 1,500 pull requests over five months ([OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/)) — a volume no human team sustains by hand, and also a volume that is only safe because each of those pull requests passed through verification rather than straight into the codebase. The question loop engineering asks of every loop, then, is the same one this chapter asks of every shape: who decides the loop ends, what evidence decides it, and what happens to the work when the loop is killed halfway through, because a loop that cannot answer those three questions is a service in name only, a script that someone forgot to stop.

### Designing state that survives a crash

Once the shape is chosen, the next question is what the run remembers, and the governing idea is that the durable record — not the process, not the context window — is the agent. Mastra's durable-agents writing puts it crisply: a long-running agent is a durable record that short-lived processes take turns with, and the model loop, the sandbox where tools run, and the record itself are three separate things, so that any one of them can be killed and replaced without losing the run ([Mastra, "What are durable AI agents?"](https://mastra.ai/blog/what-are-durable-ai-agents)). That separation drives every design rule that follows. State must be plain data — strings, numbers, lists, dictionaries — serialised as JavaScript Object Notation (JSON), because a checkpoint is a snapshot that has to be written to a database, read back by a different process, possibly on a different machine, possibly after a deploy. The moment state holds a live handle, a model client, an open file, or a pickled object, it can no longer be restored anywhere except the process that created it, which defeats the purpose. And state must stay small, because every byte in state is written at every checkpoint: a 50-megabyte document belongs in object storage with only its key in state — the claim-check pattern — and `code/03_state_serialisation.py` demonstrates the difference, where a snapshot holding a claim check for a 50-megabyte attachment is still 240 bytes of JSON, measured locally.

State also needs a schema version, because the code that reads a checkpoint will not always be the code that wrote it. A deploy halfway through a long-running job means new code resumes old state, and without a version field the new code silently misreads the old shape — the most common way a durable system corrupts itself. The rule is therefore to stamp every snapshot with a version, to migrate old versions forward with pure functions that are tested against real snapshots captured in production, and to fail loudly on a version newer than the code, since that means the code is behind the data and guessing would be worse than stopping. Secrets deserve their own rule on top of that: a credential in a checkpoint ends up in every backup, replica, and log that the checkpoint touches, so serialisation should refuse to write any field whose name looks like a secret, and the code in this chapter does exactly that. Finally, state should distinguish two things that are constantly confused: execution state, which answers "where in the work are we" and is scoped to one run, and memory, which answers "what does the agent know" and is scoped to a user or a thread across runs. Mastra keeps them in separate storage domains for exactly this reason, and conflating them is how a resume leaks one customer's ticket into another customer's run ([Mastra, "What are durable AI agents?"](https://mastra.ai/blog/what-are-durable-ai-agents)).

### The feature list: progress as a durable record

State, as this chapter has described it so far, is the record of where a run is, and the feature list is the most useful form that record takes when the run is a project rather than a single task. A feature list is a plain file, usually JavaScript Object Notation (JSON), that names every unit of work the agent has to complete, and each feature in it is a triple: a behaviour description that says what done looks like in plain words, a verification command that proves it, and the current state of the feature. The triple matters because each part does a job the others cannot: the description tells the agent what to build, the verification command tells the harness whether the build succeeded, and the state tells everyone — the agent, the operator, the next process that resumes the run — how far along the work is. A concrete example is a feature that reads "the triage agent retries a failed draft up to three times", with the verification command `pytest tests/test_retry.py`, and a state of `active`, which together say what to do, how to prove it, and where it stands, without any of those three living in the model's memory where a crash would erase them.

The state of a feature moves through a four-state machine, and the machine is the heart of the idea, because it is the harness that moves it and never the agent. A feature starts as `not_started`, moves to `active` when work on it begins, moves to `blocked` when something outside the agent's control stops progress — a missing credential, a failing dependency, a question only a human can answer — and moves to `passing` only when the verification command succeeds. The transition into `passing` is gated, which is the precise sense in which the harness controls the machine: an agent that claims a feature is done has only made a claim, and the harness runs the verification command, and only a passing command moves the feature to `passing`. An agent that writes its own state into the file has broken the design, because the moment the agent controls the record of its own progress, the record stops being evidence and becomes a self-assessment, and the whole point of the feature list is that the record is evidence.

The number of features that are not yet passing is the pressure on the agent, which is the idea of back-pressure stated as plainly as it can be stated: every unpassed feature is work the system still owes, and the count of them is the size of the job remaining. When the count reaches zero, the project is complete, because every verification command in the file has passed, which is a definition of done that a machine can check and an operator can trust. And the same file is read by every part of the harness, which is what makes it a primitive rather than a convenience: the scheduler reads it to decide which feature to work on next, the verifier reads it to know which command to run, the handoff reporter reads it to summarise progress for the next agent or the next human, and the progress tracker reads it to show the operator how far along the project is. Four consumers, one file, no copies to drift apart, and a crash anywhere in the system loses nothing, because the file is the record and the record is on disk. The course's `templates/feature_list.json` is a starter version of this file, with the triple and the four states already laid out, and the exercise that follows it is to drive a run from that file and watch the pressure fall to zero.

### Checkpointing and recovery: snapshots versus replay

With state designed, there are two fundamentally different ways to make a run survive a crash, and the choice between them is the chapter's second big decision. The first is snapshot checkpointing, which is what LangGraph and Mastra both do: after each step — at each super-step boundary, one tick of the graph in which every scheduled node runs — the runtime writes a snapshot of the whole state to a checkpointer, keyed by a thread identifier, and a fresh process resumes by loading the latest snapshot and continuing from there ([LangGraph checkpointers documentation](https://langchain-ai.github.io/langgraph/reference/checkpoints/)). The checkpointers form a ladder of durability: the in-memory saver is for tests and forgets everything when the process exits, the SQLite saver survives a process restart on one machine, and the PostgreSQL saver is the production choice. Microsoft's Agent Framework works the same way, creating a checkpoint at the end of each superstep that captures every executor's state, the pending messages, and the shared state, with in-memory, file, and Azure Cosmos DB storage behind one protocol ([Microsoft Learn, "Workflows — Checkpoints"](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)). The crucial subtlety, and the one that bites in production, is that a checkpoint is written at a super-step boundary and never in the middle of a node — so the node that was running when the process died runs again from its first line on resume, and any side effect it performed before the checkpoint is performed twice unless the node is idempotent. The receipt node in `code/02_langgraph_checkpoint_resume.py` is idempotent by design, recording the receipt against the ticket identifier and skipping duplicates, and the exercise that removes that guard is the one that teaches the lesson permanently.

The second way is durable execution by replay, which is Temporal.io's model, and it inverts the problem: instead of snapshotting state, Temporal records the history of everything that happened — the event history — and rebuilds state by re-running the workflow code against that history ([Temporal, "Understanding Temporal"](https://docs.temporal.io/evaluate/understanding-temporal)). The workflow is ordinary code with loops and conditionals, but it must be deterministic, because replay only reconstructs the right state if the code makes the same decisions given the same history; anything non-deterministic — the wall clock, a random number, a network call — is forbidden in workflow code and must live in an activity, whose result is recorded in the history and returned verbatim on replay. The payoff for that discipline is stronger than snapshotting: a crashed activity is never re-run at all, since its recorded result is replayed, and a workflow can sleep on a durable timer for months without holding a process open. The price is the determinism contract itself, plus the event history's hard limits and an extra service to operate, and `code/04_temporal_workflow.py` lets you feel both sides — a local simulator that replays a JSON event log with no server, and the same workflow definition ready to run against a real Temporal server. There is also a third, quieter form of recovery that both models support and that Chapter 8 will develop fully: time travel, the ability to list a thread's checkpoints, rewind to an earlier one, edit the state there, and fork a new path from it, which turns a checkpoint history into a debugging tool as well as a safety net ([LangChain Academy, "Introduction to LangGraph"](https://academy.langchain.com/courses/intro-to-langgraph)).

### Putting it together: the decision framework

So the chapter's framework, stated as one flow, goes like this: first, name the unit of progress you refuse to lose — a turn, a step, or a pause inside a step — because that decides the granularity of the durable record, and Mastra's account of the three granularities is the clearest statement of the choice ([Mastra, "What are durable AI agents?"](https://mastra.ai/blog/what-are-durable-ai-agents)). Then choose the shape by who owns the next step: a DAG when the path is fixed, a cyclic graph when a step needs a second chance under a code-owned guard, a free-form loop only when the path is unknowable, with a hard cap and budget owned by code. Then design the state as small, plain, versioned JSON with claim checks for large payloads and no secrets, and choose the recovery mechanism by how much you can afford to redo: snapshot checkpointing when re-running the interrupted step is cheap and safe, durable execution by replay when re-running it is expensive, charged, or impossible. And finally, write down the failure modes before you ship — the kill between a side effect and its checkpoint, the deploy over a running workflow, the checkpoint that grows until it is slower to write than the work it protects — because each of them has a named defence in this chapter, and a system whose failure modes are named is a system that can be operated, whereas one whose failure modes are merely hoped away is a system waiting for its first 2 a.m.

One more thing is worth saying plainly about the code, because a reader who finds a template draft or a rule-based reviewer in it should be able to tell a deliberate stand-in from an unfinished one. Every demo in this chapter runs in two modes: a deterministic mode, in which drafts are templates and the reviewer is a rule, and a live mode (`--live`), in which drafts are written by a real model, drafts are judged by a real model, and the free-form loop's next step is chosen by a real model. The deterministic mode is the deliberate stand-in, and it stays because the thing each demo is studying — the topology in `01`, the checkpointing in `02`, the replay model in `04`'s simulator — is only testable if every run faces the same verdicts, and because the exercises are written against those exact outcomes. The live mode is the same job with the stand-ins removed, and the receipt ledger both modes share is a real file, not a stand-in at all: a receipt is a JSON line in `receipts.jsonl`, and a second execution for the same ticket appends nothing. The one remaining simulator is the local Temporal replay in `04`, which stands in for a Temporal server rather than for the work — its activities are real in both modes — because it is the only way to study the replay model with no infrastructure.

## The numbers that matter

Every number here traces to a source verified live on 18 November 2026, or is labelled as measured locally by running the chapter's own code.

Temporal.io's event history is capped at 51,200 events or 50 megabytes per workflow execution, with warnings from 10,240 events or 10 megabytes, and a single payload is capped at 2 megabytes with an event-history transaction capped at 4 megabytes ([Temporal, "System limits"](https://docs.temporal.io/cloud/limits)). Those caps are the reason a long-running agent loop cannot simply run forever on Temporal: each activity adds roughly six events, so a loop that never compacts its history will hit the ceiling, and the designed escape is Continue-As-New, which closes the run and starts a fresh history carrying forward only the state you choose. The same caps are also the reason payloads must be claim checks: a transcript passed whole into every activity lands in the history permanently, so history grows toward the cap far faster than the step count suggests. Mastra's side of the ledger is the opposite scale: a suspended order workflow's whole snapshot serialised to 1,059 bytes of JSON, with a per-step map reading `reserve-inventory: success` and `human-approval: suspended` ([Mastra, "What are durable AI agents?"](https://mastra.ai/blog/what-are-durable-ai-agents)). That number is the argument for keeping state small in one figure — a checkpoint that small is cheap to write at every step, cheap to read back on resume, and small enough that keeping a long history of them is not a storage decision at all.

The chapter's own measurements, run locally while writing it, put concrete numbers on the LangGraph path. With LangGraph 1.2.22 and langgraph-checkpoint-sqlite 3.1.3, a four-ticket triage run through `code/02_langgraph_checkpoint_resume.py` produced 25 checkpoints — roughly six per ticket, one per super-step — and the SQLite file was 140 kibibytes after the full run and 4 kibibytes after a kill two super-steps in. Resuming the killed run from the same thread identifier in a fresh process reprocessed zero completed tickets and resolved all four, which is the acceptance test the exercises demand rather than a claim to take on trust. And the serialisation file shows the same smallness from the other side: a one-ticket state snapshot is 198 bytes of JSON, and adding a claim check for a 50-megabyte attachment grows it only to 240 bytes. For scale, the syllabus this chapter's shape is borrowed from — LangChain Academy's "Introduction to LangGraph" — runs to 55 lessons and about six hours of video, which is a useful calibration of how much depth the graph model repays once you commit to it ([LangChain Academy, "Introduction to LangGraph"](https://academy.langchain.com/courses/intro-to-langgraph)).

## The advanced-level design-review angle

In a design review, this chapter is not tested by asking you to recite an API; it is tested by handing you a failure and asking what you would have built differently. The question will sound like: "Your agent charged a customer twice after a deploy — walk me through the design that let that happen." The strong answer starts from the kill window, not from the framework: a side effect was performed, and the record of it was not durable before the process died, so the resumed run performed it again, and the fix is an idempotency key on the side effect plus a checkpoint boundary that sits after the recording of the result rather than before it. Or the question will be a choice: "You have a ten-step onboarding flow with a human approval in the middle that can take two days — LangGraph, Temporal, or a plain loop?" The strong answer names the decision variables before picking: the approval is a durable pause, so you need a snapshot or a history that outlives the process; the steps are fixed, so a DAG or a cyclic graph beats a free-form loop; the approval arrives days later across deploys, so the state must be versioned and the node identities stable; and if the steps include charged actions, replay beats snapshotting because a crashed charge must never re-run. What marks the answer as advanced-level is not the framework name but the failure modes volunteered unprompted: the checkpoint that grows with the transcript, the deploy that breaks replay determinism, the cycle without a guard, the loop whose cost grows with the square of its steps, and the resume that leaks one tenant's state into another's because execution state and memory were stored in the same bucket. If you can name the failure mode and its defence in the same breath, you are answering as someone who has operated the system, not merely read about it.

## How this maps to Mastra and Amazon Bedrock

The reader's production stack is Mastra on Amazon Web Services Elastic Container Service with Amazon Bedrock, and the mapping is closer than the Python code in this chapter might suggest. Mastra's workflows are the DAG and cyclic shapes of this chapter in TypeScript: steps composed with `.then()`, `.branch()`, and `.dowhile()`, with `suspend()` and `resume()` providing the durable pause — suspension writes a snapshot to the configured storage, keyed by run identifier, and resuming re-executes the suspended step with typed resume data rather than restoring a call stack ([Mastra, "Suspend and resume"](https://mastra.ai/docs/workflows/suspend-and-resume)). The mapping to the chapter's rules is direct: a Mastra workflow snapshot is the LangGraph checkpoint under another name, the same small-plain-versioned JSON discipline applies, and the same warning holds — a crash mid-step can leave a run stuck in `running`, so the step that was in flight runs again and must be idempotent. Mastra's durable-agent API, currently in beta, wraps the agent loop itself in a workflow so that a long-running loop gets the same recovery contract, which is the chapter's free-form loop with a durable record underneath it rather than beside it ([Mastra, "What are durable AI agents?"](https://mastra.ai/blog/what-are-durable-ai-agents)). On the model side, the language model calls in this chapter's activities are exactly the calls a Mastra agent makes through Amazon Bedrock, whose agents product orchestrates a foundation model with action groups and knowledge bases ([Amazon Bedrock, "Create and configure agent manually"](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-create.html)), and the tools those calls invoke are, in the reader's stack, Model Context Protocol (MCP) tools — the open protocol for connecting a language-model application to external tools and data ([Model Context Protocol, "Specification"](https://modelcontextprotocol.io/specification/2026-07-28)). The architectural point carries across unchanged: whether the tool is a Bedrock action group or an MCP server, it is an activity, not workflow code — it is called from the orchestrated step, its result is recorded in the durable record, and it is the thing that must be idempotent, because it is the thing that touches the world. Chapter 2 will build the MCP side from scratch; this chapter is the reason the MCP side needs the discipline it will teach.
