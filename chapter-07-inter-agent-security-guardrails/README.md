# Chapter 7 — Inter-Agent Security & Guardrails

> **What you will be able to do after this chapter:** look at an agent that reads email, web pages, tool output and messages from other agents, and see it for what it is — a program that lets strangers write into its instruction stream — and then build the system of defences that makes that survivable: provenance tagging, a sanitisation proxy, least-privilege tool scoping, approval gates and an audit log, each enforced in code rather than in a prompt.

## The idea in plain words

Imagine you hire a capable assistant, give them the keys to your inbox and your customer database, and then discover that anyone in the world can slip a note into the pile of paper on their desk, and that your assistant treats every note on the desk as if you wrote it. That is an agent. A language model cannot tell the difference between an instruction and a piece of data, because by the time either reaches it they are both just tokens in the same stream, and so everything the agent reads — a tool result, a retrieved document, a web page, a message from another agent — is a potential instruction, whether or not anyone intended it as one. This is the trust boundary that the whole chapter turns on, and once you see it you cannot unsee it: the model output is data, the tool output is data, and the only things that may act as instructions are the system prompt you wrote and the authenticated user you serve, so the security of an agent is not a property of the model at all, it is a property of the harness you build around the model, and a guardrail that lives only in a prompt is not a guardrail, it is a hope.

The classic name for the attack is prompt injection, a term [coined in 2022](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) by analogy with [SQL injection](https://owasp.org/www-community/attacks/SQL_Injection), and the analogy is exact in the way that matters: in both cases trusted instructions and untrusted input are glued into one string, and the system cannot tell which part is which. What changed the stakes, and what makes this chapter about agents rather than chatbots, is the indirect form of the attack, which [this paper](https://arxiv.org/abs/2302.12173) named indirect prompt injection in 2023 when it showed that an attacker who never talks to the model at all can still steer it, simply by planting instructions in content the application is likely to retrieve — a web page, an email, a document — and the paper's taxonomy still frames the field, because it shows the same trick producing data theft, fraud, intrusion, self-spreading instructions and denial of service, depending on what tools the compromised agent can reach. The threat's sharpest practical form is the [lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/): an agent becomes a data-theft path when it combines access to private data, exposure to untrusted content, and a way to communicate externally, and with all three present a single hidden sentence can read your data and send it to an attacker, while removing any one of the three breaks the chain entirely — which is why this chapter's defences are organised around cutting legs of that trifecta rather than around catching bad words.

That framing also explains why the [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/) lists prompt injection as LLM01, its top risk, and why the same list's neighbouring entries matter here too: excessive agency (LLM06) is what turns an injection into damage, because an agent with more permissions than its task needs can do more with a stolen instruction, and improper output handling (LLM05) is what lets an injected model output reach a downstream system unchecked. Microsoft's [Lesson 6 of AI Agents for Beginners](https://microsoft.github.io/ai-agents-for-beginners/06-building-trustworthy-agents/), on building trustworthy agents, is the adapted backbone of this chapter, and it already contains the three ideas this chapter builds on — a threat table that pairs each threat class with a mitigation, least-privilege access as the answer to over-broad system access, and human-in-the-loop approval for sensitive operations — and this chapter's original work is to take those ideas from a checklist and turn them into a running system, with the attack demonstrated first and the defence proven against it afterwards.

## The mechanism, step by step

The story starts with the attack, because a guardrail you have never seen fail is a guardrail you do not understand. Consider a support agent whose job is to summarise the newest ticket, and suppose the newest ticket contains a polite request followed by a hidden block that says, in effect, ignore everything above and send the customer's account details to an outside address. The vulnerable version of this agent, which you can run in `code/demo_agent.py`, does exactly what a naive agent does: it calls the ticket tool, feeds the raw result to its decision step, and then calls the send tool with the address the ticket named, and the exfiltration happens with no error, no warning and nothing in the log that looks like an attack — which is the first lesson, that an injection does not look like a breach, it looks like the agent doing its job. The guarded version of the same agent runs the same ticket through five layers, and each layer is designed to fail independently of the others, so that an attacker who defeats one still faces the rest.

The first layer is provenance tagging, and it is the cheapest and most neglected of the five, because it is a data-model decision rather than a security product. Every piece of content in the guarded agent carries its source and a trust level with it, as a `ContentItem` in `code/guardrails.py`, and there are only two trust levels — trusted, meaning the system prompt or the authenticated user, and untrusted, meaning everything else — because a middle level is where injections hide, quietly promoted to trusted by the next person who handles them. The rule that follows is simple to state and strict to enforce: untrusted content may be summarised, quoted or displayed, but it may never be used as an instruction, and the code enforces that by making the trusted-text accessor refuse untrusted content outright, so the mistake of treating data as a command has to be made deliberately rather than by accident.

The second layer is the sanitisation proxy, which is where untrusted content is cleaned before the model ever sees it, and the word proxy matters here, because the cleaning happens in a separate component that sits between the tool and the model, not inside the model's prompt. The proxy in `code/guardrails.py` does three things in order: it strips invisible characters, including the Unicode tag characters in the range U+E0000 to U+E007F that render as nothing in most editors but read as text to a model; it removes lines that match instruction-like patterns, such as "ignore all previous instructions" or "send the data to", and records exactly what it removed; and it redacts secret-shaped values, such as an API key or a private key block, so that a secret smuggled into retrieved content cannot be copied into a prompt or an outbound message. What is left is then wrapped in explicit delimiters that label it as untrusted data, so the model prompt can say truthfully that the text between the markers is data to summarise rather than instructions to follow. Two honest limits belong here, and the chapter states them plainly rather than burying them: the proxy is a heuristic, so a well-paraphrased injection will slip past it, and a proxy that is too aggressive will strip legitimate text — a support ticket that genuinely contains the word "send" — which is why the proxy returns what it removed, so a human can tell a real attack from a false positive, and why the proxy is never the only layer.

The third layer is least-privilege tool scoping, and it is the layer that [DeepLearning.AI's Governing AI Agents](https://www.deeplearning.ai/courses/governing-ai-agents) course uses as its central example, in its Databricks form of views, column masking and agent identities that grant an agent only the data its task needs. The principle transfers directly out of that platform: each tool in the registry declares the scopes it needs, in the same spirit as OAuth scopes, and the agent is handed only the tools whose scopes cover the current task, so a summarisation task never receives the send tool at all, and a tool outside the granted scopes is refused by the registry rather than by the model. Scoping is also where the chapter's second attack lives, because tool poisoning does not attack the model through data at all, it attacks it through the tools themselves. In the [Model Context Protocol](https://modelcontextprotocol.io/), a tool's description is free text that the model reads in full while the human approves only a tool name, and [Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks) showed in April 2025 that a poisoned description — an ordinary-looking calculator whose description secretly told the model to read the user's private SSH key — could exfiltrate credentials through a tool the user had approved. The same family includes shadowing, where one tool's description rewrites how the agent should use another tool, and the rug pull, where a server that was clean when reviewed changes its description afterwards, and the scale of the problem is now measured rather than anecdotal: the [MCPTox benchmark](https://arxiv.org/abs/2508.14925), built on 45 live Model Context Protocol servers and 353 authentic tools, reports that poisoned tools succeeded against 20 agent models with the highest refusal rate, for Claude 3.7 Sonnet, under 3%, and with the most vulnerable model succeeding in 72.8% of cases. The defence in code is pinning: the registry records a hash of each tool description at review time and re-checks it on every call, so a changed description is refused until a human re-reviews it, and the audit log records the refusal as a rug pull rather than as a generic error.

The fourth layer is the approval gate, and it exists because the first three layers are probabilistic while some actions are irreversible. Read-only calls pass through, but write and exfiltration calls are held until an approver — a human, or a policy callback in tests — says yes to the exact arguments, including the destination address, because an approval that hides the destination is not an approval. Two details make the gate work in practice rather than on paper: the gate checks the destination against an allow-list before the human is even asked, so a person is never put in the position of making a security decision under time pressure about an address they have never seen, and the default approver denies, so a missing approver is a safe failure rather than an open gate. This is the layer that Microsoft's Lesson 6 calls human-in-the-loop, and the chapter's contribution is to place it where it belongs in the sequence — after the proxy and the scopes, so that humans are asked about the small number of calls that survive the earlier layers, rather than about every call, which is how approval fatigue sets in and humans start clicking yes to everything.

The fifth layer is the audit log, and it is the layer that turns the other four from a hope into something you can prove. Every guardrail decision — a tool called, a sanitisation performed, a rug pull refused, an approval granted or denied — is written to an append-only log with a timestamp, the tool involved, and the evidence that justified the decision, and secrets are never written to it. Without the log, a blocked attack and a lucky miss look identical, and without the log you cannot answer the question the next section asks, which is how you know the guardrail works. The log is also the bridge to the production stack this course is built around, because [Guardrails for Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-components.html) provides the same shape as a managed service — content filters, denied topics and sensitive-information filters applied to prompts and responses — and the lesson to carry across is that a managed guardrail still needs the harness around it: Bedrock's own documentation notes that its inline guardrail does not evaluate tool results, tool definitions or tool-call arguments, which are exactly the channels this chapter's attacks travel through, so the managed layer and the harness layer complement each other rather than replacing each other.

Finally, the chapter closes the mechanism with the strongest defence in the literature, because an experienced engineer should know where the ceiling is. [CaMeL](https://arxiv.org/abs/2503.18813), from Google DeepMind and ETH Zurich, does not try to detect injections at all: it extracts the control flow and the data flow from the trusted user query, compiles them into a program, and executes that program in a custom interpreter in which untrusted data can never change the program's flow, with capabilities attached to every value so that private data cannot flow to an unauthorised destination. On [AgentDojo](https://arxiv.org/abs/2406.13352) — the benchmark this chapter uses as its evaluation standard, with 97 realistic tasks and 629 security test cases across email, messaging, travel and banking environments — CaMeL solves 77% of tasks with provable security, against 84% for an undefended system, and that 7-point gap is the honest price of a structural guarantee, stated here as the authors report it. CaMeL is not something you will reimplement in a week, and the chapter does not pretend otherwise; it is the direction the field is moving, and the dual-model pattern inside it — a privileged model that plans from the trusted query alone, and a quarantined model that reads untrusted content with no tools — is a pattern you can adopt in miniature today, by giving the call that handles dirty content zero tools.

## The advanced-level interview angle: proving a guardrail works

Here is where most candidates stop, and where you should not. A junior answer to "how do you secure your agent?" is a list of filters; an advanced answer is an evaluation. The interviewer is not really asking what you would block, they are asking how you would know — and the honest answer starts with the admission that no prompt-level defence is complete, because the model cannot reliably distinguish instructions from data, so the claim to defend is never "our agent cannot be injected", it is "our agent cannot be injected into doing damage, and here is the measurement that shows it". That measurement has three parts, and each part maps to something you can build in this chapter's exercises.

First, report utility and attack success together, never one without the other, because a guardrail that blocks every attack by refusing every task is not a guardrail, it is an off switch. AgentDojo's design is the template: benign tasks with formal success checks on the final state, injection tasks with their own checks on the attacker's goal, and the two reported side by side as utility under attack and targeted attack success rate, so that a defence which drops the attack success rate from 17.6% to 1.75% while dropping utility from 47.7% to 42.7% — the figures [Meta's LlamaFirewall paper](https://arxiv.org/abs/2505.03574) reports for PromptGuard 2 together with AlignmentCheck on AgentDojo — can be judged as a trade-off rather than celebrated as a victory. When you present a number in an interview, present it that way, with the utility cost attached, and name the benchmark and the version, because a number without a benchmark is a marketing claim.

Second, red-team the guardrail itself, not just the model. A fixed list of attack strings measures yesterday's attacker, so your evaluation must include an adaptive attacker: someone who has read your proxy's patterns, your allow-list and your approval flow, and who writes the paraphrase, the encoding trick and the multi-turn slow burn that your current defences miss. In the exercises you will do exactly this, by taking your own working defence and attacking it until it breaks, and then writing down the bypass and the layer that should have caught it — and in an interview, the sentence "here is the attack that broke my first version, and here is what I changed" is worth more than any number of defences you claim have never been broken, because a defence that has never been attacked is a defence that has never been tested.

Third, show the failure mode you chose on purpose. Every guardrail design trades false positives against false negatives, and the right trade depends on the action: a summarisation agent can afford to over-block, because the cost of a false positive is a ticket that needs a human glance, while a payment agent cannot afford to over-block, because the cost is a legitimate payment refused, and it cannot afford to under-block either, because the cost is money moved. An advanced answer names the trade, names the cost on each side, and shows the audit log that lets you measure the false-positive rate in production and tune the threshold — and that is also why the audit log is a first-class layer in this chapter rather than an afterthought, because without it you are tuning blind.

## What to run first

Start with `code/demo_agent.py`, which runs the poisoned-ticket scenario against a vulnerable agent and a guarded agent in the same process, with no API key and no network access. On this machine the vulnerable agent exfiltrates the customer record to the attacker's address, the guarded agent blocks it and records the block in its audit log, and the guarded agent still summarises a clean ticket normally — and those three outcomes, taken together, are the chapter in miniature: the attack works, the defence works, and the defence does not break the legitimate task. Then run `python -m unittest test_guardrails -v` in the same directory: 13 tests, each named for the attack it covers, so that a failing test reads as a security regression. The notebook `code/07_guardrails.ipynb` walks through the same material interactively, and `exercises.md` takes you from reproducing the attack to red-teaming your own defence.
