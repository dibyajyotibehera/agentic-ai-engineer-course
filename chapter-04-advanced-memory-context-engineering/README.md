# Chapter 4 — Advanced Memory and Context Engineering

## The idea in plain words

An agent that cannot remember is an agent that starts every task as a stranger, and an agent that remembers everything is an agent that drowns in its own notes, so the real engineering problem is neither storage nor recall but judgement about what deserves to survive the turn. Think of the way you yourself work a long support case: you keep the current ticket in front of you, you remember roughly what happened on the last few tickets with this customer, and you carry a small set of settled facts — the customer's plan, their data residency, the refund policy as it stands today — without re-reading the whole history each time. That is exactly the shape this chapter builds, because a production agent needs the same three layers, and it needs them as a system with rules rather than as a longer prompt. The working tier holds what is live right now, the episodic tier holds what happened on past tasks in a form the agent can search, and the semantic tier holds the settled facts and rules that should survive across sessions, and the whole point of separating them is that each tier has a different cost, a different lifetime and a different failure mode, so each one gets its own budget and its own eviction rule. Microsoft's [AI Agents for Beginners](https://github.com/microsoft/ai-agents-for-beginners) Lesson 13, "Managing Agentic Memory", teaches the same three-way split as working, short-term and long-term memory, with working memory living in the conversation session, short-term memory accumulating inside a thread, and long-term memory held in an external store that the agent reaches through tools, and this chapter adapts that skeleton with attribution and then raises it to advanced depth by adding the parts no introductory lesson covers: a write gate that decides what earns a write, eviction policies that decide what leaves when the store fills, conflict handling for the day the policy changes, tenant isolation so one customer's memory never leaks into another's, and a token budget that turns all of it into a cost per task you can defend in a design review. The shape of the lesson also draws, as syllabus inspiration only, on DeepLearning.AI's [Context Engineering](https://learn.deeplearning.ai/courses/context-engineering/lesson/fwe3dxjr/a-conversation-between-jeff-huber-and-andrew-ng) course, its [Long-Term Agentic Memory with LangGraph](https://www.deeplearning.ai/short-courses/long-term-agentic-memory-with-langgraph/) short course, Oracle's [Agent Memory: Building Memory-Aware Agents](https://www.deeplearning.ai/courses/agent-memory-building-memory-aware-agents) course, and [LLMs as Operating Systems: Agent Memory](https://www.deeplearning.ai/courses/llms-as-operating-systems-agent-memory), none of whose content is copied here.

## Why a longer prompt is not a memory system

The tempting shortcut is to keep appending history to the prompt until the model has everything, and the reason it fails in production is that it fails on three axes at once, which is why the rest of this chapter keeps returning to those three axes. First there is cost, because every token in the prompt is paid for on every turn, so a fact that is re-read a thousand times costs a thousand times more than a fact that is retrieved once and then summarised, and the Mem0 paper makes the point with measured numbers: against a full-context baseline, Mem0 attained a 91% lower p95 latency and saved more than 90% of the token cost, while achieving a 26% relative improvement in the LLM-as-a-judge metric over OpenAI's memory on the LOCOMO benchmark ([arXiv:2504.19413](https://arxiv.org/abs/2504.19413)). Second there is accuracy, because attention degrades over distant tokens and the model starts confusing what happened in March with what changed in June, which is a failure no amount of window size fixes, since the Mem0 authors report the same pattern explicitly: extended context windows alone do not solve long-term coherence because real conversations are thematically discontinuous. Third there is safety, because a prompt that contains everything contains everything, including the other tenant's data, the secret somebody pasted in passing, and the superseded policy that the model will cheerfully quote as current, so the moment memory becomes a store rather than a transcript you need the same controls any store needs: scoping, versioning, expiry and an audit trail. Once you see those three pressures together, the design that follows stops looking like a collection of tricks and starts looking inevitable, which is the shift this chapter is trying to produce: memory is a write-gated, versioned, tenant-scoped store, not a longer prompt.

## The mechanism, part one: the three tiers and what each one costs

The working tier is the conversation itself, the messages and the scratchpad for the task in hand, and it is the only tier that is free to write to, because writing to it means appending to a list you already hold, yet it is also the most expensive tier to read from, because everything in it is re-sent to the model on every turn. That asymmetry drives the first design rule, which is that working memory should hold the current task and nothing else, and anything that needs to survive the session should be promoted out of it through the write gate rather than left to accumulate. The episodic tier is the record of past tasks — what the agent did, what the outcome was, what went wrong — stored as short summaries with embeddings so that a new task can retrieve the handful of past episodes that resemble it, and its cost is paid once at write time, when the episode is summarised and embedded, and then again in small amounts at read time, when only the retrieved episodes enter the prompt. The semantic tier is the settled knowledge: facts about the user, entities and their relationships, rules and policies, and the distilled lessons from many episodes, and it is the cheapest tier per use, because a single fact costs a few dozen tokens each time it is retrieved, yet it is the most expensive tier to get wrong, because a wrong fact is applied to every future task until somebody corrects it, which is why the semantic tier gets the strictest write gate and the only conflict handling in the system. Microsoft's Lesson 13 draws the same map in its own terms, and the Cognee notebook in that lesson shows the semantic tier in its richest form, turning unstructured text into a knowledge graph of entities and relationships backed by vector embeddings, while the Mem0 notebook shows the episodic-to-semantic promotion path, extracting durable facts from conversations and deduplicating them against what is already stored; both are linked in [references.md](references.md), and the code in this chapter re-implements the same shape in framework-neutral Python so you can see every decision instead of inheriting it from a library.

The cost arithmetic is what turns this from a diagram into an engineering decision, so let us walk through it with the one price this chapter treats as a verified fact, which is that OpenAI's text-embedding-3-small costs $0.02 per 1M tokens (OpenAI pricing, [platform.openai.com/docs/pricing](https://platform.openai.com/docs/pricing)). Embedding is the write-time cost of the episodic and semantic tiers, and at that price the arithmetic is almost embarrassingly cheap: embedding a 1,000-token episode summary costs 1,000 × $0.02 / 1,000,000, which is $0.00002, so ten thousand episodes a day cost $0.20 a day in embeddings, and even a million-token corpus costs $0.02 to embed. That tells you something important, which is that the embedding bill is never the reason to skip memory, and the real money is in the large language model tokens that retrieved memories consume on every task, so the budget that matters is the prompt budget, not the storage budget. To keep that arithmetic honest without inventing a model price, the code in this chapter prices large language model tokens parametrically: you supply the per-1M-token input price of whatever model you actually run, and the cost model reports the cost per task as a formula rather than a fabricated number. Against that background, the other verified numbers in this chapter are best read as levers on the same equation. The GPT Semantic Cache paper ([arXiv:2411.05276](https://arxiv.org/abs/2411.05276)) reports that caching answers by semantic similarity, rather than by exact text match, reduced API calls by up to 68.8%, with cache hit rates from 61.6% to 68.8% across query categories, a positive hit rate above 97%, and a cosine similarity threshold of 0.8 as the optimum across a 0.6–0.9 sweep — and note carefully that this 68.8% figure comes from that arXiv paper, not from the GPTCache library, and the two must not be conflated. What that means in cost terms is that for repetitive traffic, a semantic cache sitting in front of the episodic tier can remove roughly two thirds of the calls entirely, which dwarfs any saving you will get from tuning the embedding model. Pinecone's own multitenancy documentation makes a similar point about layout: with 100 tenants holding 1 GB each, searching one tenant's namespace costs 1 read unit, because a query costs 1 read unit per 1 GB of namespace searched, with a minimum of 0.25 read units, while the same search with metadata filtering across a single shared 100 GB namespace costs 100 read units, because it scans all 100 GB regardless of the filter, and each `$in` or `$nin` filter operator is capped at 10,000 values (Pinecone, [Design for multitenancy](https://docs.pinecone.io/guides/data/design-for-multitenancy)). At 10,000 queries a day that is 10,000 read units against 1,000,000 read units for the same answers, a hundredfold difference decided entirely by how you lay out the store, which is why tenant isolation is treated in this chapter as a cost decision as well as a safety decision. And GraphRAG ([arXiv:2404.16130](https://arxiv.org/abs/2404.16130)) shows what the semantic tier can become when it grows into a graph: a two-stage index that first derives an entity knowledge graph from the source documents and then applies Leiden community detection and pre-generates community summaries, with queries answered by a map-reduce pass over those summaries, beating naive Retrieval-Augmented Generation (RAG) on comprehensiveness in 72–83% of head-to-head comparisons on podcast transcripts and 72–80% on news articles, with p < .001, and on diversity in 75–82% and 62–71% respectively — while the root-level variant, which answers from the top-level community summaries alone, retains a 72% comprehensiveness and 62% diversity win rate at a fraction of the cost, which is the version you reach for when the full graph is too expensive to query on every task.

## The mechanism, part two: the write gate, or what earns a write

If everything the agent sees gets written to memory, the store fills with trivia, contradictions and secrets, and retrieval quality collapses under the weight of it, so the write gate is the single most consequential component in the system, and it is where most production memory systems actually fail. The gate in this chapter asks five questions in order, and a candidate memory must pass all five before it is stored. First, is it durable, meaning will it still be true and useful in a week, so that a preference, a decision, a policy or a learned lesson passes while a transient status, a one-off identifier or a verbatim transcript fails. Second, is it new or changed relative to what is already stored, so that a duplicate is dropped and a changed fact goes to conflict handling instead of being silently appended. Third, is it safe to store, meaning it contains no credential, no secret, no payment detail and nothing the user marked as private, because a memory store is a retrieval surface and anything in it can surface in a future prompt. Fourth, is it attributable, meaning it carries its source, its tenant, its author and its timestamp, because an unattributed memory cannot be challenged, corrected or deleted. And fifth, is it worth its tokens, meaning its expected reuse justifies the prompt tokens it will consume on future tasks, which is a judgement call the gate makes with a simple scoring rule in the code — a combination of importance, expected reuse and recency — rather than by asking the model to decide afresh each time. Mem0's own pipeline implements the same idea in production form, running extraction, deduplication against existing memories and an update-or-add decision on every write, and LangMem, LangChain's memory library, makes the same split explicit by offering both a hot path, where the agent consciously saves notes with tools, and a background path, where a memory manager extracts and consolidates memories asynchronously (LangMem, [github.com/langchain-ai/langmem](https://github.com/langchain-ai/langmem)). The background path matters because the write gate does not have to run on the critical path: for a support copilot, the gate can run after the ticket closes, when latency no longer matters, and the lesson to carry away is that the gate's strictness is a product decision, not a technical default — a strict gate gives you a small, trustworthy store and a loose gate gives you a large, untrustworthy one, and there is no configuration that gives you both.

## The mechanism, part three: retrieval, eviction and conflict handling

Retrieval is where the three tiers meet the prompt, and the discipline here is that retrieval is budgeted, not open-ended, which leads directly into the token budgeting section below. Each tier is queried with the current task, the results are ranked by a blend of similarity, recency and importance, and only the top few cross the gate into the prompt, with their identifiers and scores recorded so that a later audit can show exactly which memories influenced an answer. Eviction is the mirror image of retrieval, and it is the part of memory design that most tutorials skip, even though it is what determines whether a year-old store is still useful. This chapter implements four eviction policies and makes you choose between them, because the choice encodes a theory about what your agent's past is worth. Least-recently-used eviction drops whatever has not been read for longest, which is simple and fair but discards the rarely-needed fact that would have saved a task. Least-frequently-used eviction drops whatever has been read least often, which protects the workhorses but starves new memories before they have had a chance to prove themselves. Importance-decay eviction scores each memory as its importance multiplied by an exponential decay over its age, so a high-importance memory survives longer than a trivial one but nothing survives forever, and the half-life becomes a tunable product parameter — a support policy might deserve a half-life of months, while a transient workaround deserves one of days. And time-to-live eviction drops memories at a fixed expiry, which is the only policy that guarantees a stale fact disappears on schedule, and the only one that satisfies a data-retention obligation without a human in the loop. In practice a production store layers them, using time-to-live as a hard ceiling, importance-decay as the ranking, and least-recently-used as the tie-breaker, and the code in this chapter does exactly that, with the policy composable so you can measure the difference rather than argue about it. The MemGPT paper gives the classic form of the same pressure from inside the context window itself: when the prompt reaches about 70% of the context window, MemGPT inserts a memory-pressure warning telling the model to move useful information into working context or archival storage, and at 100% it flushes, evicting about 50% of the first-in-first-out queue after recursively summarising what leaves ([arXiv:2310.08560](https://arxiv.org/abs/2310.08560)). That 70% warning and 50% flush are worth remembering as design constants, because they are the reason a memory system needs its own eviction long before the window fills: if you wait for the model to feel the pressure, you have already paid for the tokens.

Conflict handling is where the system earns its keep, and the running example in this chapter is deliberately mundane, because mundane is where production breaks: in March the support policy said refunds within 30 days needed no approval, and in June the policy changed to 14 days with manager approval, so the semantic tier now holds two memories that contradict each other, and the agent must not average them, must not pick one at random, and must not quote the March version as if it were current. The rule this chapter implements is versioned supersession with an explicit authority check: every semantic memory carries a version, a source, an authority level and a timestamp, and a new memory supersedes an old one only when its authority is at least as high as the old one's and its source is one the system trusts for that kind of fact — a policy document outranks a chat message, a manager's correction outranks an agent's inference, and a newer low-authority claim never silently overwrites an older high-authority one. When the authority check fails, the system keeps both memories, flags the new claim as contested while the current fact stands, and routes the decision to a human or to the next agent turn with the conflict made visible, which is the only honest behaviour, because the alternative is an agent that states a superseded policy with complete confidence. The old memory is never deleted on supersession, it is retained with a superseded flag and a pointer to its replacement, so that an audit can reconstruct what the agent believed on any given date, and so that a rollback is a flag flip rather than a data recovery exercise. That versioned, append-only shape is borrowed from the way LangMem treats deletion — the model may recommend a removal, but the calling code decides what happens — and it is the same instinct that makes the code in this chapter treat every destructive operation as a state change rather than an erase.

## The mechanism, part four: tenant isolation, or the leak you cannot afford

Tenant isolation is the requirement that turns a memory layer from a feature into a trust boundary, and the failure mode is correspondingly severe, because a cross-tenant leak is not a quality bug but a data breach. The rule is simple to state and easy to get wrong in implementation: every memory belongs to exactly one tenant, every read and every write carries the tenant identifier, and no query may ever run without one. The code enforces this structurally rather than by convention, by making the tenant identifier a required parameter of the store's read and write paths and by scoping every index on it, so that a forgotten filter is a type error rather than a silent leak, and the exercises include a test that attempts a cross-tenant read and expects it to fail. Pinecone's numbers above give the cost argument for the same design, but the safety argument is stronger: namespaces are stored separately, so a namespace-per-tenant layout gives physical isolation between tenants, and offboarding a tenant is a namespace delete, which Pinecone describes as a lightweight and almost instant operation (Pinecone, [Implement multitenancy](https://docs.pinecone.io/guides/data/implement-multitenancy)). The same shape in Postgres with pgvector is a tenant column with row-level security, or a partitioned table per tenant, and the trade-off between the two is the trade-off this chapter asks you to measure: pgvector keeps the embeddings in the same rows as the relational data they describe, so a retrieval query is one SQL statement with ordinary `WHERE` filters instead of a fan-out to a second system, which is why the code defaults to SQLite for the exercises and documents the Postgres with pgvector upgrade path, with the schema and the SQL included, rather than requiring a running database to learn the pattern (pgvector, [github.com/pgvector/pgvector](https://github.com/pgvector/pgvector)). One more isolation rule deserves stating plainly, because it is the one that gets skipped under deadline pressure: the semantic cache is also tenant-scoped, since a cached answer for one tenant's question is that tenant's data, and a shared cache across tenants would leak answers even if the underlying store were perfectly isolated.

## The mechanism, part five: context compression and dynamic token budgeting

With the tiers, the gate, the eviction rules and the isolation in place, the last mechanism is the one that decides what the model actually sees on any given task, and it is best understood as a budget with a rebalancing rule rather than as a fixed allocation. Start with the total prompt budget for the task, which is the context window minus the system instructions, the tool schemas and a safety margin, and then allocate it across the tiers in proportion to what the task needs, not in fixed percentages. A new task with an unknown customer needs more episodic retrieval and less semantic recall, while a returning customer's routine request needs the opposite, and a task that hits a contested memory needs headroom reserved for the conflict note, so the allocator in the code takes the task type as an input and rebalances on every call. The worked allocation in the exercises uses a 4,000-token memory budget as its example, split as 1,600 tokens for working memory, 1,400 for episodic retrieval, 600 for semantic facts and 400 held in reserve, but the numbers themselves are an example, not a prescription, and the exercise asks you to re-derive them from your own retrieval measurements, because a budget that is not measured is just a guess with arithmetic attached. Compression is what happens inside each allocation when the retrieved material does not fit, and it happens in three stages of increasing loss, so that the system degrades gracefully instead of truncating mid-sentence. First the system drops the lowest-ranked items entirely, which loses recall but preserves the fidelity of what remains. Then it summarises the survivors, replacing a full episode with a two-line abstract and a pointer to the full record, which preserves the gist at roughly a tenth of the tokens. That second stage is a real model call in the code when a summariser is supplied (`TokenBudget.compress` takes an optional summariser, wired to the model in `code/llm_summariser.py`); without one it keeps a head excerpt that is labelled as an excerpt, not a summary, because a head excerpt is not a summary and must not be presented as one. And only then, if the budget is still exceeded, it truncates the oldest working-memory turns, which is the MemGPT flush in miniature, and it does so after writing a recursive summary of what left, so that the evicted material survives in compressed form rather than vanishing. The semantic cache from the GPT Semantic Cache paper belongs in this section too, because it is compression at the level of the whole call: when a new query is semantically close enough to a cached one, at a cosine similarity of 0.8 or above, the cached answer is returned without invoking the model at all, which is the cheapest token budget of all — zero. Finally, the budget is enforced by measurement, not by hope: every task logs the tokens each tier actually consumed, the cost model turns those tokens into a cost per task, and the weekly review asks the only question that matters, which is whether the memories that cost the most tokens are also the memories that change the most outcomes, because a tier that is expensive and rarely decisive is a tier whose budget should shrink.

## The mechanism, part six: keeping a long run honest — compaction, pruning, rot, and lazy loading

The mechanisms so far answer what the agent should remember between tasks, and this section answers the question that follows once a single task runs long, which is what the agent should still be carrying by turn forty, because a long run does not fail the way a short one fails: it fails by accumulation. Picture the layers the agent is actually reasoning over as a stack, widest at the bottom and narrowest at the top, and the whole section that follows is about moving information down that stack before the top gets too heavy to think with. At the very top sits the prompt itself, the system instructions and the tool schemas, which are always present and therefore must stay small. Below it sits working memory, the live transcript and scratchpad of the task in hand. Below that sits episodic memory, the summaries of past tasks the agent can pull in when the current one resembles them. Below that sits semantic memory, the settled facts and rules. And at the bottom sits the external store and the graph, the full records and the entity relationships that the upper layers only ever point at, never carry. Compaction and lazy loading are the two moves that keep that stack honest: compaction pushes what is live in working memory down into a denser form before it overflows, and lazy loading refuses to pull anything up the stack until the step that needs it actually asks for it, so the reader can place every technique below on that stack and see at once whether it is pushing down or pulling up too early.

Compaction is the push-down move, and it is worth naming precisely, because it is not truncation and it is not the three-stage compression of the previous section, even though it uses summarisation as one of its tools. Where compression shrinks retrieved material to fit a budget, compaction rewrites the live transcript and the scratchpad themselves into a compact state summary — the decisions taken so far, the open questions still unanswered, the tool results that are still load-bearing, and the history of what has already been tried and failed — and then restarts the loop from that summary as if it were the beginning of the task, with the old transcript retired. The trigger is the pressure point this chapter already established, which is why it needs no new constant: when the prompt reaches about 70% of the context window, the point at which MemGPT inserts its memory-pressure warning ([arXiv:2310.08560](https://arxiv.org/abs/2310.08560)), that is the moment to compact, because waiting until the window is full means compacting under duress, with the model itself choosing what to keep, and a model under token pressure is exactly the wrong editor for its own memory. What must survive a compaction is everything the next step cannot re-derive: the decisions already made and why, the open questions, any tool result the plan still depends on, and the failure-signature history, the record of approaches already tried that did not work, because without that history the agent will cheerfully retry the dead end it already exhausted. What may be dropped is everything already consumed: the verbatim tool outputs whose conclusions have been extracted, the superseded plans, the exploratory turns that led nowhere, and the chatter of a plan that was replaced. And the failure mode to design against is the quiet one, which is a bad compaction that drops a decision without saying so, so that ten turns later the agent re-decides the same question differently — in the support copilot, it re-decides that a refund needs no approval after the June policy had already settled it, and nothing in the transcript contradicts it, because the contradiction was compacted away. The defence is to make compaction auditable in the same way the write gate is auditable: the compacted summary must list the decisions it preserves, each with its source, so that a dropped decision is a visible omission rather than a silent one, and the code in `code/compaction.py` implements exactly that check, refusing to call a compaction complete unless every load-bearing fact the caller named is present verbatim in the summary.

That same shape shows up in a production coding harness, which is worth noting because it shows the stack above at work in a real system, over runs that last hours. Claude Code, one widely used coding harness, organises its memory into four layers, running from durable project instructions that are always present, through session notes and the working transcript, down to external files and records that are only ever pointed at, and it compacts those layers through five levels, so that each level rewrites the material below it into a denser form and the most durable facts are the last to be compressed away. The shape is the stack at the top of this section, and the staged degradation is the three-stage compression of the previous section, applied to a run where a single flat transcript would rot long before the task finished. The scale of what a harness adds is visible in Anthropic's comparison of its Opus 4.5 model on a retro-game task: the bare model took 20 minutes and cost $9, while the harnessed version took 6 hours and cost $200 (Anthropic, [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)), a longer and more expensive run that finished work the bare model could not, which is the trade the memory layers exist to make, spending context and time on remembering well so that the run survives long enough to finish.

Tool-result pruning is the same instinct applied one level down, to the single largest consumer of context in most agentic runs, which is the output of the tools themselves, because a tool that returns a whole page of search results or a whole billing record hands the agent far more than the next step needs, and every token of it is re-paid on every subsequent turn. There are four ways to prune it, and a production agent uses all four, choosing by what the next step actually needs. First, summarise it: replace the full output with its conclusion and the few figures the plan depends on, by a real model call in the code (`prune_tool_result_with_llm` in `code/compaction.py`, cheap judge route, temperature zero), which on the demo's billing record turned 379 estimated tokens into 38 while keeping the plan, the renewal date, the seat count and the invoice figures exact; the 5,000-token tool output becoming roughly 500 tokens in the lesson is the same ratio as a worked example rather than a measured figure, and the offline fallback without a model backend keeps a head excerpt labelled as an excerpt, not a summary. Second, keep only the fields the next step needs: if the plan needs the customer's plan name and renewal date, pass those two fields and drop the rest of the record. Third, pass a pointer instead of the content: store the full result in the episodic tier or an external store, and put only a reference in the prompt, such as the record identifier and a one-line description, so the agent can retrieve the full result if a later step asks for it, and pays nothing for it until then. And fourth, expire it: a tool result that was only needed for one step, such as the list of candidate tickets consulted to pick one, should be marked single-use and dropped once that step is done, rather than carried forward out of inertia. The design-review angle here is the same as for the write gate, which is that the strong answer names the mechanism and then names what it costs: summarising loses detail the model can no longer check, a pointer adds a retrieval round-trip when the detail turns out to matter, and expiry is only safe when the result genuinely has no second use, so the choice is a judgement about the next step, not a default.

Context rot is the name for what happens when those two defences are missing, and it deserves to be named as a failure mode in its own right, because it is the failure the previous sections have been circling without labelling. It works through two distinct mechanisms, and confusing them is itself a design error, because each one needs a different fix. The first is attention dilution, which is the quieter of the two: as the context grows, the relevant facts are buried under volume, and the model stops using them, not because they were deleted but because they are too far away and too surrounded to win attention, which is the same degradation the Mem0 authors describe when they note that extended context windows alone do not solve long-term coherence. The fix for dilution is the one this section has already built: compaction, pruning, and lazy loading, all of which reduce volume. The second mechanism is behavioural contamination, which is the louder one: stale instructions, superseded plans, or a wrong intermediate conclusion linger in the context and actively steer later steps, so the agent is not merely forgetting the right fact but following the wrong one, and the March-versus-June policy is the running example — the March rule sitting in the transcript after June has superseded it is not a memory problem, it is a live instruction to do the wrong thing. The fix for contamination is not volume reduction but the eviction and conflict handling of the earlier sections: versioned supersession, the contested flag, and expiry, applied to the live context as well as to the store, because a superseded plan in the transcript is as dangerous as a superseded fact in the semantic tier. Put together, rot is the reason the budget in the previous section is not enough on its own: a context can be under budget and still be rotten, full of stale instructions the model will follow faithfully, which is why the code adds a rot detector alongside the budget check, flagging a transcript whose tokens are mostly old or whose instructions are known to be superseded, before the next step runs on it.

Lazy loading is the counterweight to all of this, and it is the simplest idea in the section to state and the hardest to keep to under deadline pressure, which is: do not put it in the prompt until the step that needs it asks for it. Eager context stuffing — loading the customer's whole history, every policy, and every past episode into the prompt just in case — is how a context rots before the task has even started, because most of what was loaded will never be used, and all of it dilutes and contaminates what is. The lazy alternative is retrieval on demand, which is the episodic and semantic tiers doing their job as designed, pulling in only the memories that match the current step; tool-result pointers, which are the pruning technique above used as a loading discipline, so that a large result is fetched only when a step names it; and deferred episodic recall, where the agent does not reach for past episodes at the start of the task at all, but only when it hits a step it has seen fail before, which is the moment the episode is actually decisive. The trade-off to state plainly is that lazy loading costs a retrieval round-trip at the moment of need, and a step that needs a fact it did not ask for will stall, so the design rule is to load eagerly only what every step of the task needs — the system instructions, the current goal, the decisions already taken — and to load everything else lazily, on demand, with a pointer standing in for it until then.

### Progressive disclosure: give the agent a map, not an encyclopedia

Lazy loading answers when the agent should pull material into context, and progressive disclosure answers how that material should be organised so the agent can find it without loading all of it, which makes the two techniques partners: lazy loading is the discipline of waiting, and progressive disclosure is the structure that makes waiting cheap. Progressive disclosure means organising everything the agent might need into layers, where the top layer is a compact index that names what exists and where it lives, and each deeper layer holds the detail for one topic only, so the agent reads the index first and then opens only the layers its task actually touches. The concrete form of the index is a short file at the root of the project, conventionally called AGENTS.md, and a good one fits on a single screen: it states what the project is, lists the commands for building, testing and linting, names the conventions the agent must follow, and points at the deeper documents, the architecture notes, the deployment runbook and the data model, with one line each saying what lives there (OpenAI, [Harness engineering](https://openai.com/index/harness-engineering/)). The agent therefore starts every task by reading a short map, and it loads a runbook only on the task that needs the runbook, while the rest of the documentation stays on disk, unread and unpaid for. That last point is where the technique earns its place in a chapter about budgets, because context is re-sent to the model on every call, so every token loaded is a token paid for on every turn of the run: a manual stuffed into the prompt at the start costs its full size multiplied by the number of turns, while a map plus one loaded chapter costs the map on every turn and the chapter only on the turns that need it, which is why the same run can cost a fraction as much and still have the detail available when it matters. The cost argument has a quality argument riding alongside it, because a prompt full of unread documentation dilutes attention and contaminates behaviour in exactly the ways the rot section describes, while a map keeps the prompt small and lets each loaded layer arrive at the step that asked for it, fresh and relevant. A worked template for such an index lives in this course at [templates/AGENTS.md](../templates/AGENTS.md), and Exercise 7 asks you to write one for the support copilot and measure the difference it makes. The idea generalises beyond files on disk: the same layering applies to [tool schemas](../chapter-02-tool-use-mcp/README.md), where the agent first sees a short description of each tool and loads the full schema only for the tool it is about to call, and to the memory tiers themselves, where the semantic tier's one-line facts are the map and the episodic tier's full records are the detail behind it, so once you have the habit of disclosing progressively, you will find it everywhere the agent meets more material than one prompt can hold.

One more technique belongs in this section, not because it is a prompt change but because it is what you reach for when the prompt changes have stopped working, and that is Retrieval-Augmented Fine-Tuning, known as RAFT ([arXiv:2403.10131](https://arxiv.org/abs/2403.10131)). RAFT is a training recipe, not a context trick: the model is fine-tuned on question-and-answer pairs presented with retrieved documents in context, including distractor documents that do not help answer the question, so that it learns to use the retrieved evidence that matters, to cite the relevant passage, and to ignore the documents that do not help — in the paper's own framing, to become a better open-book exam taker. It fits exactly where this chapter's retrieval is good but the model is not: when the episodic and semantic tiers are returning the right memories and the model still ignores them, quotes the wrong one, or gets misled by a plausible distractor, no amount of prompt engineering will fix a model that has never been trained to distrust its context, and that is the symptom RAFT is for. Its cost is also exactly what makes it a last resort rather than a first one, which is that it is a training run, with a training dataset to build, a fine-tune to run and evaluate, and a model to version and deploy, rather than a prompt change you can ship in an afternoon, so the advanced-level answer is to reach for it only after you can show, from your own retrieval logs, that the retriever is returning the right material and the model is misusing it — and if you cannot show that, the money is better spent on the retriever, the write gate, or the compaction in this section.

## The grounded numbers, in one place

So that the numbers in this chapter can be checked without hunting through the text, here they are together, each with its source. MemGPT ([arXiv:2310.08560](https://arxiv.org/abs/2310.08560)): main context, comprising system instructions, working context and a first-in-first-out queue with recursive summary, against external context, comprising recall storage and archival storage; a memory-pressure warning at about 70% of the context window and a flush at 100% that evicts about 50%; and on the Deep Memory Retrieval task, accuracy rising from 32.1% to 92.5% for GPT-4, from 35.3% to 93.4% for GPT-4 Turbo, and from 38.7% to 66.9% for GPT-3.5 Turbo. GraphRAG ([arXiv:2404.16130](https://arxiv.org/abs/2404.16130)): comprehensiveness win rates against naive Retrieval-Augmented Generation (RAG) of 72–83% on podcast transcripts and 72–80% on news articles, diversity win rates of 75–82% and 62–71%, all with p < .001, and the root-level variant retaining a 72% comprehensiveness and 62% diversity win rate at a fraction of the cost. GPT Semantic Cache ([arXiv:2411.05276](https://arxiv.org/abs/2411.05276)): up to 68.8% fewer API calls, hit rates of 61.6–68.8%, a positive hit rate above 97%, and a cosine threshold of 0.8 as optimal across a 0.6–0.9 sweep, from the arXiv paper and not from the GPTCache library. Pinecone multitenancy ([Design for multitenancy](https://docs.pinecone.io/guides/data/design-for-multitenancy)): 1 read unit per 1 GB of namespace searched, minimum 0.25 read units, so 100 tenants at 1 GB each cost 1 read unit per tenant-scoped query against 100 read units for metadata filtering across a shared 100 GB namespace, with `$in` and `$nin` filters capped at 10,000 values. OpenAI embeddings: text-embedding-3-small at $0.02 per 1M tokens (OpenAI pricing, [platform.openai.com/docs/pricing](https://platform.openai.com/docs/pricing)). And Mem0 ([arXiv:2504.19413](https://arxiv.org/abs/2504.19413)): 91% lower p95 latency and more than 90% lower token cost than a full-context baseline, with a 26% relative improvement in the LLM-as-a-judge metric over OpenAI's memory on LOCOMO. Anthropic's harness comparison ([Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)): on a retro-game task, the Opus 4.5 model running bare took 20 minutes and cost $9, while the harnessed version took 6 hours and cost $200. Every other number in the lesson, including the worked budget allocations and the cost-per-task examples, is labelled as an example or an assumption, and the exercises ask you to replace those assumptions with measurements from your own traffic.

## The advanced-level design-review angle

In a design review, the engineer who says "I would give the agent a bigger context window" has described a purchase, not a design, and the engineer who says "memory is a write-gated, versioned, tenant-scoped store with a token budget" has described a system, so the difference this chapter is trying to build is the difference between those two sentences. Expect to be pressed on the write gate first, because it is the decision that reveals judgement: what earns a write, what is deduplicated, what is refused, and who is accountable when the gate is wrong, and the strong answer names the five gate questions above and then admits the trade-off, that a strict gate under-remembers and a loose gate over-remembers, and that the right strictness is measured by retrieval precision on real traffic rather than chosen by taste. Expect to be pressed on conflicts second, because the March-versus-June policy is the question that separates engineers who have shipped from engineers who have read: the strong answer describes versioned supersession, the authority check, the retained superseded record, and the contested state that routes to a human, and it does not claim the system can resolve a genuine disagreement on its own. Expect to be pressed on cost third, and here the strong answer does the arithmetic out loud: embedding at $0.02 per 1M tokens is negligible, the prompt tokens are the bill, the semantic cache removes up to 68.8% of calls on repetitive traffic, and a namespace-per-tenant layout costs 1 read unit where a shared namespace with metadata filtering costs 100, so the layout decision is a hundredfold cost decision before it is a safety decision. And expect to be pressed on failure modes last, because an experienced engineer is hired for what happens when the system is wrong: the answer is that a poisoned memory is corrected by supersession rather than deletion, a leaked memory is prevented by structural tenant scoping rather than by remembering a filter, and a bloated memory is controlled by eviction policies with a measured half-life rather than by hoping the window grows. If you can tell that story as one connected argument, starting from the cost of a token and ending at the audit trail, you are answering as the engineer who would own the system, not as the engineer who would merely use it.
